## Document authority

This document drafts the planned heavy-asset publication contract (HAP-001): how an artifact a harness or generation tool produces while running inside a Git project — a PDF, a DOCX, an image, a recording, a dataset, an archive — is classified, where it is allowed to land, how the producing process learns where to write, how the artifact is published into the heavy-asset tier that [ADR-0003](adr/0003-local-markdown-and-tiered-assets.md) names and registered in the Context Catalog, what its states mean, what happens when it lands in the wrong place, how outputs of a process Omnifrons never launched are brought in, and the failure states and conformance tests the storage plane has lacked. ADR-0003 is the decision this contract makes executable; its rationale is not restated here. The [target architecture](target-architecture.md) governs any conflict.

This draft does not redefine work already owned elsewhere:

- **[ADR-0003](adr/0003-local-markdown-and-tiered-assets.md)** owns the locality decision: always-local Markdown, the separate blob tier, the Catalog's read-side record, hydration, the initial Linux backend, and the ban on synchronizing a live `.git` directory through a consumer cloud folder. HAP-001 adds the write half — how bytes enter the tier and how a Catalog record comes to exist — and never widens what ADR-0003 decided.
- **AEC-001** ([adapter-feed-events.md](adapter-feed-events.md)) owns the feed envelope, the `ref` shape `{ kind, id, locator }` with its `unresolved` state, the `scope.declared` payload, and the approvals write path. HAP-001 adopts the `ref` shape unchanged and proposes three additions — an `asset-binding` in `scope.declared`, an `artifact.state` event kind, and an `artifact-publication` approval category — recorded under [Proposals carried to other drafts](#proposals-carried-to-other-drafts) as proposals, not adoptions.
- **[RCS-001](renderer-content-security.md)** owns downloads, attachments, the quarantine directory, and the file-name sanitization rule (RCS-001-R10, RCS-001-R11). - **[MRP-001](migration-and-recovery-plan.md)** owns deletion through tombstone kind `artifact` and the best-effort backup of the tier (MRP-001-R11, MRP-001-R19, MRP-001 D10). HAP-001 defines no deletion or backup path; it names the publication identity a tombstone refers to.
- **[HTP-001](handoff-transaction-protocol.md)** owns the handoff state vector, which carries artifact references by identity only (HTP-001-R18), and consumes the portable-work contract's handoff candidate build without adding exclusions of its own. - **RSP-001** ([roaming-and-engram-sync.md](roaming-and-engram-sync.md), [workspace-roaming-protocol.md](workspace-roaming-protocol.md)) owns device-local memory scope roots (RSP-001-R14) and credential custody (RSP-001-R6), and replicates the memory plane only. HAP-001 proposes scenario rows whose `Discharges` column names requirements defined here, never a requirement of VP-001's own (desktop-stack-verification-plan.md § Scenario catalog ("names the requirement id, in the owning contract")).
- **[Versioning and compatibility](versioning-and-compatibility.md)** owns the workspace-layout vocabulary this contract reuses, the reserved `.omnifrons/` namespace the policy and the default outbox live under, and the version domains table this contract proposes a row for.

## Purpose and scope

HAP-001 governs the **write path into the heavy-asset tier**: how an artifact produced while a harness runs with its working directory inside a Git project is classified, where it may land, how the producing process learns where to write, how the artifact becomes a published and registered asset with a portable reference, which states it passes through, what happens when it lands somewhere else, how the output of a process Omnifrons never launched is ingested, and how each failure is shown, recovered, and tested.

In scope:

- artifact classes, the per-project classification policy, and the role that owns it;
- the destination mapping per project — an asset root as a Catalog identity plus a provider locator — and per device — device-local paths that never roam, including the product's own work area;
- the outbox: the one harness-facing output directory inside the project, its per-run subdirectories, attribution, and its exclusion from handoff candidacy and scans;
- discovery for writes: the run subdirectory declared to a mediated run, the guidance note an unmediated producer reads, and the ways publication is requested;
- the publication transaction: validation order, the single-handle discipline, publication, Catalog registration, publication identity, idempotent retry, entry retention, and recovery after interruption;
- the artifact state vocabulary and the feed event proposed for AEC-001;
- wrong-root detection and its remedies;
- unmediated producers: the agent guidance note and ingestion of unattributed entries;
- the signal mapping — healthy and failure conditions — of the storage plane's write path;
- the security constraints every step obeys;
- the conformance evidence that discharges this contract's requirements, and the amendments and proposals it requires elsewhere.

Out of scope:

- the read side — hydration of a remote-only asset, eviction, and remote-only rendering — decided by [ADR-0003](adr/0003-local-markdown-and-tiered-assets.md) and presented by [context-orb.md](context-orb.md);
- the provider adapter's own protocol — how the initial Linux backend is driven, or how a Windows or macOS adapter uses native placeholder APIs — bounded by ADR-0003 and the target architecture; this contract states only the capabilities an adapter must declare;
- deletion of a registered artifact — [MRP-001](migration-and-recovery-plan.md)'s tombstone kind `artifact`;
- backup of the tier — MRP-001-R19 and MRP-001 D10;
- downloads and attachments the renderer receives — [RCS-001](renderer-content-security.md);
- Git-tracked content itself — the portable-work contract and TM-001's Git surface govern what enters a handoff or a commit; this contract decides only that a file so classified never enters the tier through it, and proposes one exclusion to the handoff candidate build;
- what a harness does with the guidance files it reads — the prompt-injection surface [TM-001](threat-model.md) owns;
- Markdown — never an artifact of this contract (target architecture, invariant 11).

This contract holds identically under every scope mode ([Scope modes](target-architecture.md#scope-modes)). What changes with the mode is not the rule but the honesty of the label: only `sandbox-enforced` can prevent a write outside the project, and every mode discloses that a write inside the project but outside the outbox is detected afterwards, never prevented ([Wrong-root detection and remedies](#wrong-root-detection-and-remedies)).

## Problem statement

An agent runs with its working directory inside a Git project and produces a forty-megabyte PDF report. It writes the file next to the source it read, because that is the only location it knows. The next handoff candidate blocks on an oversized binary (target-architecture.md § Initial exclusions and blocks ("Binary or oversized files block")), or the user commits it, and the vault's Git transport — meant for Markdown and small portable state — now carries a deliverable it will never need again and cannot forget.

A second agent writes its recording into an "output" folder a consumer sync client happens to mirror. The bytes reach a cloud; nothing registered them. The Context Catalog knows nothing, the Orb draws nothing, and on the next device the folder holds a placeholder the product never promised to hydrate.

A third generation tool remembers the output path from its previous invocation and writes into another project's directory. Nothing in that project asked for the file, and no scan of the current project will find it.

Nothing failed. Each tool wrote exactly where it was pointed or where it defaulted. The reads are already covered — a harness receives selected content plus provenance, never an unrestricted path (target-architecture.md § Workspace and artifact access ("mediated, bounded, read-only retrieval")) — but no contract says where a generated heavy artifact belongs, who decides, how the harness is told, what turns the file into something another device can reference, or what to do when it lands in the wrong place. Between a tool that writes faithfully and a tier that only Omnifrons should fill there is no owning contract; that seam is this document's scope.

**The harness never holds write authority over the heavy-asset tier: it writes into the project's outbox — a run subdirectory it was told about — and requests publication; Omnifrons validates, publishes, and registers; only a registered artifact has a portable reference; and an artifact in the wrong place is reported, never moved.**

Terms already defined by another artifact are used with that artifact's meaning and are not redefined; only terms this document introduces, or narrows for its own purpose, appear below. Where this document says *handoff candidate*, it means the portable-work contract's candidate tree; a *candidate entry* is this document's own term for a file in the outbox awaiting validation, and the two are never shortened to the same word.

## Design rules

Binding for every section below:

1. **Mediated publication, never direct write authority.** A harness is told where to write — a run subdirectory of the project's outbox, inside the project it may already write to — and never receives write authority over the tier, over another project, or over the vault. The only write path into the tier is Omnifrons's validate–publish–register transaction; anything else is the separate itemized elevation the target architecture already requires for direct access outside the project (target-architecture.md § Workspace and artifact access ("separate itemized elevation")).
2. **Classification is declared policy, not inference.** A per-project policy maps a declared class, a detected type, and a size to a destination. Source, configuration, and small portable text may remain in Git under an approved policy; the rule is never "every non-Markdown file goes to the tier".
3. **Identity is logical; paths are device-local.** An asset root is an asset root identity plus a provider locator, and an artifact is an artifact Catalog identity. A device asset path, the product work area, or a run subdirectory's path exists only in device configuration and in the launch environment of the process that needs it, never in a record, a feed event, a startup brief, an envelope, or an IPC payload (AEC-001 design rule 6; RCS-001-R14; HTP-001-R18).
4. **Discovery for writes is declared, and asymmetric.** The launch plan tells the harness where to write; nothing tells the harness where the artifact ends up. A publish response carries a portable reference, never a destination path.
5. **Validate, then publish, then register; one handle, one digest, one source of bytes.** Every check runs before a byte leaves the outbox, on the one handle the entry was opened with; the digest computed from that handle is the digest the record carries; the bytes that leave the outbox come from that same handle, never from whatever a path names later; an entry is removed only after the published copy is verified and the record exists.
6. **States are distinct, and availability is observed per device.** `candidate`, `published-local`, `registered`, and `provider-synced` are four facts, never one. A record does not make bytes local anywhere, and no device infers another device's availability.
7. **Wrong root is reported, never repaired silently.** A misplaced artifact is flagged with a remedy choice and is never moved, deleted, or published without it. `.gitignore` neither untracks a file nor governs a provider, so it is never a control.
8. **Observation, never control.** `artifact.state` describes what happened (AEC-001 design rule 2); a publication request is an approval item, never an effect the feed produces.
9. **Content is never authority.** Only a device-local human approval bound to identity-evidence facts can approve a publication (TM-001-R1, TM-001-R7); HAP-001-R22 enumerates what cannot, and a registered artifact gains no trust by being registered (target architecture, invariant 9).
10. **One outbox, one pipeline; attribution is a claim the run itself makes.** Mediated and unmediated output share the outbox and the same ingestion, validation, approval, publication, and registration; an entry is attributed to a run only where it lies under that run's subdirectory and the run's own proposal names it by digest, and location alone never attributes and never satisfies a standing approval.

## Artifact classes and classification policy

The vocabulary is the [compatibility policy](versioning-and-compatibility.md)'s (versioning-and-compatibility.md § Workspace layout ("portable, generated, local, reconstructible, or user-editable")), extended by one class:

| Class | Meaning | Default destination |
| --- | --- | --- |
| `portable` | Small text Git carries as part of the workspace — source, configuration, OpenSpec content | `git-tracked` |
| `generated` | Output the workspace's own build reproduces; small enough and textual enough to live under Git or its ignore rules | `git-tracked` under the project's own ignore rules |
| `local` | Device-local state — machine-local content under `.omnifrons/`, device configuration | Never published and never a candidate entry |
| `reconstructible` | Caches, indexes, traces | Never published |
| `user-editable` | Content the user owns and edits; notes belong to the knowledge plane, other user-editable files stay Git-managed | `git-tracked` |
| `generated-heavy` | An output a harness or generation tool produces that is not a Markdown note and that policy routes to the tier — PDF, DOCX, image, audio or video recording, dataset, archive | `asset-root` |

Rules:

- **Declared, not inferred** (HAP-001-R1). A publish request declares the class; a policy row also matches on the detected type — extension plus magic bytes, the same identification RCS-001 applies to executables (renderer-content-security.md § Content classes and rendering modes ("identified by the OS's own extension list")) — and on size. Where the declared class and the detected type disagree, the policy row for the detected type wins and the disagreement is shown at approval.
- **Git-managed files stay Git-managed** (HAP-001-R3). A candidate entry whose destination is `git-tracked` reaches its tracked path only through an explicit user action naming the target — an ordinary workspace write, subject to the portable-work contract's exclusions ([Initial exclusions and blocks](target-architecture.md#initial-exclusions-and-blocks)) — never through the publication path, and Omnifrons never commits it.
- **Markdown never** (HAP-001-R2). A Markdown note is knowledge-plane content: always local, non-evictable, and outside this contract (target architecture, invariant 11).
- **Executables go to quarantine** (HAP-001-R4). A candidate entry identified as executable is classified `quarantine` and is reveal-only there (RCS-001-R11); a policy row routing executables to the asset root is valid only when it records the Asset Policy Owner's approval of that row.
- **No matching row blocks.** An entry no row matches renders `unclassified` and waits for the Asset Policy Owner; the decision creates a policy row, never a one-off exception, so the next entry of the same kind classifies itself.
- **Owner.** The Asset Policy Owner (D2) approves a project's policy and its changes; while the role is vacant, the Project Owner exercises it. Nothing in the policy is binding before that approval — the same discipline GOV-001 applies to its own tables (governance.md § Role catalog ("catalog below is a proposal")).
- **Where the policy lives.** The product ships the table above as the default policy; a project's policy is that default plus its own rows and, when declared, the outbox path ([Outbox](#outbox)), recorded as portable configuration under the reserved `.omnifrons/` namespace and versioned under the record and locator domain proposed in [Amendments this contract requires](#amendments-this-contract-requires). A policy is secret-free and path-free like every portable configuration (versioning-and-compatibility.md § Portable configuration ("Portable configuration is secret-free")) — the outbox path is a project-relative name, not a device path; it maps classes to destinations and grants nothing — a synchronized policy is untrusted content that cannot authorize a write (HAP-001-R40; target architecture, invariant 9).

## Destination mapping

### Per project

A project's asset root is its asset root identity paired with the provider locator of the root object the provider adapter created for it. The pair is recorded in the Catalog and carried in the scope's asset binding; it is the only way the asset root is ever named. Every artifact published there takes an artifact Catalog identity — the asset root identity paired with the artifact's publication identity. A project has one asset root by default; routing classes to several roots is not drafted here.

### Per device

Each device keeps a device asset path table — asset root identity to the device asset path where that root's contents are materialized — and the product work area, Omnifrons's own device-local, owner-only directory for recovery entries and the publication journal. Both are device configuration under the same rule RSP-001 applies to memory scope roots (RSP-001-R14): declared per device, never replicated, never derived from synchronized content. A Windows or macOS device path is never the canonical reference for anything; whether such paths are stored at all, or derived from a per-OS default and never written down, is D8.

A device asset path and the product work area are canonicalized before any authorization that names them (target-architecture.md § Workspace and artifact access ("Canonical paths resolve symlinks/junctions")). Either that resolves inside a registered workspace root or inside the vault is refused at configuration time, and both are re-canonicalized and re-checked against every registered workspace root and the vault afterwards — the device asset path at every publication (HAP-001-R14), the product work area at every use and on every workspace registration (HAP-001-R7) — a workspace registered after configuration, or a root that moved, must not silently turn the tier or the work area into part of a worktree. A path the product can recognize as a consumer sync client's folder is refused the same way, with the disclosure that such recognition cannot prove absence: the tier is separate physically as well as logically (adr/0003-local-markdown-and-tiered-assets.md § Decision ("physically and logically separate blob tier")). The product work area is never declared to a harness and never a harness output location; where it lives is D1.

### Provider adapter capabilities

Every provider adapter implements the same catalog, hydration, integrity, failure, and eviction contract (target-architecture.md § Local Markdown and tiered heavy assets ("same catalog, hydration, integrity, failure")) and declares, per adapter:

| Capability | Values | Meaning |
| --- | --- | --- |
| `publish_mode` | `copy` \| `move` | How the published bytes leave the outbox. `copy`, the default, reads them from the held handle. `move` is permitted only when the adapter declares a handle-anchored move as [Definitions](#definitions) defines it. A path-based rename is never a publication mechanism, because it would move whatever the path names at that moment rather than what was digested and approved. Either way the published copy is re-verified by digest (HAP-001-R17) |
| `confirmation_kind` | Adapter-defined token | The observation that yields `provider-synced` — for the initial Linux backend, a list operation after an explicit upload reporting the object with matching size and, where exposed, digest (D6) |
| `object_limit` | Size or `unknown` | The largest object the provider accepts; consumed by the size check (D4) |
| `quota_visibility` | `visible` \| `unknown` | Whether remaining provider quota can be read through the adapter and shown |
| `native_placeholder` | `yes` \| `no` | Whether the adapter uses a platform placeholder and hydration API rather than explicit operations; never changes the confirmation rule |

The adapter runs inside Omnifrons's own process boundary behind the `BlobStorePort`; its credentials live in the OS secret store under the custody classes the target architecture defines and are never part of a harness launch (HAP-001-R37). The provider is driven through explicit operations only: a mounted folder, a background synchronization client, or a folder such a client mirrors is never an asset root (adr/0003-local-markdown-and-tiered-assets.md § Decision ("background synchronization engine")).

### Asset binding

A context scope today carries a knowledge root, a memory binding, a delivery binding, and an agent binding ([Context scopes and agent bindings](context-orb.md#context-scopes-and-agent-bindings)); AEC-001's `scope.declared` carries references to the first three plus the agent binding ([Scope lifecycle](adapter-feed-events.md#scope-lifecycle)). This contract proposes a fourth, the **asset binding**, with three fields: the asset root identity, the provider adapter id, and the classification policy version in force. A scope without an asset binding has no destination: publication renders `destination-unconfigured` with a setup proposal, and Omnifrons never substitutes a tracked path, the vault, another project's root, or a provider default (HAP-001-R6).

## Outbox

A harness writes where its permission model lets it write. Harness permission models scope file writes to the working directory plus declared additional directories and prompt for anything else; the built-in `claude-code` adapter launches with `dontAsk` (spike-log.md § Slice 3 — first built-in harness adapter → Scope ("--permission-mode dontAsk")), under which anything that would prompt is denied; and a `sandbox-enforced` scope's write set is the project. An output location outside the project is therefore unwritable for a real harness. The outbox is the answer: one directory inside the project root that every producer — a run Omnifrons launched or a process it never saw — writes into, read by one pipeline.

### Declaration

A project's classification policy MAY declare one outbox path relative to the project root; a project that declares none uses the default (D17). The declaring entry lives in the policy under `.omnifrons/`, so that a process reading the folder finds the path without Omnifrons running, while the directory itself may sit anywhere inside the project root. The declared path canonicalizes inside the project root and is not a link; a declaration that fails either renders `outbox-invalid`, blocks ingestion, and blocks every launch that would declare a run subdirectory under it (HAP-001-R8).

The outbox is a location inside the project: readable and writable by anything that can reach the project. It is never the product work area and never the destination of anything — bytes leave it only through the publication transaction.

### Run subdirectories and attribution

For a mediated run, Omnifrons creates a run subdirectory — `<outbox>/<run id>/` by default (D20) — before spawn and declares it to the harness as its output location (HAP-001-R9, HAP-001-R10). Creation is defensive rather than trusting: immediately before it, the outbox path is canonicalized again and confirmed to be a real directory inside the project root and not a link; the subdirectory is then created with a create-exclusive operation that fails if anything — a file, a directory, a link of any kind — already sits at that path, and a failure renders `outbox-unavailable` and blocks the launch; after creation, Omnifrons opens the created directory and verifies by handle that what it will point the harness at is the directory it just created, not something swapped in at the path. Owner-only permissions keep other OS users out; they do not keep out another process running as the same user, which can still write into the subdirectory after creation (TM-001 A6) — a residual this contract discloses and builds attribution around rather than pretending away.

An entry is attributed to a run only when two facts coincide: it lies under that run's subdirectory, and the run's own publish proposal names it by content digest (HAP-001-R11, HAP-001-R12). An entry under a run subdirectory that no proposal from the run names is unattributed — the run did not claim it, so nothing does — and an entry anywhere else in the outbox is unattributed. Location alone never attributes, and never satisfies a standing approval (D3). A run whose transport surfaces no typed proposals — the PTY fallback — therefore produces only unattributed entries; the record still carries the run subdirectory the entry was found under as a location fact, never as provenance (HAP-001-R36).

### Exclusion from handoff candidacy and scans

The outbox sits inside the project, which is exactly where handoff candidates are built from and where wrong-root scans and file watchers look. The portable-work contract excludes ignored files from a handoff candidate and blocks binary or oversized ones (target-architecture.md § Initial exclusions and blocks ("Ignored files are excluded", "Binary or oversized files block")); HTP-001 consumes that handoff candidate as approved under the portable-work contract and adds no exclusions of its own (handoff-transaction-protocol.md § Lifecycle ("candidate per the portable-work contract")). Neither rule names the outbox, so today an outbox entry stays out of a handoff candidate only because it is ignored, or because it is binary or oversized — an ignore rule the user maintains and a size or type block, not a product rule that knows the outbox exists. With every mediated run now writing into the outbox, that gap is load-bearing: this contract requires the outbox to be excluded from handoff candidacy and from the wrong-root verdict of the scan and any watcher by the product's own rule (HAP-001-R44), and the amendment to § Initial exclusions and blocks under [Amendments this contract requires](#amendments-this-contract-requires) is required, not optional. Until it is accepted, handoff preflight discloses which of the two existing rules is keeping each outbox entry out, and shows every outbox entry that would enter a handoff candidate in the candidate preview. The D16 scan and any optional watcher read the outbox as an ingestion source, never as a wrong root.

`.gitignore` remains hygiene: Omnifrons proposes an ignore rule for the outbox so its content stays out of everyday Git noise and out of an accidental `git add`, and the guidance note recommends the same; the rule decides nothing about handoff candidacy, ingestion, or a provider. Where the outbox lives inside the project carries a trade-off of its own, stated in D17: under `.omnifrons/` it sits inside the directory whose portable content Git carries and travels with it unless excluded; as a top-level ignored `outbox/` it is kept out by the existing ignored-files rule but rests on the user's ignore file and sits outside the reserved namespace the layout metadata governs. RSP-001 replication never carries the outbox either way: the memory profile replicates the memory plane only and leaves the knowledge plane to ADR-0003 (roaming-and-engram-sync.md § Purpose and scope ("tiered heavy assets are decided")).

## Discovery for writes

The launch plan declares the run subdirectory to the harness as its output location. Under the slice-3 launch policy the environment is cleared and rebuilt from a fixed base plus an adapter's declared keys (spike-log.md § Launch policy ("plus an explicit allowlist")); the run subdirectory's path is delivered through one declared, non-secret key, proposed as `OMNIFRONS_OUTPUT_DIR`; whether a tool's native output routing may stand in for the key is D7. The key is admitted because it is declared and because it matches none of the secret-shaped patterns the launch policy refuses outright (spike-log.md § Launch policy ("refuses outright")). Its value is the run subdirectory — created before spawn under the project's outbox, keyed by run id, with owner-only permissions. The working directory stays the project's canonical path exactly as today (spike-log.md § Launch policy ("picked workspace's own canonical path")): the run subdirectory is inside that project, so the harness's own permission model already permits the write, and the project remains the requested scope (target architecture, invariant 5).

This is the one place a raw device path is handed to a harness, and it is handed only to the process that must write there. It never reaches a feed event, a startup brief, an envelope, a Catalog record, or an IPC payload (HAP-001-R5). What the harness is not told is as fixed as what it is told: neither a device asset path nor the product work area nor the provider nor any credential crosses the launch boundary (HAP-001-R9, HAP-001-R37).

The instruction that goes with the key — write generated deliverables to the declared output directory, and name each one by content digest in a publish proposal — is part of the adapter's startup context. Under `advisory` scope it is advice a harness can ignore, and the product says so ([Wrong-root detection and remedies](#wrong-root-detection-and-remedies)). A process Omnifrons never launched receives no key at all; for it, the outbox itself and the agent guidance note are the counterpart of this declaration ([Unmediated producers](#unmediated-producers)).

Publication is requested in exactly two ways, and proposed in two more (HAP-001-R12):

- **A typed proposal from the harness.** An adapter surfaces an `artifact.publish` proposal the way it surfaces a tool call — a proposal only, naming entries under the run subdirectory by content digest and relative name, a declared class, a display name, and logical relationships (note, task, or run identities, never paths). Nothing in the harness executes it; the proposal becomes an approval item ([Approvals (feed side)](adapter-feed-events.md#approvals-feed-side)), a proposal from a producer whose verdict is `untrusted` is never accepted (adapter-feed-events.md § Producer identity and key distribution ("renders as `untrusted`")), and the digest it names is what attributes the entry to the run once Omnifrons's own digest from the handle matches it.
- **An explicit user action.** From the artifacts surface of the Studio dashboard ([Dashboard set](context-orb.md#dashboard-set)) or from the approval queue, the user selects a candidate entry and requests publication.
- **A proposal at run end.** When `run.finished` arrives, Omnifrons inventories the run subdirectory and proposes publication for every entry no proposal from the run has named — as unattributed entries — it proposes, never publishes.
- **A proposal at outbox inventory.** At the start of a session for the project and at handoff preflight, Omnifrons inventories the whole outbox and proposes ingestion of every entry it has not ingested or refused unchanged.

Every inventory is passive but not careless: to recognize an entry it has already ingested or refused, it digests entries with the same canonicalize-then-open-without-following-links discipline the transaction uses (HAP-001-R15, HAP-001-R16), so a symbolic link planted in the outbox is never dereferenced during inventory. The response to a publication, whichever way it was requested, is the portable reference and nothing else.

## Publication transaction

The transaction runs in a fixed order; each step must complete before the next begins, and a failure at any step ends the transaction with nothing published (HAP-001-R13).

1. **Location and attribution.** The candidate entry lies inside the project's outbox. An entry under a run subdirectory that the run's own proposal names by digest is attributed to that run — the run is the producer even when publication is requested after the run ended — and every other entry is unattributed (HAP-001-R11).
2. **Classification.** The policy row decides the destination. Only `asset-root` continues; `git-tracked` is offered as a user relocation, `quarantine` as a user move into RCS-001's quarantine directory, `refuse` ends the transaction, and `unclassified` blocks pending the Asset Policy Owner.
3. **Containment.** The entry's path is canonicalized — symlinks and junctions resolved — and must still lie inside the outbox; the device asset path is re-canonicalized and re-checked against every registered workspace root and the vault (HAP-001-R14).
4. **Handle identity.** The entry is opened exactly once, without following links; from that one handle Omnifrons takes every identity fact — regular file, link count, file identity — and never consults the path again for any later step (HAP-001-R15). A handle that is not a regular file is `outbox-escape` (HAP-001-R15); a link count above one is `outbox-linked` (HAP-001-R20). The handle stays open until step 7 completes, within the bound D22 sets on handles held awaiting approval (HAP-001-R17).
5. **Integrity.** The content digest and size are computed once, from the same handle (HAP-001-R16); a known-pattern secret scan runs on the same bytes and produces a warning, never a guarantee (HAP-001-R41). For an attributed entry the digest must equal the one the run's proposal named; otherwise the entry is unattributed (HAP-001-R11).
6. **Approval.** The approval surface shows the identity-bound facts — entry name, class, detected type, size, digest, destination by display name and asset root identity, scope, the producing run or the unattributed fact, and the act-as identity — and the human disposes, while the handle from step 4 remains open (HAP-001-R22). Granularity is D3.
7. **Publish.** The published bytes are taken from the handle held since step 4 (HAP-001-R17): under `publish_mode: copy`, the default, they are read from that handle into the asset root's device materialization; under `publish_mode: move`, only through the adapter's declared handle-anchored move. A path-based rename is never used. Before the bytes move, Omnifrons confirms that the entry's path still names the handle's file identity; if it does not, the outcome is `outbox-escape`, nothing is published, and the held handle's bytes are written to a recovery entry in the product work area, so what was digested and approved is what survives (HAP-001-R18). The published copy is then re-read and its digest compared with step 5's: a match yields `published-local`; a mismatch discards the copy and preserves the entry (HAP-001-R21).
8. **Register.** The Catalog record is written ([Catalog record](#catalog-record)) with its display names sanitized, and the portable reference issued; the artifact is `registered`. No reference exists before this step (HAP-001-R24).
9. **Provider upload.** The adapter uploads through its explicit operations and observes its declared confirmation; the observation yields `provider-synced` (HAP-001-R25). The upload is part of the approved publication when the provider is reachable; when it is not, the record carries `provider_state: pending` and the retry is proposed, run on explicit user action or on a schedule the user configured, never silently; a non-retryable refusal is `failed`, shown with the adapter's reason (HAP-001-R30).
10. **Entry cleanup.** The entry is removed from the outbox only after steps 7 and 8 are verified — never earlier, and never when any step failed (HAP-001-R28; D19).

**Single-handle discipline.** Steps 4 through 7 follow the discipline slice 2's executable prober already practices — canonicalize, open the canonical path once without following a link placed there afterwards, confirm the regular file from that open file's own metadata, hash from the same handle (spike-log.md § Slice 2 — executable identity and approval → What it proves ("then opens the canonical path")) — with the three additions the steps state: the link-count check, the handle held through the approval wait, and the published bytes taken from that handle. Two residuals are disclosed rather than closed (HAP-001-R19). Where the platform offers no equivalent of a no-follow open (spike-log.md § Slice 2 — executable identity and approval → What it defers ("No Windows equivalent of the Linux")), a symbolic link or reparse point placed at the path between canonicalization and the open can redirect that open to another file; every fact, the digest, and the bytes still describe the one file the open landed on, so a hard link is still caught by its link count and the digest and the published bytes cannot diverge, and VP-S27 records the residual. And the `move` fallback's unlink runs only if the source path still names the handle's file identity, but that check and the unlink are two steps with no atomic primitive between them, so a same-user process can swap the path in between and the fallback can at worst unlink a file that was not the one published — the same-user residual TM-001 A6 already records.

**Publication identity.** The publication identity is derived deterministically from the project identity and the content digest. A repeated request for the same identity — a retry after an interruption, a second run producing byte-identical output — acknowledges the existing record, adds the new display name as an alias when it differs, and neither publishes a second copy nor writes a second record (HAP-001-R23). Two projects publishing identical bytes hold two publications; identity is content-addressed within a project, never across projects. That cross-project separation rests on project identity being non-forgeable — an upstream dependency on the registered scope's identity (context-orb.md § Context scopes and agent bindings ("first-class entity naming which world"); RSP-001-R13) that this contract consumes and does not prove; a forged project identity would let one project acknowledge another's publication as its own.

**Journal and recovery.** Every step writes a publication journal entry in the product work area — publication identity, step, outcome, digest, reason, UTC time — before the next step runs. On restart, Omnifrons resumes each incomplete publication from its last verified step: a `published-local` copy without a record is registered; a record whose local copy fails verification is re-published from the retained entry, through a fresh handle and a fresh approval; a record with `provider_state: pending` is offered its upload. Registration and publication recover independently, and an interruption yields a recoverable state or an explicit `uncertain` state, never false completion (HAP-001-R29) — the same retention rule HTP-001 states for a failed handoff publish (HTP-001-R12).

### Catalog record

The record is ADR-0003's Catalog entry — logical identity, relationships, provenance, remote locator, availability, size, and integrity, without content authority (adr/0003-local-markdown-and-tiered-assets.md § Decision ("without becoming the content authority")) — with the fields this contract makes concrete:

| Field | Meaning |
| --- | --- |
| `publication_id` | The publication identity |
| `catalog_id` | The artifact Catalog identity: the asset root identity paired with the publication identity; the `locator` of the artifact's `ref` |
| `asset_root_id` | The asset root identity of the root the artifact was published to |
| `class`, `type`, `size` | The classification outcome, the detected type, and the size in bytes |
| `digest` | The content digest and the identifier of its algorithm (D13) |
| `names` | The display name from the request, plus aliases added by later identical publications; producer-supplied text, sanitized under RCS-001's file-name rule before display or reference (HAP-001-R24) |
| `relationships` | Logical identities of the notes, tasks, and runs the artifact relates to; never a path |
| `provenance` | `scope_id` and the UTC time of every state transition; for an attributed entry also the producing `run_id`, producer identity (`producer_id`, `producer_instance`), adapter id, and a reference to the executable approval record that governed the producing launch — never the executable's path; for an unattributed entry `producer: unattributed`, nothing standing in for those fields, and the run subdirectory it was found under, when there was one, as a location fact only (HAP-001-R36) |
| `provider` | Adapter id, provider locator once uploaded, the confirmation kind observed, and `provider_state` (`pending` \| `synced` \| `failed` \| `unavailable`), with `failed` reserved for a non-retryable refusal (HAP-001-R30) |
| `availability` | Per device identity: `local`, `remote-only`, or `unknown`, each an observation recorded by that device with its UTC time (HAP-001-R27) |
| `state` | The latest state from [Artifact states](#artifact-states) |
| `record_version` | The record schema integer of the proposed version domain |

A record is small portable state: secret-free, path-free, and carried the way other portable state under the reserved namespace is carried (adr/0003-local-markdown-and-tiered-assets.md § Decision ("small portable state")). Where records live and how they travel is D9. On a device that has not verified the bytes, the record renders the artifact remote-only and hydratable only once `provider_state` is `synced`; while the bytes exist only on the producing device, that device renders the reference `unresolved` rather than remote-only-and-fetchable ([Reference resolution](adapter-feed-events.md#reference-resolution)).

## Artifact states

Publication states:

| State | Entry condition | Evidence | What it never means |
| --- | --- | --- | --- |
| `candidate` | A candidate entry exists in the outbox, attributed or unattributed | Outbox inventory | That the entry will be published, or that it has been validated |
| `published-local` | The published copy in the device asset path verified against the validation digest | Publication journal entry for step 7 | That a record exists, that the provider holds the bytes, or that any other device can see them |
| `registered` | The Catalog record exists and the portable reference has been issued | Catalog read | That the bytes are anywhere except where `availability` and `provider_state` say |
| `provider-synced` | The adapter observed its declared confirmation for the uploaded object | Adapter observation, with the confirmation kind recorded | That the artifact is available on another device — that device observes for itself |

Detection condition, outside the publication lifecycle:

| Condition | Entry condition | Evidence | What it never means |
| --- | --- | --- | --- |
| `misplaced` | An artifact was detected at a wrong root | Wrong-root scan, the handoff preflight, or a publish request naming a path outside the outbox | That anything was moved, or that the file entered the publication transaction |

The four publication states are recorded and rendered separately, and the [Signal mapping](#signal-mapping) table is the exhaustive list of state tokens this contract exposes to a product surface — every failure and pending token there is named by the requirement that governs it, and Omnifrons exposes no other (HAP-001-R26). Per-device availability is a separate fact each device observes for itself (HAP-001-R27): a device renders an artifact `local` only after verifying the bytes at its own device asset path by digest; otherwise `remote-only` when `provider_state` is `synced`, and `unknown` when it is not. Hydration, which turns `remote-only` into `local` after explicit download and integrity verification, is the read side ADR-0003 already decides (adr/0003-local-markdown-and-tiered-assets.md § Decision ("triggers explicit hydration")) and is not restated here.

**Feed event.** This contract proposes one event kind, `artifact.state`, carrying a state token, rather than three kinds (`artifact.candidate`, `artifact.published`, `artifact.registered`). One kind mirrors how the feed already carries a lifecycle — `handoff.state` and `sync.state` each carry their state verbatim — and it keeps the closed catalog small; consumers deduplicate on `event_id` either way, and a bootstrap snapshot includes the latest state of every publication not yet `provider-synced`, so a cold start has no dangling artifact reference, the same closure HTP-001 D7 gives handoffs. The payload: publication identity, the artifact's `ref`, the state token, `scope_id`, the producing `run_id` or the unattributed marker, the device that recorded the transition, the confirmation kind when the state is `provider-synced`, and the reason on a failure state — never a path (HAP-001-R35). The event observes; the only mutation is the approval disposition that authorized the publication ([Approvals write path](adapter-feed-events.md#approvals-write-path)). Whether the event kind is adopted, and under which schema version, is AEC-001's decision (D10).

## Wrong-root detection and remedies

An artifact is detected at a wrong root through the mechanisms D16 selects; the default proposal is a scan of the project worktree after every run for new untracked files matching a heavy type or exceeding the size threshold, plus the handoff preflight, which already blocks a binary or oversized file (target-architecture.md § Initial exclusions and blocks ("Binary or oversized files block")) and under this contract offers that file as `misplaced` instead of only blocking. A publish request naming a path outside the outbox is the third source: it is refused and the named file, if it exists inside a registered project, is flagged the same way. The outbox is read by the same scan as an ingestion source, never as a wrong root (HAP-001-R43, HAP-001-R44).

A `misplaced` artifact is offered exactly three remedies, and nothing happens until the user chooses one (HAP-001-R32):

- **Quarantine** — the file is moved into RCS-001's quarantine directory, outside any workspace (RCS-001-R10; renderer-content-security.md § Content classes and rendering modes ("itself lives under the product's")), where it stays unexecuted and reveal-only like any other quarantined artifact.
- **Publish** — the file is copied into the outbox as an unattributed entry and the publication transaction runs from step 1. The copy-in is itself under the single-handle discipline: the misplaced file is opened once without following links, its identity facts and digest are taken from that handle, and the copy is made from it — HAP-001-R15 through HAP-001-R20 applied with the misplaced file as the candidate — so the remedy has no substitution window of its own. The original is left in place; removing it is a separate explicit user action, because the product never deletes a file it did not create — the outbox, declared for consumption, being the one exception this contract states (HAP-001-R28).
- **Ignore** — the decision is recorded against the file's identity and digest, and the file is not offered again until its content changes.

Design rule 7 holds because an ignore rule leaves an already-tracked file tracked, says nothing to a consumer sync client mirroring the folder, and does not move bytes out of the worktree a handoff candidate is built from.

**Output discipline per scope mode.** Only `sandbox-enforced` scope can prevent a write outside the project root, and its write set is the project, which contains the outbox; under it the product reports output discipline as `enforced`. Under `harness-enforced` and `advisory` scope the product reports `advisory` and discloses that a write outside the project is possible and is detected after the run, not prevented (HAP-001-R33) — the containment residual TM-001 already records for a harness under those modes (TM-001 HAR-1) and the target architecture's non-goal of treating `cwd` as a sandbox (target-architecture.md § Explicit non-goals ("UI approvals as a sandbox")). In every mode, including `sandbox-enforced`, a write inside the project but outside the outbox — a tracked path, a source directory — is inside the permitted write set and is therefore detected by the scan, never prevented; the report says so (HAP-001-R34).

## Unmediated producers

Users also run agents on the same project folder outside Omnifrons — another harness, another assistant product, the same agent driven by a different tool. No launch plan declared a run subdirectory to such a process, no run id names it, and no adapter surfaces its proposals; whatever it generates lands wherever it chose. The outbox lowers the friction for that case without widening any authority (design rule 10): a conventional drop location any agent can discover from the folder alone, a plain-English note asking agents to use it, and ingestion of what arrives there through the same transaction as everything else, marked as what it is — unattributed.

### Agent guidance note

Omnifrons provides a short, product-neutral note for the project's agent guidance file — `AGENTS.md` or the harness's equivalent — as the fixed template below, with only the outbox path substituted for `<outbox path>` (HAP-001-R42). Whether Omnifrons writes it into the file itself or only offers it is D18; a write into a tracked guidance file is an ordinary workspace write the user approves. Its last line is true under the default per-artifact approval and carries its own qualification for a project that relaxes D3.

```markdown
## Generated files

- Write every generated file that is not a Markdown note — documents, images, audio, video, datasets, archives, exports — into `<outbox path>`, relative to this project's root. Create the directory if it does not exist.
- If your environment names an output directory for this run, write there instead; it is a subdirectory of `<outbox path>`, and a file you also declare in a publish proposal is recorded as this run's output.
- Keep Markdown notes where this project already keeps its notes, never in `<outbox path>`.
- Never write large or binary files into source or configuration paths, and never commit them; `<outbox path>` should be listed in this project's ignore rules.
- Use a new, descriptive file name for every output; do not overwrite an existing file in `<outbox path>`.
- Treat `<outbox path>` as write-only: do not read, execute, or delete what is there.
- Unless this project has explicitly allowed automatic approval for outputs a run itself declared, a person reviews everything written to `<outbox path>` before it is used anywhere else.
```

The note is advisory in exactly the sense scope mode `advisory` is: it sets expectations and enforces nothing, an agent can ignore it, and nothing about it is containment (TM-001 HAR-1). What it changes is where a cooperative agent's output lands, not what a hostile one can do; wrong-root detection keeps covering everything written anywhere else (HAP-001-R43).

### Unattributed entries

An entry that no run's own proposal names by digest — at the outbox root, or under a run subdirectory the run did not claim it in — is unattributed (HAP-001-R11). It is proposed at the next inventory (HAP-001-R12) and, once accepted, passes the same pipeline as an attributed entry — the same classification policy, the same single-handle discipline with the outbox as containment root, the same approval, the same publication and registration. Nothing is copied before validation; the handle is the source. Its record carries `producer: unattributed` and nothing standing in for a run id, an adapter id, or an executable-approval reference, and the approval surface says so (HAP-001-R22, HAP-001-R36).

The refusal of `untrusted` producers (HAP-001-R22) is about feed-producer verdicts — an adapter instance whose signed proposal fails verification against its paired key. An unattributed entry has no producer and no verdict; nothing proposed it but Omnifrons's own inventory, and the human approves it explicitly with the unattributed fact in view. That explicit approval is the gate, and a standing approval policy (D3) never covers an unattributed entry. The entry's content is as untrusted after registration as any other artifact (HAP-001-R38).

## Security constraints

- **Canonicalization and one handle before authorization.** Every path this contract authorizes — the outbox, a run subdirectory, a candidate entry, a device asset path, the product work area, a quarantine target, a relocation target — is canonicalized with symlinks and junctions resolved before the authorization that names it, and an entry is then judged only through the one handle it was opened with: identity facts, digest, and the published bytes all from that handle, never through a path-based rename (HAP-001-R10, HAP-001-R14, HAP-001-R15, HAP-001-R16, HAP-001-R17, HAP-001-R20). This extends the target architecture's rule to the write side (target-architecture.md § Workspace and artifact access ("Canonical paths resolve symlinks/junctions")) and closes the hard-link case canonicalization alone cannot see: a hard link canonicalizes inside the outbox, is a regular file, and keeps a stable digest, so only the handle's link count exposes it. A run subdirectory is created exclusively and verified by handle for the same reason: a link pre-planted at its path would otherwise point the harness elsewhere.
- **Provider credentials are harness-invisible.** They live in the OS secret store under the custody classes the target architecture defines, are consumed only by the provider adapter inside Omnifrons's process boundary, and are never part of a launch environment: the only environment key this contract adds is non-secret, and the launch policy's secret-shape refusal remains the single choke point for everything else (HAP-001-R37). A missing credential renders `unprovisioned-secret` and blocks provider upload only; local publication and registration proceed.
- **Publication is approval-mediated.** A publication is an action a human approves on the device, bound to identity-evidence facts (TM-001-R1, TM-001-R7; HAP-001-R22), and a synchronized policy cannot stand in for that approval (HAP-001-R40). An unattributed entry is approved with its missing provenance in view and never under a standing policy, and so is a recovery entry; a standing policy, if D3 is ever relaxed, covers only entries a run itself declared (HAP-001-R22). The approval never renders inside a terminal pane (RCS-001-R6).
- **Provenance is recorded** (HAP-001-R36). A consumer reading an artifact reference can trace it to the launch that produced it — or sees `producer: unattributed` and traces it to nothing — and the artifact carries a visible provenance label wherever it is rendered (TM-001-R2). Attribution requires the run's own digest-naming proposal; location alone is recorded as a fact, never as provenance (HAP-001-R11). Producer-supplied display names are sanitized before display or reference (HAP-001-R24).
- **Artifact content is untrusted.** A registered artifact is rendered through RCS-001's attachment class — a quarantined landing, reveal for an executable, external launch only with a gesture and confirmation (renderer-content-security.md § Content classes and rendering modes ("Quarantined landing")) — and registration elevates nothing (HAP-001-R38; target architecture, invariant 9).
- **Secrets are scanned, not proven absent.** The known-pattern scan at validation warns before approval (HAP-001-R41), with the same disclosure the memory plane makes: detection cannot prove absence (RSP-001 D6; TM-001 SEC-3).
- **The outbox is a same-user location inside the project.** A run subdirectory's owner-only permissions keep other OS users out, but any process running as the same user — including every harness the user runs — can read and write there, before and after creation (TM-001 A6); the product discloses this and relies on it for nothing beyond a location fact. The product work area is owner-only and outside every workspace, holds only what the product itself writes, and is re-checked at every use (HAP-001-R7).
- **Open handles are bounded.** Handles held open awaiting approval are capped per project (D22); an entry beyond the cap stays `candidate` and is re-opened under the discipline when its turn comes (HAP-001-R17), so an approval queue cannot be turned into a handle-exhaustion attack.

Each requirement is an acceptance gate with a testable condition.

## Open decisions

These are the questions this draft proposes a default for without yet closing; the Project Owner's recorded approval, not the presence of a default here, is what closes one (governance.md § Document authority ("system proposes, user disposes")). No cadence, cap, or retention window below is a hardcoded constant.

| ID | Question | Options | Default proposal |
| --- | --- | --- | --- |
| D1 | Where does the product work area live, within the bound HAP-001-R7 sets? | The product's application-data directory, outside any workspace; a user-chosen directory that satisfies HAP-001-R7 | The product's application-data directory, the same area RCS-001-R10 sites the quarantine directory in; never inside a workspace root or the vault, and never declared to a harness — it holds only what the product itself writes |
| D2 | What is the name of the role that owns classification and publication policy, and who holds it while vacant? | Asset Policy Owner; Catalog Steward | Asset Policy Owner, matching GOV-001's owner-of-a-policy naming; the Project Owner exercises the role while it is vacant |
| D3 | At what granularity is publication approved? | Per artifact; a per-scope standing policy that auto-approves classes under a size cap; per run | Per artifact in v1. A per-scope standing policy is a later relaxation that may cover only an entry the run's own proposal named by digest (HAP-001-R11, HAP-001-R22) and never `unclassified`, `misplaced`, unattributed, location-only, or recovery entries — an `outbox-escape` is a security-relevant anomaly, and re-publishing its recovery entry always needs a fresh explicit approval (HAP-001-R18) |
| D4 | What size cap and quota apply? | No cap; a fixed cap; the adapter's declared object limit; a per-project quota | The provider adapter's declared object limit governs where one is declared; otherwise no product cap in v1 beyond a free-space check, with the figure revisited on VP-S25 evidence; no per-project quota by default, and provider quota shown whenever the adapter exposes it |

| D6 | Which provider confirmations count as `provider-synced`? | Any successful upload exit status; upload plus a list operation reporting matching size and digest where exposed; a provider-native availability flag | Upload plus a list operation reporting the object with matching size and, where the provider exposes one, digest, as the initial Linux backend's confirmation kind; a native flag is never a confirmation |
| D7 | May an adapter route a generation tool's native output path, or declare a direct output root, instead of the run subdirectory? | Run subdirectory only; a declared direct output root equal to the device asset path; native routing per tool | Run subdirectory only — a direct output root gives the harness write authority over the tier and turns every stray write into a published one; native routing is reconsidered only for a tool that cannot honor a declared output directory, and then as a per-adapter exception under GOV-001's registry |
| D8 | Are Windows and macOS device asset paths stored at all? | Stored as device configuration; derived from a per-OS default and never written; not supported until a native adapter exists | Stored as device-local configuration, never portable, exactly like the Linux path; a per-OS default seeds the value at setup |

## Acceptance evidence and follow-up

The checklist that discharges this contract, each item naming the requirements it evidences:

- **End-to-end publication.** A PDF produced by a harness run lands in the run subdirectory, is named by digest in the run's proposal, is published, is registered with the run's provenance, and receives a portable reference `{ kind: artifact, id, locator }` that resolves on the producing device through the Catalog first ([Reference resolution](adapter-feed-events.md#reference-resolution)); the digest in the record equals the digest computed from the handle; a display name carrying a traversal sequence, a reserved device name, a bidirectional override, or excessive length is normalized or rejected before display; the registered artifact renders through the attachment class, reveal-only when executable, with no elevated trust and no restored approval; and the entry is removed only after the published copy and the record are verified (HAP-001-R9, HAP-001-R12, HAP-001-R13, HAP-001-R16, HAP-001-R21, HAP-001-R23, HAP-001-R24, HAP-001-R28, HAP-001-R36, HAP-001-R38).
- **Git-managed files stay Git-managed.** A source or configuration file under a `git-tracked` policy row is never published to the asset root, is never flagged `misplaced` in its tracked location, and reaches its tracked path from the outbox only by an explicit user relocation (HAP-001-R1, HAP-001-R3); a Markdown note is refused as an artifact (HAP-001-R2).
- **Executable routing gate.** An executable candidate entry is classified `quarantine` and stays reveal-only there; it reaches the asset root only under a policy row that records the Asset Policy Owner's approval, and a row without that record is rejected at policy load (HAP-001-R4).
- **Wrong-root output and its remedies.** An artifact written into a tracked repository path, into another registered project, and into the vault renders `misplaced` in each case, is never moved, and offers the three remedies; the publish remedy copies from a single handle opened without following links and a path swap during the remedy is refused; a matching `.gitignore` rule changes nothing; the output-discipline report reads `enforced` only under `sandbox-enforced` scope whose write set is the project root, `advisory` otherwise, and the in-project-outside-outbox disclosure appears in every mode (HAP-001-R32, HAP-001-R33, HAP-001-R34).
- **Denied or unavailable destination.** A scope without an asset binding, an unreachable provider, a non-retryable provider refusal, an absent provider credential, and a refused approval each preserve the entry and expose their recovery action; the unreachable provider still allows local publication and registration, and the refusal is shown with the adapter's reason and never retried silently (HAP-001-R6, HAP-001-R22, HAP-001-R28, HAP-001-R30, HAP-001-R37).
- **Restart and retry are idempotent.** The process is killed after `published-local` and before registration, and again after registration and before upload; on restart each publication resumes from its last verified step with exactly one record and one uploaded object, and a repeated publish request for the same bytes acknowledges the existing record — or the state renders explicitly `uncertain`, never a false completion (HAP-001-R23, HAP-001-R29).
- **Device relocation and pending upload.** With an upload pending, the device asset path is changed; the artifact renders `uncertain` on that device until re-verified by digest at the new path, the upload then resumes, and at no point is availability on another device claimed (HAP-001-R25, HAP-001-R27).
- **Containment, handle identity, and integrity.** A candidate entry replaced by a symlink or junction resolving outside the outbox renders `outbox-escape`; a non-regular file — a FIFO, a socket, a device — is refused and renders `outbox-escape` (HAP-001-R15); a hard link to a file outside the outbox renders `outbox-linked` with nothing digested; a path whose target is swapped between digest and copy renders `outbox-escape` with nothing published and the approved bytes present as a recovery entry in the product work area, outside the project, under `publish_mode: copy` and again under a `move`-capable adapter, because the bytes come from the original handle and no path-based rename runs; on a platform without a no-follow open the residual is recorded, never a pass; a published copy altered between digest and verification renders `integrity-mismatch` with the entry preserved; a device asset path reconfigured to resolve inside a registered workspace root renders `destination-invalid` at the next publication; and proposals beyond the D22 cap stay `candidate` and are re-opened under the discipline in turn (HAP-001-R14, HAP-001-R15, HAP-001-R17, HAP-001-R18, HAP-001-R19, HAP-001-R20, HAP-001-R21).
- **Limits.** An entry over the adapter's declared object limit renders `over-limit` and is refused before any byte is copied, with the limit and size shown (HAP-001-R31).
- **Launch environment, run subdirectory, outbox, and product work area.** The child's observed environment contains the declared output key naming a run subdirectory under the project's outbox and no provider credential, its working directory is the project's canonical path, and a planted secret-shaped key never reaches it — extending the slice-3 observed-environment test (spike-log.md § Launch policy ("plus an explicit allowlist")); the run subdirectory is created exclusively with owner-only permissions and verified by handle before spawn, and a link or file pre-planted at its path blocks the launch with `outbox-unavailable`; an invalid outbox declaration blocks the launch; a product work area configured inside a registered workspace root is refused, and a workspace registered mid-session over the work area makes the next journal write refuse with `work-area-invalid` (HAP-001-R5, HAP-001-R7, HAP-001-R8, HAP-001-R9, HAP-001-R10, HAP-001-R37).
- **Untrusted producer.** A publish proposal from a producer whose verdict is `untrusted` never becomes an approval item (HAP-001-R22).
- **Unmediated producer and attribution.** With Omnifrons closed, an external process writes a PDF into the outbox root, a second into an existing run subdirectory, and a third into a tracked path; at the next session the outbox-root entry is proposed as unattributed and registered with `producer: unattributed` and no run id, adapter id, or approval reference; the file in the run subdirectory, named by no proposal from that run, is also unattributed, with the run subdirectory recorded as a location fact only and shown as such at approval; both are validated in place under the single-handle discipline with the outbox as containment root, approved explicitly and never under a standing policy, and removed from the outbox only after publication and registration are verified; the tracked-path file renders `misplaced` and no outbox entry does; a handoff candidate built meanwhile excludes every outbox entry by the product's rule once the exclusion amendment is accepted, and before that preflight discloses which existing rule keeps each entry out and shows in the handoff candidate preview any that would enter; the guidance note offered for the project matches the template with only the path substituted, is labelled advisory, and reaches the guidance file only through an approved write; a synchronized policy naming a raw path or attempting an auto-approval is rejected at load; a symbolic link planted in the outbox is never dereferenced by the inventory; an outbox entry whose path is swapped mid-validation renders `outbox-escape` with its recovery entry in the product work area, outside the project; a declared outbox path that is a link or resolves outside the project renders `outbox-invalid` (HAP-001-R8, HAP-001-R11, HAP-001-R12, HAP-001-R15, HAP-001-R18, HAP-001-R22, HAP-001-R36, HAP-001-R40, HAP-001-R42, HAP-001-R43, HAP-001-R44).
- **Observation only.** `artifact.state` is emitted on every transition with no path in its payload, the bootstrap snapshot carries every publication not yet `provider-synced`, and no event kind moves a byte (HAP-001-R35).
- **Provenance and rendering.** Every record carries the provenance fields its attribution allows and no executable path; a registered artifact renders through the attachment class with its provenance label, and an executable artifact is reveal-only (HAP-001-R36, HAP-001-R38).
- **Deletion and policy.** Deleting a registered artifact writes an MRP-001 tombstone naming the publication identity and nothing else removes it (HAP-001-R39); a synchronized policy naming a raw path or attempting to auto-approve is rejected at load (HAP-001-R40); a planted credential pattern in a candidate entry produces a warning before approval, and the absence of a warning is never displayed as proof (HAP-001-R41).
- **Governance check.** Acceptance findings are recorded per GOV-001 with the self-approval flag where the accountable and approver roles coincide (GOV-001-R3), and the role this contract proposes is exercised by the Project Owner until the assignments register names someone.

Against ADR-0003's own follow-up — conformance tests for catalog state, hydration integrity, eviction safety, offline behavior, and provider failure (adr/0003-local-markdown-and-tiered-assets.md § Acceptance evidence and follow-up ("conformance tests for catalog state")) — this contract discharges the write-side catalog state, offline behavior, and provider failure items. Hydration integrity and eviction safety are read-side and remain undrafted.

Debt, not drafted here:

- The read side — hydration, eviction, and the on-demand locality policy — has no contract of its own yet; this document names its states and stops.
- The current spike adapters declare no output key, so nothing in the repository yet implements HAP-001-R9; the [spike log](spike-log.md) records what exists.
- An earlier revision of this draft declared a harness-facing staging area outside the workspace. It was retired because harness permission models scope writes to the working directory plus declared additional directories and prompt for anything else; the built-in `claude-code` adapter launches with `dontAsk`, under which anything that would prompt is denied (spike-log.md § Slice 3 — first built-in harness adapter → Scope ("--permission-mode dontAsk")); and a `sandbox-enforced` write set is the project — an out-of-workspace location would have been unwritable for a real harness.
- The consequence of that change is carried, not hidden: the outbox sits inside handoff candidates and watcher scope, so HAP-001-R44 and the exclusion amendment to the target architecture's § Initial exclusions and blocks are load-bearing for every mediated run, and until that amendment is accepted the outbox's exclusion from a handoff candidate rests on the user's ignore rule and the binary or oversized block, with the product saying which.
- The per-OS sandbox write set HAP-001-R33 relies on is [VP-001](desktop-stack-verification-plan.md)'s evidence to produce; until VP-S23 runs on a pinned baseline the `enforced` label is unproven on every platform.
- The no-follow open HAP-001-R15 relies on has no Windows equivalent today, so on Windows the substitution window before the open is closed only as far as VP-S27 proves it and is otherwise disclosed under HAP-001-R19 (spike-log.md § Slice 2 — executable identity and approval → What it defers ("TOCTOU window's closure is platform-specific")); which platforms offer a rename or link performed from an open handle, and therefore which adapters may declare a handle-anchored `move`, is VP-S27's evidence as well.
- Cross-project collision safety of the publication identity rests on a non-forgeable project identity this contract consumes from the registered scope and does not itself prove.
- Attribution requires the run's own digest-naming proposal; a manipulated harness that names a file it did not produce still attributes it, bounded by the harness's own integrity and the same-user boundary (TM-001 A2, A6) — this contract records the location fact and discloses the limit rather than claiming proof of authorship (HAP-001-R11).
- The agent guidance note, like every other file in a project's agent guidance, is content the harness reads: it is a prompt-injection surface [TM-001](threat-model.md) owns (threat-model.md § Prompt injection ("Sources: repository files")), and this contract's template lowers friction for a cooperative agent without changing what an injected instruction in the same file could ask a harness to do.
- The provider adapter for the initial Linux backend, and any native-placeholder adapter for Windows or macOS, is undrafted; this contract binds only the capabilities it must declare.
- Open decisions D1 through D22 remain the owner's calls; a feature that assumes a default before the owner disposes must say so rather than presenting the default as decided.
