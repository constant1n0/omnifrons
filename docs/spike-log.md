## Slice 1 — supervisor to renderer streaming

### What it proves

That a demo child process's stdout and stderr can be captured by `omnifrons-supervisor`, framed, and streamed to a Tauri renderer over a typed `tauri::ipc::Channel`, end to end, on Linux, in a development build:

- A process spawned from a validated request (never a raw program path or argument vector) emits captured output frames in order, with a bounded delivery queue that drops under backpressure rather than blocking the producer, and reports the drop count on the next delivered frame.
- A line longer than the per-frame byte cap splits into consecutive frames with no bytes lost; invalid UTF-8 is lossily decoded rather than dropped or erroring.
- A process that ignores `SIGTERM` is still stopped, definitively, by escalating to `SIGKILL` within a bounded deadline.
- Every IPC error surfaces as a closed, typed error code with a fixed catalogue message, never the underlying OS error text (which can carry a real filesystem path).

Both `HarnessKind`s emit a leading `"ready"` stdout line before any `"line <n> out"` output, printed only once a `DemoIgnoresSigterm` process's `SIGTERM`-ignore handler is already installed (`DemoLines` prints it too, for symmetry, even though it installs no handler). A caller can subscribe to the process's output and wait for this line as a genuine synchronization point before calling `stop` against it, closing a handler-install race a fixed sleep could only ever paper over with a guess at "long enough" (`crates/omnifrons-supervisor/src/demo.rs`'s `run`; `crates/omnifrons-supervisor/tests/demo_harness.rs`).

### What it defers

- **Any acceptance claim.** This is a development-mode build on one contributor's Linux machine, not a packaged release build on a pinned baseline. See [Relationship to VP-001](#relationship-to-vp-001).
- **Windows and macOS.** The output-capture reader tasks and the demo harness are platform-generic (Tokio, `std::io`), but the final `State` frame is only ever sent once a reap is confirmed, and `omnifrons-supervisor`'s Windows stop path never confirms a reap yet (`repository-layout.md` § Crate map; pending VP-001 VP-S5, the Job Object policy). Windows output capture therefore never emits a terminal marker today — an inherited gap, not a new one.
- **Windows running-process cap is permanent, not recoverable.** Because Windows `stop` cannot confirm a reap (previous bullet), a stopped process's bookkeeping entry is never evicted from `Running` to `Terminal` there — stated plainly: on Windows, the 16-concurrently-running cap is reached for good once 16 processes have ever been spawned, and `spawn` refuses every one after that for the rest of that supervisor's lifetime, no matter how many of those 16 were actually stopped. This is a real limitation of this slice, not a test artifact — it stands until Job Object containment (VP-001 VP-S5) lands and Windows `stop` can confirm a reap like `unix::stop` does.
- **Any real harness.** `HarnessKind` names exactly two synthetic demo behaviors (`DemoLines`, `DemoIgnoresSigterm`); no user-supplied program, script, or arbitrary executable is reachable through this slice's IPC surface at all.
- **Malformed-payload fuzzing and reconnection/cancellation behavior.** This slice proves the happy path and the two edge cases above; it does not run the adversarial input corpus or renderer-restart scenarios [VP-S13](#procedure-notes-for-vp-s13) and [VP-S15](#procedure-notes-for-vp-s15) call for.
- **Drop-on-supervisor-drop.** If the supervisor itself is dropped without an explicit `stop` (a panicking caller, an early return), its existing best-effort `SIGKILL` cleanup still runs, but no final `State` frame is sent for any process still subscribed at that point — the output channel is simply abandoned. A future slice should decide whether that needs fixing or is an acceptable spike-only limitation.
- **Launcher identity re-probing.** `TokioProcessSupervisor::with_demo_launcher` resolves the launcher path once, via `tauri::process::current_binary`, and caches it for the supervisor's whole lifetime; every `spawn_harness` call execs that cached path with no re-probe of its identity (digest, signature, or modification time) immediately before each launch. [Threat model TM-001, HAR-3](threat-model.md) requires exactly that re-probe for a harness whose executable identity could go stale between launches — "re-probe immediately before launch; material change requires renewed approval and re-binds the identity evidence." This slice's cached-path shortcut is acceptable only because the "harness" it launches is this application's own binary (`--demo-harness`, gated by the non-default `demo-harness` cargo feature), re-exec'd in place — not a third-party executable a supply-chain compromise (TM-001 actor A10) could swap out between launches. A future slice adding a real, user-supplied harness must not carry this shortcut forward; it needs HAR-3's re-probe.

### The IPC contract

Three typed commands, registered next to `shell_health`:

| Command | Params | Returns |
| --- | --- | --- |
| `harness_spawn` | `kind: HarnessKindDto`, `rateHz: number`, `lines: number`, `onFrame: Channel<HarnessFrame>` | `ProcessIdDto` |
| `harness_stop` | `id: ProcessIdDto`, `deadlineMs: number` | `ProcessTerminalStateDto` |
| `harness_observe` | `id: ProcessIdDto` | `ProcessStatusDto` |

No program path or argument vector ever crosses this boundary in either direction: `kind` names one of two closed, synthetic behaviors, and `rateHz`/`lines` are small bounded numbers, validated (`1..=1000`, `1..=100_000`) into an `omnifrons_app::HarnessRequest` before the supervisor ever sees them. The supervisor turns a validated request into a real `ProcessSpec` internally, execing a launcher path fixed once at construction (`tauri::process::current_binary`) — never a path carried by any command argument.

Wire shapes (`src-tauri/src/ipc/dto.rs`, unit-tested field-for-field):

```jsonc
// HarnessKindDto (input only)
"demo-lines" | "demo-ignores-sigterm"

// ProcessIdDto
42

// ProcessTerminalStateDto — code is always present, null unless exited
{"state": "exited", "code": 0}
{"state": "killed", "code": null}
{"state": "orphan-risk/uncertain", "code": null}

// ProcessStatusDto (harness_observe's return)
{"status": "running"}
{"status": "terminal", "state": "killed", "code": null}

// HarnessFrame (harness_spawn's onFrame payload) — adjacently tagged
{"stream": "stdout", "body": {"id": 42, "seq": 3, "droppedBefore": 0, "text": "line 1 out"}}
{"stream": "stderr", "body": {"id": 42, "seq": 41, "droppedBefore": 12, "text": "line 205 err"}}
{"stream": "state",  "body": {"id": 42, "seq": 13, "droppedBefore": 0, "state": "exited", "code": 0}}

// ShellError (every command's error variant)
{"code": "spawn-failed", "message": "failed to start the requested process"}
```

`ShellErrorCode` is closed: `unknown-process`, `spawn-failed`, `already-subscribed`, `invalid-request`, `too-many-processes`. `message` is always one of a small, fixed catalogue of strings — never the underlying `SupervisorError::Spawn`'s `io::Error` text, which can carry a real path. `invalid-request` now also covers `harness_stop`'s `deadlineMs`, validated into `1..=30_000` before it ever reaches the supervisor (an unbounded caller-supplied deadline would otherwise let a single `harness_stop` call occupy its blocking-thread slot indefinitely). `too-many-processes` is returned when a supervisor already tracks its maximum number of concurrently running processes — see the capacity limits below.

Capacity and framing limits (`omnifrons-supervisor/src/output_capture.rs` and `lib.rs`): a per-process delivery channel holds at most **1024** frames (`try_send` only — full means the newest frame is dropped and counted, never that the reader blocks), **except** the final `State` frame, which is guaranteed-delivered via a dedicated blocking-send thread rather than dropped alongside text when the channel is full; a single text frame carries at most **8 KiB** of decoded text (`MAX_LINE_BYTES`), longer lines splitting into consecutive frames at a UTF-8 character boundary, never mid-character; `\r\n` is treated as a line end with the `\r` stripped, and a final line with no trailing newline is still delivered once EOF is reached. A supervisor also caps its own process bookkeeping: at most **16** concurrently running processes (`spawn`/`spawn_harness` refuse a 17th with `SupervisorError::TooManyProcesses`, mapped to `ShellErrorCode::TooManyProcesses`, without ever spawning it) and at most **256** retained terminal entries, oldest evicted first by termination order — an evicted id then reports `unknown-process`/`None` from a later `stop`/`observe`, never a re-signal of a pid the OS may have since recycled. An output-capture entry is removed once both finalized and subscribed-out (its receiver already taken via `subscribe`); an entry nobody ever subscribes to is retained indefinitely instead.

### Procedure notes for VP-S13

[VP-001 VP-S13](desktop-stack-verification-plan.md#scenario-catalog) ("IPC boundary: typed commands only; path attacks rejected") will eventually need this slice's commands exercised with a malformed-payload corpus. Candidate cases, once a packaged build exists to run them against:

- Raw filesystem paths (absolute, relative, UNC, `file://`) submitted as `kind`, where only the two closed string tokens are accepted.
- Path-traversal strings (`../../etc/passwd`, symlink targets) submitted the same way.
- Wrong JSON types for every field (`rateHz` as a string, a float, or an array; `id` as a string or negative number).
- Oversized numbers: `rateHz`/`lines` beyond `u16`/`u32` range, `id` beyond `u32` range, and boundary values just inside/outside the validated ranges (`0`, `1`, `1000`, `1001`, `100_000`, `100_001` for `rateHz`/`lines`; `0`, `1`, `30_000`, `30_001` for `harness_stop`'s `deadlineMs`).
- Extra, unexpected JSON keys alongside the accepted ones for every command (e.g. `{"kind": "demo-lines", "rateHz": 10, "lines": 10, "onFrame": ..., "path": "/etc/passwd"}`). Tauri's own per-parameter command binding (each `#[tauri::command]` argument bound by name from the invoke payload) *ignores* keys it has no matching parameter for, rather than rejecting the payload outright — confirmed against this slice's own commands, which declare no catch-all parameter. The corpus therefore cannot assert rejection for this case; it must instead assert that an extra key has *no effect whatsoever* (the command behaves identically with or without it present), since silent tolerance of an unrecognized key is not itself a path or argument reaching `omnifrons-supervisor`. Whether a future slice should close this permissiveness outright — an `AppManifest`-generated strict schema, or a wrapper request struct deriving `#[serde(deny_unknown_fields)]` for each command's arguments — is an open decision this slice does not make.

Expected outcome per [target architecture, invariant 4](target-architecture.md#proposed-invariants) and [RCS-001-R14](renderer-content-security.md): rejection with a typed `ShellError`, never a best-effort coercion, and never a path or argument reaching `omnifrons-supervisor`'s `spawn` — except the extra-JSON-keys case above, whose expected outcome is no-effect tolerance, not rejection.

### Procedure notes for VP-S15

[VP-001 VP-S15](desktop-stack-verification-plan.md#scenario-catalog) ("Structured streams, bounded backpressure, reconnection, malformed events, cancellation") is this slice's closest analogue among VP-001's scenarios. Candidate procedure, once a packaged build exists:

- Drive `harness_spawn` at the top of its accepted range (`rateHz = 1000`, `lines = 100_000`) against a renderer that does not drain `onFrame`, and confirm: `harness_spawn` and `harness_stop` still return promptly; the delivered frame count stays near the 1024-frame channel capacity, not the full line count; at least one delivered frame's `droppedBefore` is nonzero once the renderer resumes draining (`crates/omnifrons-supervisor/tests/output_backpressure.rs` is this slice's dev-mode analogue).
- Kill and restart the renderer mid-run; confirm `harness_observe` still reports the harness's true status and a fresh `harness_spawn` subscription is possible for a *new* process (this slice's `subscribe` is one-shot per process id, not reconnect-capable for an existing subscription — a gap this scenario should surface explicitly, not paper over).
- Inject malformed `HarnessFrame`-shaped events at the transport layer (not achievable through this slice's own commands, which only ever emit well-formed frames) to confirm the renderer's own parsing rejects them rather than crashing.
- Cancel mid-run via `harness_stop` with a short `deadlineMs` against a `DemoIgnoresSigterm` process, confirming escalation to `SIGKILL` and a definite terminal state within the deadline (`crates/omnifrons-supervisor/tests/demo_harness.rs` is this slice's dev-mode analogue).

### Renderer

The renderer half of this slice: a typed IPC client plus a minimal control panel driving it, all under `renderer/src/`.

- `ipc/harness.ts` — the *only* renderer module that imports `@tauri-apps/api/core`. Exports types mirroring `src-tauri/src/ipc/dto.rs` field-for-field (`HarnessKind`, `ProcessId`, `ProcessTerminalState`, `ProcessStatus`, `HarnessFrame`, `ShellError`), plus `harnessSpawn(request, onFrame)` (constructs a `Channel<HarnessFrame>`, wires its `onmessage` to `onFrame`, and invokes `harness_spawn` with exactly `{ kind, rateHz, lines, onFrame }`), `harnessStop(id, deadlineMs)`, `harnessObserve(id)`, and the `isShellError` type guard.
- `controlCharacters.ts` — `stripControlCharacters`, kept out of `PlainTextLine.tsx` so that component file only exports a component (the project's `react-refresh/only-export-components` lint rule).
- `PlainTextLine.tsx` — renders one line of untrusted text as plain text: strips C0 control characters (U+0000-U+001F except tab), DEL (U+007F), C1 control characters (U+0080-U+009F), and the bidirectional/format controls U+200B-U+200D (zero-width space/non-joiner/joiner), U+200E/U+200F (LRM/RLM), U+202A-U+202E (explicit bidi embeddings/overrides), and U+2066-U+2069 (explicit bidi isolates) — treated as format controls, not text, per RCS-001-R18, the same distinction RCS-001 already draws for OSC 0/2 titles and OSC 9 notifications ("control and bidirectional-override characters stripped"). Stripping U+200C/U+200D is a deliberate trade-off against scripts (Arabic, Indic) that rely on ZWJ/ZWNJ for correct shaping (`controlCharacters.ts`'s doc comment weighs the cost). Keeps every other character, no markup, no links, no OSC interpretation (RCS-001-R1, RCS-001-R18). `UntrustedText.tsx` is untouched.
- `HarnessPanel.tsx` — kind select (`demo-lines`/`demo-ignores-sigterm`), rate/lines number inputs validated client-side with `Number.parseInt` against the same bounds `omnifrons_app::harness_catalog` enforces (`1..=1000` Hz, `1..=100_000` lines; advisory only here, the Rust catalog is the sole authority and validates again regardless), disabling Start and showing an inline message for an empty, non-numeric, negative, or out-of-range value. Start/Stop buttons — Start additionally disabled while a spawn is pending or a harness is already active, since this slice allows only one active harness per panel; Stop disabled once no harness is active, including right after a successful stop resets it. A state badge renders the wire token verbatim (`running`, `exited (code N)` or `exited (code unreported)` when the platform reported no code, `killed`, `orphan-risk/uncertain` — never `done`, per target-architecture.md invariant 8). An output log renders every frame through `PlainTextLine` prefixed by its stream name, capped at the most recent 2000 entries with a `<mark>` marker ("showing the last 2000 lines; N earlier lines are not shown", N cumulative) once older entries are trimmed, plus a `<mark>` row ("N frames dropped before this line") whenever a frame's `droppedBefore` is nonzero. An error banner renders a `ShellError`'s `code` and `message` as plain text through `PlainTextLine` — or the fixed string "unexpected error", with no message text, for any rejection that isn't `ShellError`-shaped. A mount effect reads every process id remembered in `sessionStorage` (one key, `JSON.parse`/`JSON.stringify`, wrapped in try/catch) and calls `harnessObserve` for each: a still-`running` id shows "stream reconnected; earlier output not replayed"; a terminal status, an `unknown-process` rejection (a stale id, forgotten silently, no banner), or a completed `harness_stop` all prune the id from `sessionStorage`; any other rejected `ShellError` shows the banner once and also prunes the id, since it cannot be reconnected to either way. A `mountedRef` set false in that effect's cleanup guards both its promise handlers and the frame callback, so neither does anything once the component has unmounted. Mounted from `App.tsx` below the existing content.

Tests (Vitest + `jsdom`, `@testing-library/react`, `@tauri-apps/api/mocks`' `mockIPC`/`clearMocks`), all green:

- `ipc/harness.test.ts` (8 tests): `harness_spawn` is invoked with exactly the keys `kind`, `rateHz`, `lines`, `onFrame` and no path-shaped key; a frame sent on the live `Channel` reaches the `onFrame` callback; a rejected `harness_spawn` propagates its `ShellError` payload; `harness_stop`/`harness_observe` pass `id`/`deadlineMs` correctly and return the mocked shape verbatim (including `orphan-risk/uncertain`); `isShellError`'s positive and negative cases.
- `PlainTextLine.test.tsx` (11 tests): every C0 control character except tab is stripped, DEL is stripped, C1 control characters are stripped, the bidi marks/embeddings/isolates and the zero-width space/non-joiner/joiner are each stripped, tab is kept, non-ASCII is kept, and rendered markup stays literal (no `<b>` element, text visible).
- `HarnessPanel.test.tsx` (25 tests): initial render (kind options, input bounds, controls present); Rate/Lines validation (empty, negative, non-numeric, above-max all disable Start and show an inline message; correcting a value re-enables it); literal `<b>` frame rendering; the OSC 8 test (below, exact-equality); the dropped-frames `<mark>` text; the log-cap `<mark>` marker across 2500 pushed frames; the badge reading `killed` (with the exact `harness_stop` args asserted) and resetting `activeId`/disabling Stop once it resolves; `exited (code N)` and `exited (code unreported)`; `orphan-risk/uncertain` verbatim from a mocked `state` frame (asserting `done` never appears); the `spawn-failed` error banner with no `/` in its message, control characters stripped from a banner's code/message, and the generic "unexpected error" banner for a non-`ShellError` rejection; a second click not spawning twice while Start is disabled; a mount-time reconnection marker for a `running` remembered id, pruning on a terminal status, silent forgetting on `unknown-process`, the banner-once-and-prune path for another `ShellError`, and the mounted-guard test proving the mount effect no-ops (no `sessionStorage` write) once unmounted.

**What the OSC 8 test proves, and does not prove.** The panel is fed one `stdout` line containing a full OSC 8 hyperlink sequence — `ESC ]8;;https://example.invalid BEL label ESC ]8;; BEL` — and the test asserts the rendered output contains no `<a>` element and that the visible text is exactly the input with its ESC (`0x1B`) and BEL (`0x07`) bytes removed: `]8;;https://example.invalidlabel]8;;`. Every other byte, including the OSC marker's own punctuation (`]8;;`) and the URL text, survives literally, because `PlainTextLine` strips individual C0/DEL code points and never recognizes or interprets a sequence. This proves the stripping is per-byte and blind to OSC structure (so a malformed or partial escape sequence cannot smuggle a link past it) and that RCS-001-R18 ("sanitization must not remove textual content") holds on this path. It does **not** prove anything about a terminal content class or an OSC policy: this slice has no terminal pane, no confined terminal frame, and no OSC allowlist (renderer-content-security.md § Content classes and rendering modes defines that class; nothing here implements it). The harness output this slice renders is plain text — the default every content source with no declared class gets — never PTY output.

**Mocking `Channel` in `mockIPC`.** `@tauri-apps/api/mocks`' `mockIPC(cb)` replaces `window.__TAURI_INTERNALS__.invoke`; the real `invoke()` in `@tauri-apps/api/core` calls that function with its `args` object passed straight through, with no JSON serialization at that layer (serialization to the wire happens deeper, inside the real bridge `mockIPC` replaces). Confirmed against the installed package's own source (`@tauri-apps/api@2.11.1`'s `core.js` and `mocks.js`): the mock handler's `args.onFrame` is therefore the exact live `Channel` instance `harnessSpawn` constructed, not a serialized placeholder. Calling `args.onFrame.onmessage(frame)` from inside the mock handler is the approach that worked; no `Channel` mock or module-level hook was needed. Separately, jsdom has no WebCrypto implementation, and the mock's channel-id registry needs `window.crypto.getRandomValues` to mint callback ids for every `Channel` a test constructs; `testSupport/installJsdomCrypto.ts` installs a minimal, non-cryptographic fill for it (Tauri's own docs demonstrate this with Node's `crypto.randomFillSync`, but that does not type-check under `tsconfig.app.json`, which excludes Node's ambient types, so the fill here uses no Node built-in). Both this polyfill and React Testing Library's `cleanup()` after every test are installed once, centrally, by `testSupport/setup.ts` (`vite.config.ts`'s `test.setupFiles`), rather than each test file repeating its own `beforeAll`/manual `cleanup()` call. `vite.config.ts` also sets `test.allowOnly` explicitly to `!process.env.CI` (Vitest's own default, made explicit so a stray `.only` reads as a deliberate, reviewable choice rather than an accident that happens to also be caught in CI).

**Strict TypeScript.** `tsconfig.app.json` and `tsconfig.node.json` both set `"strict": true`; the renderer code (including every test file, since `tsconfig.app.json` includes `src`) already type-checked clean under it with no changes needed.

## Slice 2 — executable identity and approval

### What it proves

That a caller-supplied executable's identity can be probed, approved once, re-verified immediately before every later launch, and launched with no arguments — on Linux, in a development build:

- Identity is content, path, and size, never a timestamp: `ExecutableIdentity`'s equality (`crates/omnifrons-domain/src/executable.rs`) compares canonical path, size, and SHA-256 digest only, deliberately excluding `modified_at` and platform evidence — informational fields a re-probe can observe differently between two calls with no actual content change.
- `LaunchGate::decide` (`crates/omnifrons-app/src/launch_gate.rs`) never trusts a cached identity: it re-probes the recorded canonical path fresh on every call (a spy prober counts exactly one probe per `decide` call, never zero, never cached) and checks, in order, canonical path (`ShadowedPath` if the re-probe resolves elsewhere), digest/size (`ChangedSinceApproval`, carrying both digests), and status (`Revoked`) — matching [TM-001 HAR-3](threat-model.md)'s requirement to "re-probe immediately before launch". An approval store that cannot even be read denies fail-closed as `Unapproved` rather than risking a false allow.
- Revocation is honest and re-approvable: a revoked approval's id can never launch again, but the same identity can be approved again under a fresh id — `JsonlApprovalStore` (`crates/omnifrons-adapters/src/jsonl_approval_store.rs`) records this as an append-only log (mode `0o600` on unix; a revocation is a new line referencing the earlier approval id, never an edit of it), so the file's own growth is the evidence a revocation actually happened, and a truncated or malformed line fails the whole read as `Corrupt` rather than silently dropping it.
- `FsExecutableProber` (`crates/omnifrons-adapters/src/fs_prober.rs`) canonicalizes, then opens the canonical path *exactly once* (unix: `O_NOFOLLOW`, refusing a symlink placed at that exact path after canonicalization), and confirms *that one open file*'s own `fstat` is a regular, executable file within a 512 MiB cap before ever reading its content, then stream-hashes it in 64 KiB chunks from the same handle. A non-executable file is proven never hashed at all (a several-hundred-megabyte sparse fixture still probes as `NotExecutable` within a tight time budget, never actually reading that much content).
- On Linux, `FsExecutableProber` hashes *while copying* the candidate's bytes into a fresh, sealed `memfd` (`MFD_CLOEXEC | MFD_ALLOW_SEALING`, then `F_SEAL_SHRINK | F_SEAL_GROW | F_SEAL_WRITE | F_SEAL_SEAL`): the returned handle's content is provably exactly the bytes that were hashed, immutable from that point on, including against this process itself (`crates/omnifrons-adapters/tests/fs_prober.rs` proves the sealed length, digest, and a rejected write with `EPERM`). `TokioProcessSupervisor::spawn_approved` (`crates/omnifrons-supervisor/src/lib.rs`) then execs that sealed `memfd` directly via `/proc/self/fd/<n>`, with `stdin` always `/dev/null` — never the executable's own bytes — so a file replaced or overwritten at the display path after the seal was applied still executes the sealed content, proven directly (`crates/omnifrons-supervisor/tests/approved_launch.rs`) against a `#!/bin/sh` fixture whose display-path content is both replaced and overwritten in place after sealing, and against a fixture that reads its own `stdin` and observes only immediate `EOF`.
- The demo harness path is unaffected: `spawn_approved` launches with no arguments at all, never the `<kind> <rate_hz> <lines>` argv shape `spawn_harness` uses, and the shell's `harness_spawn` command dispatches to one or the other based on which tagged `kind` the caller sent. The demo launcher binary itself is explicitly exempt from the approval gate this slice: it is the app's own binary, whose identity the eventual UTA-001 platform signing will cover, not a caller-supplied executable this gate's threat model is about — a self-approval bootstrap for the app's own binary is deferred, not implemented here.

### What it defers

- **Any acceptance claim**, for the same reason as slice 1: this is a `dev-mode-only` result on one contributor's Linux machine. See [Relationship to VP-001](#relationship-to-vp-001-1) below.
- **Approval expiry.** An `ApprovalRecord` is `Active` until explicitly revoked; nothing ages it out on its own. [VP-S14](desktop-stack-verification-plan.md#scenario-catalog)'s own procedure notes below flag this as a real gap the eventual scenario should probably probe.
- **Store integrity beyond append-only structure.** `approvals.jsonl`'s `0o600` mode and JSONL-append discipline make *accidental* corruption or a naive rewrite detectable (a truncated line, or one carrying an unsupported `schema` value, fails closed as `Corrupt`), but nothing here is cryptographically signed or tamper-evident against a deliberate, well-formed edit by anyone with write access to the file (the device-local user this store's own trust model already assumes has that access, per `DeviceLocalUser`'s (`crates/omnifrons-domain/src/executable.rs`) own "opaque marker for whoever is using this device" framing — but a *different* local principal, or a later compromise of that account, could rewrite history undetected). Store signing is a real, named gap, not an oversight.
- **No single-instance guard on `JsonlApprovalStore`.** `ApprovalId` is now derived (`sha256(domain ++ canonical_path ++ sha256 digest ++ approved_at nanoseconds)`, first 8 bytes) rather than counted, and `record` rejects a derived id already on file (`ApprovalStoreError::Duplicate`) — this removes the specific "two concurrent `max() + 1` reads collide" race, but nothing here prevents two separate process instances (or two threads racing within one) from concurrently appending against the same file at all; a real single-instance guard (a lock file, an advisory `flock`) is deferred, not implemented.
- **Windows executable detection is provisional by extension allowlist alone** (`exe`/`com`/`bat`/`cmd`, `FsExecutableProber::is_windows_executable_extension`), never a real ACL or Authenticode signature check — `FsExecutableProber`'s own doc comment says so. Untested end-to-end in this spike (no Windows machine available; the extension check itself is unit-tested cross-platform, and a `#[cfg(windows)]` prober test exists but has not run on real Windows); a real Windows executability decision needs its own verification work.
- **No Windows equivalent of the Linux `O_NOFOLLOW` protection or memfd sealing.** `open_checked` (`crates/omnifrons-adapters/src/fs_prober.rs`) refuses a symlink placed at the canonical path after canonicalization on unix via `O_NOFOLLOW`; `std`'s `OpenOptionsExt` exposes no equivalent flag on Windows, so a symlink or reparse point swapped into that same narrow window would still be followed there. Windows also has no sealed-memfd equivalent, so every Windows probe returns `ExecHandle::File`, with only inode identity during hashing guaranteed and the hash-to-exec window fully open (see the TOCTOU bullet below). Both are documented, real gaps, not oversights.
- **No platform code-signing or publisher-identity verification anywhere in this slice.** "Approval" here means "a human clicked approve for this exact byte content once"; it says nothing about who published that content. This is a strictly narrower claim than a real code-signing check would make, and does not by itself close [TM-001 A10](threat-model.md) (a compromised distribution channel) beyond forcing re-approval on the next material change (HAR-3's own stated limit: "harness/adapter supply-chain integrity itself is outside TM-001's mitigation reach beyond re-approval").
- **The TOCTOU window's closure is platform-specific, stated exactly, not glossed over: Linux executes precisely the hashed bytes (sealed memfd); macOS/Windows: path spawn, in-place modification and substitution between hash and exec are not prevented.** On Linux, `FsExecutableProber` opens the canonical path exactly once (`O_NOFOLLOW`) and hashes while sealing the content into an immutable `memfd` (`ExecHandle::SealedMemory`); `spawn_approved` execs that sealed `memfd` itself via `/proc/self/fd/<n>`, so what actually runs is, by construction, exactly what was hashed — not a re-read of the display path, which may by then be replaced, overwritten, or retargeted. This still does not close every window: a symlink retargeted between `decide()`'s `canonicalize` and its one `open()` call is a race `open_checked`'s `O_NOFOLLOW` refuses only when it lands *at* the already-canonicalized path, and it proves nothing about a swap happening before that canonicalize step at all. On macOS and Windows (or a Linux probe that falls back to `ExecHandle::File`), `spawn_approved` spawns by the display path directly, with no such guarantee: only the *inode identity* observed while hashing holds, and in-place modification or a path retarget between hash and exec is not prevented there, exactly as `docs/target-architecture.md`'s honesty requirements demand recording rather than glossing over.
- **Malformed-payload fuzzing for the four new commands** (`executable_pick_and_probe`, `executable_approve`, `executable_revoke`, `approvals_list`) and the extended `harness_spawn` tagged `kind`. This slice proves the happy paths and the specific denial/TOCTOU cases above; VP-S13's adversarial corpus (slice 1's own procedure notes) has not been re-run against this larger command surface.
- **The renderer's `approved`-kind approval select does not live-refresh across components.** `HarnessPanel` and `ApprovalSurface` each hold their own independent `approvalsList()` fetch (no shared state, no context) — approving a new executable in `ApprovalSurface` does not update `HarnessPanel`'s own approval select until the `Kind` field is re-selected back to `approved` (re-triggering that panel's own fetch) or the page is remounted. A future slice should decide whether this needs a shared store or is an acceptable spike-only seam.
- **TM-001-R7's "act-as identity" clause has no distinct value to display in this narrow slice.** `ApprovalSurface` fully implements R7's identity-evidence display (canonical path, size, both digests, modification time, platform evidence), but this slice's one launch action is always "run this exact executable, with no arguments, as the current device-local user" — there is no separate actor identity a real multi-identity harness invocation would need to distinguish. Recorded here as an honest scope limit, not an omission.
- **The `changed-since-approval` handling in `ApprovalSurface` is defensive, not exercised by any wired backend path in this slice.** `executable_approve`/`executable_pick_and_probe`/`executable_revoke`/`approvals_list` never actually return this code today — only `harness_spawn`'s `LaunchGate::decide` path does, and that failure surfaces in `HarnessPanel`'s banner, not `ApprovalSurface`'s. `ApprovalSurface` still implements the required digest-comparison-plus-Renew UI generically, for whichever surface a future slice wires this code into, and its own tests exercise it via a mocked rejection rather than a real cross-component trigger.

### The IPC contract additions

Four new typed commands, registered next to `shell_health`/`harness_spawn`/`harness_stop`/`harness_observe`:

| Command | Params | Returns |
| --- | --- | --- |
| `executable_pick_and_probe` | *(none)* | `ProbeResultDto` |
| `executable_approve` | `candidateId: number` | `ApprovalDto` |
| `executable_revoke` | `approvalId: number` | `null` |
| `approvals_list` | *(none)* | `ApprovalDto[]` |

`executable_pick_and_probe` opens the native OS file picker (`tauri-plugin-dialog`'s `blocking_pick_file`, called only from a `spawn_blocking` task — calling it from the async executor's own thread would deadlock, per the plugin's own documented warning) and probes whatever the user selected. The raw path the user picked is **never** returned; `evidence.canonicalPath` — the *resolved*, symlink-followed path — is the one place a filesystem path reaches the renderer in this whole surface, deliberately, for [TM-001-R7](threat-model.md) display. A successful probe is remembered server-side under a fresh `candidateId`, in a bounded (32-entry, oldest-evicted) table scoped to this shell process's own lifetime — never persisted, never stable across a restart.

Wire shapes (`src-tauri/src/ipc/dto.rs`, unit-tested field-for-field):

```jsonc
// harness_spawn's kind parameter is now internally tagged, bundling each
// variant's own parameters, rather than a flat kind + optional
// rateHz/lines/approvalId set (deliberately: a flat shape would let a
// caller submit a meaningless combination, e.g. "approved" with a
// rateHz, that would then need extra validation to reject after the fact).
{"type": "demo-lines", "rateHz": 10, "lines": 100}
{"type": "demo-ignores-sigterm", "rateHz": 10, "lines": 100}
{"type": "approved", "approvalId": 42}

// ProbeResultDto (executable_pick_and_probe's success payload)
{
  "candidateId": 7,
  "evidence": {
    "canonicalPath": "/opt/tool/app",
    "size": 4096,
    "sha256": "<64 lowercase hex chars>",
    "sha256Short": "<first 8 of those hex chars>",
    "modifiedAt": 1732000000000,   // ms since epoch, or null
    "platform": {"os": "unix", "mode": 493}
    // or: {"os": "windows", "extension": "exe", "attributes": 32}
  }
}

// ApprovalDto (executable_approve's and approvals_list's payload)
{
  "approvalId": 42,
  "evidence": { /* same EvidenceDto shape as above */ },
  "approvedAt": 1732000000000,
  "status": "active",       // or "revoked"
  "revokedAt": null         // ms since epoch once status is "revoked"
}

// ShellError, extended with an optional structured `detail` (present only
// for changed-since-approval today; omitted entirely otherwise, never a
// literal `null`)
{
  "code": "changed-since-approval",
  "message": "the executable's content has changed since it was approved",
  "detail": {"recordedSha256Short": "aaaaaaaa", "observedSha256Short": "bbbbbbbb"}
}
```

`ShellErrorCode` gains nine variants this slice: `no-candidate` (an unknown `candidateId`/`approvalId`, or the file dialog returned nothing), `not-executable` (the re-probed target is not a regular, executable file — folding `ProbeOutcome::NotRegularFile` and `NotExecutable` together, since neither is actionable differently by a caller), `probe-failed` (the target could not be read at all), `too-large` (over the size cap), `unapproved`, `changed-since-approval`, `shadowed-path`, `revoked`, and `approval-store-unavailable` (the store itself could not be read or written — the closed `ApprovalStoreError` reasons, four as of the review-fix pass's added `Duplicate`, collapse to this one code for the same "not actionable differently" reasoning). Every message stays a fixed catalogue string with no `/`, matching slice 1's own no-path-leak discipline; only `changed-since-approval`'s `detail` ever carries digest material, and only as 8-character short-hex prefixes, never a full digest or a path.

The default capability (`src-tauri/capabilities/default.json`) stays `core:default` and nothing else — `tests/config.rs`'s `default_capability_grants_only_core_default` test is unchanged and still passes. This is not an oversight: `tauri_plugin_dialog::DialogExt::dialog()` is a direct Rust method call from inside `executable_pick_and_probe`'s own command body, never an IPC invocation of `plugin:dialog|open` from the webview — capability/ACL enforcement in Tauri 2 gates *IPC-invoked* plugin commands crossing the webview boundary, not a Rust-side call one of the shell's own commands happens to make into a plugin crate's API. Confirmed against `tauri-plugin-dialog@2.7.3`'s and Tauri's own documentation before relying on it, not assumed.

### Procedure notes for VP-S14

[VP-001 VP-S14](desktop-stack-verification-plan.md#scenario-catalog) ("Executable identity, re-probe, shadowed-path resistance") is this slice's direct analogue. Candidate procedure, once a packaged build exists:

- Approve an executable, then replace its content in place (same path, new bytes) before relaunch: expect `changed-since-approval`, with both recorded and observed short digests present and distinct (`crates/omnifrons-app/tests/launch_gate.rs`'s `rewritten_file_is_denied_with_both_digests` is this slice's dev-mode analogue).
- Approve an executable, then retarget the path to a different file (a symlink swap, or a same-named replacement one directory level up) before relaunch: expect `shadowed-path`, with both the approved and resolved canonical paths present (`shadowed_path_is_denied_with_both_paths` is the analogue).
- Revoke an approval and attempt to relaunch it: expect `revoked`; then re-approve the same executable and confirm the *new* approval id launches while the old one stays permanently denied (`revoked_approval_is_denied`, `re_approval_after_revoke_is_allowed`).
- On Linux specifically: replace the approved file's content in the narrow window between the shell's `LaunchGate::decide` call and the actual launch, and confirm the *original*, already-vetted content still executes rather than the replacement — this is a *positive* assertion (the narrowed window held), distinct from every other case above (which assert a *denial*) — `crates/omnifrons-supervisor/tests/approved_launch.rs` is the dev-mode analogue; the real scenario should also attempt to defeat this window (e.g. a tighter race, or a symlink swap instead of an unlink-and-recreate) and confirm whether it still holds under real timing pressure, not just this test's own generous ordering.
- Confirm no approval ever silently expires: leave an approval untouched for whatever the longest realistic gap between launches is, and confirm it still launches — this is the flip side of "expiry" being a deferred concern above, and the scenario should decide whether that absence is acceptable or a gap to close before VP-001 can rely on it.
- Attempt the same shadowed-path/rewritten-content attacks on macOS and Windows and confirm the *documented* outcome — a denial when the gate's own re-probe catches it (since `decide`'s comparison logic is platform-generic), but with the residual TOCTOU window from decide to launch left open there, never narrowed the way Linux's fd-exec path narrows it. The scenario's expected outcome on those two platforms is therefore "a race is theoretically possible, not eliminated" rather than the stronger claim available on Linux — recording that difference plainly, not silently normalizing it away.

Expected outcome per [TM-001 HAR-3/HAR-4](threat-model.md): "material change requires renewed approval and re-binds the identity evidence" and "canonical path resolution before authorization" — both properties this slice's `LaunchGate::decide` implements and its own tests exercise, with the platform caveats recorded above.

Four new typed wrappers: `executablePickAndProbe()`, `executableApprove(candidateId)`, `executableRevoke(approvalId)` (discards `invoke`'s resolved value, always resolving `void`), `approvalsList()`.

## Slice 3 — first built-in harness adapter

This slice's Rust half (`omnifrons-domain`, `omnifrons-app`, `omnifrons-adapters`, `omnifrons-supervisor`, `src-tauri`) implements the first built-in harness adapter, described below; the renderer half — `AgentPanel`, the first surface that actually renders an adapter's structured event stream — is described separately in [Renderer](#renderer-2) (`pnpm -r test` grows from **94** to **169**).

### Scope

A closed, built-in `AdapterCatalog` (two entries: `stream-json-cli`, a generic parser over a `stream-json`-shaped CLI with no fixed flags of its own, and `claude-code`, the same parser with a fixed `-p --output-format stream-json --verbose --permission-mode dontAsk` argv template) stands alongside the existing demo-harness and approved-executable launch paths, never replacing either. Launching an adapter now requires three things a caller must supply explicitly, none of them a free-form program path or argument vector: a previously approved executable identity (the existing `LaunchGate`, unchanged), a picked workspace directory (`workspace_pick`, a native folder dialog, canonicalized into a `WorkspaceRoot`), and a size-capped agent prompt (`AgentPrompt::new`, 16 KiB UTF-8, no interior NUL).

### Launch policy

`HarnessAdapter::build_launch` (`crates/omnifrons-app/src/harness_adapter.rs`) turns a validated `LaunchRequest { prompt, workspace }` into a `LaunchPlan` under a fixed, small set of rules an adapter cannot widen at request time:

- **argv is always exactly the adapter's own `argv_template`.** Neither the prompt nor any other request-supplied text is ever appended, matching `docs/spike-log.md`'s own IPC-contract discipline extended to adapters (`crates/omnifrons-adapters/tests/line_agent_launch.rs`).
- **The prompt is delivered only over stdin, then the write end is closed** (`StdinPlan::PipePromptThenClose`), never through argv. `TokioProcessSupervisor::finish_spawn` (`crates/omnifrons-supervisor/src/lib.rs`) writes the prompt's bytes on its own runtime (never the calling thread) and drops the writer, signalling EOF, regardless of whether the child ever reads it — a write failure is reported as a synthetic `stderr` text frame (`"stdin write failed"`, `output_capture::emit_stdin_write_failed`) rather than silently swallowed or left to hang; this is a deliberate choice over inventing a new cross-layer "state observation" concept the raw `OutputFrame`/`FramePayload` vocabulary has no room for (see [Deviations](#deviations-from-the-brief) below).
- **The environment is `env_clear()` plus an explicit allowlist, resolved from the supervisor's own process environment at spawn time, never a value captured earlier.** `EnvPlan::new` (`crates/omnifrons-app/src/harness_adapter.rs`) merges a fixed base set — `PATH`, `LANG`, `LC_ALL`, `TMPDIR` always, plus `HOME` (unix) or `USERPROFILE`/`SystemRoot`/`SystemDrive`/`TEMP`/`TMP` (windows) — with an adapter's own `declared_env` keys, and refuses outright (`LaunchPlanError::SecretShapedEnvKey`) any key matching `*_TOKEN`/`*_SECRET`/`*_KEY`/`*_PASSWORD`/`ANTHROPIC_API_KEY`/`AWS_*`/`GH_TOKEN`/`GITHUB_TOKEN` case-insensitively, even when an adapter explicitly declares it. `TokioProcessSupervisor::finish_spawn` re-validates every allowlisted key against the same rule immediately before calling `Command::env` — a single choke point that never trusts a `LaunchPlan` (or a hand-built `ProcessSpec`, in a future caller) blindly (`crates/omnifrons-supervisor/tests/adapter_launch.rs`'s `observed_env_equals_the_allowlist_excluding_a_planted_secret_shaped_key`, which re-execs its own test binary filtered to exactly that one test with a dummy `FAKE_SECRET_TOKEN` planted in that child's environment through `Command::env` — never `std::env::set_var` in the test process itself, which is `unsafe` and races every concurrent environment reader (R1-005/R3-001, fixed in review) — and confirms, in that inner run, that the planted key never reaches the launched child even though it was never declared and is secret-shaped by name; the `cfg!(windows)` arm of its expected allowlist executes on CI's `windows-latest` matrix leg, where `cargo test --workspace --all-targets --all-features` runs, not only as a cross-compiled type-check).
- **The working directory is always the picked workspace's own canonical path.** `validate_cwd_within_workspace` (`crates/omnifrons-app/src/harness_adapter.rs`) canonicalizes a candidate cwd and confirms it equals the workspace's own canonical form, rejecting a `..` escape, an absolute path elsewhere, or a symlink whose target resolves outside (`crates/omnifrons-app/tests/launch_plan_cwd.rs`) — `LineAgent::build_launch` always calls this with the workspace's own path as the candidate, so it is a guard for a future caller with a genuinely different candidate, not something this slice's own wiring can ever actually deny.
- **Scope stays `advisory`.** Every built-in adapter's `scope_mode` is `ScopeMode::Advisory`; nothing in this slice claims sandbox or harness enforcement (`docs/target-architecture.md` § Proposed invariants, item 5).

`spawn_approved` (`crates/omnifrons-supervisor/src/lib.rs`) gained a third parameter, `plan: &LaunchPlan`, applying `plan.argv`/`plan.env`/`plan.cwd`/`plan.stdin` uniformly for every caller, including the pre-existing `kind: "approved"` launch path from slice 2. To keep slice 2's own shipped behavior unchanged there, `harness_spawn`'s `"approved"` case now builds its own default plan (`commands::default_approved_plan`) with empty argv, the same `env_clear()`-plus-base-allowlist environment an adapter launch with no declared extras gets (`EnvPlan::new(&[])` — an earlier revision of this slice used `EnvPlan::Inherit` here, arguing that an approved executable makes no declared-env claim; review (R1-001) rejected that: an approved executable is a caller-supplied program exactly like an adapter's target, and the shell's own environment can carry credentials no launch should inherit by default — fixed in review, asserted structurally by `src-tauri`'s `default_approved_plan_uses_the_base_allowlist_never_inherit`), the shell's own current directory as cwd, and `StdinPlan::Null`. Both kinds pass through `finish_spawn`'s single secret-shaped re-check; the `ExecHandle::File` branch's null stdin is now proven on every platform, not only Linux's sealed-memfd branch (`fake-agent --stdin-byte-count` observes zero bytes, `crates/omnifrons-supervisor/tests/approved_launch.rs`'s `file_branch_with_stdin_null_gives_the_child_an_empty_stdin_on_every_platform`; R3-007). `StdinPlan::Null` is the one behavior this slice actually tightens for `"approved"`, closing a pre-existing gap: `spawn_approved`'s own doc comment already claimed stdin was always `/dev/null`, but the `ExecHandle::File` branch never actually configured it before this slice — it now does, uniformly, for every launch this method ever performs.

### Event contract

`omnifrons_domain::adapter::AdapterEvent` is the closed set an adapter's `parse_line` (total and never empty: never panics, and every unparsable input yields exactly one `Unknown` — tested over a corpus of empty input, a truncated JSON fragment, 1 MiB of `'a'`, and text containing the UTF-8 replacement character — `omnifrons_app::contract::harness_adapter::harness_adapter_contract`) produces: `State { phase, observations }` (`AgentPhase::Init | Finished { subtype } | Exited` — `Exited` is named for completeness of the closed set but never produced by a built-in adapter's own `parse_line` in this slice; a process's own exit is reported through the supervisor's pre-existing, separate `state` frame, never through an adapter event), `Message { text }`, `ToolCall(ToolCallProposal)`, `Diagnostic { text }`, and `Unknown { raw, truncated }`.

`LineAgent` (`crates/omnifrons-adapters/src/line_agent.rs`), the one parser both built-in adapters share, maps three `stream-json` shapes — `{"type":"system","subtype":"init",...}` (→ `State`/`Init` with `cwd`/`model`/`session_id`, whichever are present, as text observations, in that order), `{"type":"assistant",...}` (→ one event per content block, in order: a `text` block → `Message`, a `tool_use` block → `ToolCall`, any other block → `Unknown` carrying that block's own JSON — so `parse_line` returns a `Vec<AdapterEvent>`, never empty; R3-004, fixed in review), and `{"type":"result","subtype":...}` (→ `State`/`Finished`) — and falls back to exactly one `Unknown` with the line's own bytes verbatim for anything else: invalid JSON, an unrecognized `type`, or a malformed shape (`crates/omnifrons-adapters/tests/line_agent.rs`).

**`ToolCallProposal` is a proposal only.** Nothing in this slice executes a proposed tool call on the caller's behalf; `AdapterEvent::ToolCall` only ever surfaces `name` and `arguments_text` for a caller (eventually the renderer) to act on, or not. This is the one point of contact with [VP-S18](#procedure-notes-for-vp-s18)'s "no execution without specific consent" requirement below.

### IPC shapes

Three new commands, registered next to the existing ones:

| Command | Params | Returns |
| --- | --- | --- |
| `workspace_pick` | *(none)* | `WorkspaceDto { displayPath }` |
| `workspace_current` | *(none)* | `WorkspaceDto \| null` |
| `adapters_list` | *(none)* | `AdapterDescriptorDto[]` |

`workspace_pick` opens the native folder picker (`tauri-plugin-dialog`'s `blocking_pick_folder`, called only from a `spawn_blocking` task, exactly like `executable_pick_and_probe`'s own `blocking_pick_file` — confirmed against `tauri-plugin-dialog`'s own source via Context7 before relying on it, not assumed) and, on a selection, replaces this shell's single active-workspace slot wholesale; a cancel (or an unresolvable path) reports `no-workspace`. `adapters_list` returns metadata only — `id`, `displayName`, `transportClass`, `promptChannel`, `scopeMode`, `notes` — deliberately never `argvTemplate` or `declaredEnv`'s resolved values, which stay this shell's own launch-time concern (`src-tauri/src/ipc/dto.rs`'s `adapter_descriptor_dto_json_shape_has_no_argv_or_env` asserts this structurally, not just by convention). The `claude-code` descriptor's `notes` disclose, in plain language, what its fixed `--permission-mode dontAsk` means for the user: anything that would need a confirmation is denied by the harness and not executed — it is the harness's most conservative non-interactive mode, executing only actions it already pre-allows (R1-003; `crates/omnifrons-adapters/src/line_agent.rs`'s `claude_code_notes_disclose_the_dont_ask_permission_mode`).

`WorkspaceDto.displayPath` is the second explicit exception to [RCS-001-R14](renderer-content-security.md)'s no-raw-path rule, alongside slice 2's `EvidenceDto.canonicalPath`: both are identity evidence flowing core → renderer for display only (the executable that will run; the directory the agent runs in), never a reference the renderer sends back in any command, and the workspace path is never sent to the harness process either — it receives the workspace only as its own working directory (R1-004). Because the value is the canonical path, on Windows it carries the verbatim `\\?\` prefix that `std::fs::canonicalize` produces there (PR #6's first Windows CI round failed on exactly that mismatch, in a test that compared a child's reported cwd with the canonical root); a display-only simplification of that prefix is deferred debt, and the identity semantics must not change to obtain it.

`harness_spawn`'s `kind` gains a fourth tagged variant:

```jsonc
{"type": "adapter", "adapterId": "claude-code", "approvalId": 42, "prompt": "do the thing"}
```

`adapterId` is validated into a closed `omnifrons_domain::adapter::AdapterId` (→ `unknown-adapter` if unrecognized) and `prompt` into an `AgentPrompt` (→ `prompt-too-large` / `invalid-request` for an interior NUL) before either ever reaches the launch gate or `build_launch`. Five new closed `ShellErrorCode` values: `unknown-adapter`, `prompt-too-large`, `workspace-unavailable` (no active workspace, or `LaunchPlanError::CwdOutsideWorkspace`), `secret-shaped-env` (`LaunchPlanError::SecretShapedEnvKey`), `no-workspace` (`workspace_pick` canceled or unresolvable).

Every captured output frame for an adapter launch is no longer forwarded raw: the shell's `forward_adapter_output` (`src-tauri/src/ipc/commands.rs`; its per-frame mapping is factored into the pure, unit-tested `adapter_wire_frames`) runs a `LineAssembler` over stdout text frames, calling the launched adapter's own `parse_line` on each assembled line (or, once the 64 KiB assembler cap is exceeded, synthesizing `Unknown { truncated: true }` without ever calling `parse_line` on the necessarily-incomplete bytes) and mapping every stderr text frame directly to `AdapterEvent::Diagnostic` — `stdout`/`stderr` raw frames are never emitted for an adapter launch, only `event` and the pre-existing `state`. Three properties of that mapping were fixed in review: a line is reassembled from each raw frame's `continued` flag (below), never from its length; `droppedBefore` on an assembled line's event is the sum over every raw frame that fed it (R3-002 — the last frame's own count alone lost every drop inside a split line), and frames lost while a line was still pending (a nonzero count arriving mid-line), or a partial line still pending when the `state` frame arrives, surface as `Unknown { truncated: true }` rather than a silently merged or dropped line; and `seq` on an adapter launch's `event`/`state` frames is the shell's own contiguous per-launch count of emitted wire frames — a raw frame yields zero, one, or several events, and the renderer keys transcript entries by `id`-`seq` — with a line's summed `droppedBefore` carried on the first of its events and `0` on the rest:

```jsonc
// HarnessFrame::Event -- id/seq/droppedBefore alongside the flattened
// AdapterEventDto's own kind/payload fields
{"stream": "event", "body": {
  "id": 42, "seq": 3, "droppedBefore": 0,
  "kind": "state",
  "payload": {"phase": "init", "subtype": null, "observations": [{"key": "cwd", "value": "/work"}, {"key": "model", "value": "fake-model"}]}
}}
{"stream": "event", "body": {
  "id": 42, "seq": 4, "droppedBefore": 0,
  "kind": "message", "payload": {"text": "hello"}
}}
{"stream": "event", "body": {
  "id": 42, "seq": 5, "droppedBefore": 0,
  "kind": "tool-call", "payload": {"name": "write_file", "argumentsText": "{\"path\":\"notes.md\"}"}
}}
{"stream": "event", "body": {
  "id": 42, "seq": 6, "droppedBefore": 0,
  "kind": "diagnostic", "payload": {"text": "diagnostic: hello"}
}}
{"stream": "event", "body": {
  "id": 42, "seq": 7, "droppedBefore": 3,
  "kind": "unknown", "payload": {"raw": "...", "truncated": true}
}}
```

`Unknown.raw` is rendered as a plain, lossily decoded string rather than base64 or a byte array: every `raw` a built-in adapter's own `parse_line`, or `LineAssembler`'s own truncation, ever produces in this slice originates from text that was already valid UTF-8 (a captured line, a buffer of concatenated already-valid-UTF-8 frames, or one content block's re-serialized JSON) — lossy decoding is a defensive fallback here, never the expected path.

Raw text frames (still emitted for demo and `approved` launches) gain one additive field, `continued`: `true` exactly when `omnifrons-supervisor`'s output capture split a line at the 8 KiB per-frame cap and more of the same line follows in the next frame of that stream, `false` when the frame ends at a genuine line end (a newline, or EOF). The split is decided lazily — a full buffer is only cut once the next byte proves the line goes on — so a genuine line of exactly 8192 bytes is one `continued: false` frame, never a continuation plus an empty terminator, whichever terminator follows it: a bare `\n`, a `\r\n` (the CR stripped, even when the `\r` and its `\n` arrive in different reads — a `\r` at the cap boundary is held until the next byte decides whether it is a line end or content; R3-012, fixed in review, `output_capture`'s own chunk-controlled unit tests), or EOF; `omnifrons_domain::output::FramePayload::Text` carries the same flag, and every consumer decides continuation from it alone (R3-003, fixed in review; `crates/omnifrons-supervisor/tests/output_framing.rs`):

```jsonc
// HarnessFrame text frames -- `continued` is additive; a consumer that
// ignores it keeps working
{"stream": "stdout", "body": {"id": 42, "seq": 3, "droppedBefore": 0, "text": "...first 8192 bytes of a long line...", "continued": true}}
{"stream": "stdout", "body": {"id": 42, "seq": 4, "droppedBefore": 0, "text": "...the rest of that line", "continued": false}}
```

### Deviations from the brief

- **A stdin-write failure surfaces as a `stderr` `Diagnostic`-shaped text frame, not a `State`-shaped "observation."** The raw `OutputFrame`/`FramePayload` vocabulary `omnifrons-supervisor`'s own output-capture module speaks has no concept of an adapter-level "observation" at all — that concept (`AdapterEvent::State`'s own `observations` field) lives only in `omnifrons-app::harness_adapter`, a crate `omnifrons-supervisor` does not depend on and must not start depending on (`docs/repository-layout.md` § Crate map). Routing the failure through the pre-existing `stderr → Diagnostic` mapping every adapter launch already performs is the correctly-layered way to surface it without inventing a new cross-layer concept solely for this one failure path; `output_capture::emit_stdin_write_failed`'s own doc comment records this reasoning, and the path is unit-tested directly (stream, the exact text `stdin write failed`, `seq`, `dropped_before`; R3-005). One consequence stays open as deferred debt: a harness that prints the literal line `stdin write failed` on its own stderr is indistinguishable, at the wire, from this synthetic frame; a distinct diagnostic payload kind would close that and is not introduced in this slice.
- **`fake-agent` hand-builds its own JSON rather than using `serde_json`.** `omnifrons-supervisor`'s own dependency table stays unchanged, as directed; a minimal, deliberately narrow string escaper (`crates/omnifrons-supervisor/src/bin/fake-agent.rs`'s `json_string`) is sufficient for this binary's own fixed, self-controlled content, and its own supervisor-crate test files (`tests/adapter_launch.rs`, `tests/adapter_events.rs`) mirror that same narrowness on the reading side (`extract_json_text_field`) rather than adding a JSON dependency to read it back.
- **`LineAssembler`'s exact-8192-byte continuation heuristic was replaced in review (R3-003).** An earlier revision inferred continuation from a frame's length and recorded its false positive (a genuine line landing exactly on the 8 KiB per-frame cap, misclassified as a continuation) as deferred; the frame now carries an explicit `continued` flag from the capturing side ([IPC shapes](#ipc-shapes)), and continuation is never inferred from length. No longer a deviation.
- **`LineAgent::parse_assistant` reading only the first content block was fixed in review (R3-004).** Every content block of an `assistant` message now yields its own event, in order, and `parse_line` returns a `Vec<AdapterEvent>` ([Event contract](#event-contract)). No longer a deviation.
- **`kind: "approved"` launches inheriting the shell's environment was fixed in review (R1-001).** An earlier revision recorded `EnvPlan::Inherit` for `"approved"` as a deliberate non-narrowing; it now gets the base allowlist ([Launch policy](#launch-policy)). No longer a deviation. The demo-harness launcher (`ProcessSpec::new`'s default) keeps `Inherit` on purpose: it re-execs this application's own binary behind a non-default cargo feature, not a caller-supplied executable.
- **A logical line with frames missing from the middle is reported `Unknown { truncated: true }`, not parsed.** `LineAssembler` marks a line truncated when a nonzero `dropped_before` arrives while that line is still pending, keeps only the contiguous prefix captured before the gap, and flushes a partial line whose terminator never arrives (the process reached its terminal state first) the same way. This is deliberately conservative: under drop conditions the renderer already reports the stream as degraded, and an adapter must never parse a line with a hole in it as if complete. A drop attributable only to the *other* stream can therefore mark an intact line truncated; accepted for this slice.

### Renderer

The renderer half of this slice adds the first surface that actually renders an adapter's structured event stream, on top of the Rust half described above. `renderer/src/ipc/harness.ts` gains the `adapter` `HarnessKind` variant, the `event` `HarnessFrame` variant carrying a discriminated `AgentEvent` union (`state`/`message`/`tool-call`/`diagnostic`/`unknown`, mirroring `AdapterEventDto` field-for-field), `Workspace`/`AdapterDescriptor` types, and `adaptersList()`/`workspacePick()`/`workspaceCurrent()` wrappers alongside the five new `ShellErrorCode` tokens — no new renderer→core surface beyond these typed wrappers, matching every prior slice's own IPC-contract discipline. The `stdout`/`stderr` text-frame body also gains the required `continued: boolean` field the Rust side now emits (`true` when more of the same line follows in the next frame, mirroring `dto.rs` field-for-field); it is carried for contract fidelity and covered by a `harness.test.ts` delivery test, but no renderer surface reassembles split lines in this slice.

`renderer/src/AgentPanel.tsx` is the new component: a workspace section (a Pick workspace button; the display path shown through `PlainTextLine`; `workspace_current` queried on mount; a canceled pick shows the quiet, non-alert status "No workspace selected", never the error banner — mirroring `ApprovalSurface`'s own pick-cancellation handling), an adapter select sourced from `adaptersList()` (display name in the option, the selected adapter's own `notes` shown as text through `PlainTextLine`), an approval select of active approvals (the same sequenced-fetch pattern `HarnessPanel`'s own `approved` kind uses, reused here so a stale `approvals_list` response can never overwrite a newer one), a prompt textarea with an advisory 16 KiB cap measured in UTF-8 bytes (`Start` disabled above it, with an inline `data-testid="agent-prompt-size-validation"` message — advisory only, `AgentPrompt::new` on the Rust side is the sole authority), and Start/Stop restricted to a single active run at a time, matching `HarnessPanel`'s own R3-004 guarantee.

Two run-identity guarantees now hold in `AgentPanel` and, identically, in the slice 1 `HarnessPanel` (both were missing there before this slice's review). First, every Start increments a per-spawn generation token (`spawnGenerationRef`) before `harnessSpawn` is called and captures it in the closure of that spawn's own `Channel` `onmessage`; the shared frame handler rejects any frame whose captured generation is not the current one. Every `harnessSpawn` wires a fresh `Channel` to the same stable handler, so a trailing frame from an earlier run's channel can otherwise arrive after a new run has started — before or after the new run's id is known, and carrying whatever id it likes — and it must never be appended nor allowed to move the badge (R1-001/R3-001); the generation alone settles that, without relying on the new id already being known. Once `harnessSpawn` resolves, the id is held in a `runIdRef` for the rest of that generation — cleared only when the next Start bumps the generation, deliberately not when the run ends — and a frame on the current channel carrying a different id is dropped too, belt and braces, after the run has ended as much as while it runs; a trailing frame carrying the run's own id after its terminal `state` frame or a successful stop is still applied, since it is that run's own output (R1-011/R3-011). Whether the run is *running* is the `activeId` state plus a `runEndedRef`, never the id ref. Frames of the current generation that arrive *before* `harnessSpawn` resolves are applied, not dropped: an instantly exiting process's terminal `state` frame can beat the spawn promise, and it still ends the run — a `runEndedRef` set by that frame makes the resolve handler leave the run ended (no active id, no "running" badge, and in `HarnessPanel` no remembered id) rather than mark it active after the fact. Second, a terminal `state` frame ends the run on its own — active id cleared, Start re-enabled, Stop disabled — rather than only the Stop path doing so (R3-002); every `state` frame is terminal by contract (`HarnessStateFrameBody` extends `ProcessTerminalState`'s closed `exited`/`killed`/`orphan-risk/uncertain` set). `HarnessPanel` additionally forgets the persisted process id on that frame, exactly as it already does for a terminal `harness_observe` status. A rejected `harness_stop`, in both panels, keeps the run active — banner shown, Stop still enabled, the run's frames still applied — rather than pretending a process ended that the supervisor never confirmed terminal.

The transcript renders, in order: the sent prompt as an untrusted "you" entry through `PlainTextLine` (entered before the spawn is requested and keyed by generation, so a frame that beats the spawn promise still follows it; if the spawn is rejected, only that generation's own prompt entry is withdrawn — a frame that already reached the current channel before the rejection is kept, not wiped), then each event by `kind` — `message` as plain text, `state` as one compact `phase, subtype, key: value, ...` line, `diagnostic` prefixed `"diagnostic: "`, `unknown` as its raw line through `PlainTextLine` with a trailing `" (truncated)"` marker when flagged, and `tool-call` inside a `data-testid="tool-call-proposal"` block labelled "proposal, not executed" that renders `name`/`argumentsText` as text only — **zero interactive elements** (no `button`, `a`, `input`, or `textarea`), since nothing this slice ships ever executes a proposed tool call (`docs/spike-log.md` § Slice 3's own Rust-side notes on `ToolCallProposal`, VP-S18). The run's own terminal `state` frame is recorded as a final `state: <token>` transcript line, the way `HarnessPanel` logs it. Any entry with `droppedBefore > 0` — an adapter event or that terminal `state` frame alike (R3-003: a drop right before the process's exit is surfaced the same way as one mid-stream) — is prefixed with the marker "`N` frames dropped before this entry — degraded, restart to replay", rendered by a `DroppedFramesMarker` component local to `AgentPanel` (not shared across panels: `HarnessPanel` keeps its own inline marker with slice 1's wording "`N` frames dropped before this line", left unchanged so its existing test expectations hold); the transcript is capped at 2000 entries with a cumulative trimmed-count marker, mirroring `HarnessPanel`'s own `MAX_LOG_ENTRIES`. Two fixed, static lines sit above the transcript: the scope badge, reading exactly "advisory scope — not a sandbox" (every built-in adapter in this slice is `ScopeMode::Advisory` — `docs/target-architecture.md` invariant 5 — and "sandbox" appears nowhere else in this panel), and the producer line, reading exactly "producer: unsigned (unknown)" (this slice implements no AEC-001 producer-signing or pairing at all — `docs/adapter-feed-events.md`'s "Producer identity and key distribution" — so an honest panel states plainly that no signature exists to verify, rather than implying a verdict this slice never computes). The error banner (`role="alert"`) renders every new code verbatim and reuses `HarnessPanel`'s own four-code `DENIAL_CODES` "untrusted" wording for a gate denial on the adapter's own `approvalId` — `unknown-adapter`/`prompt-too-large`/`workspace-unavailable`/`secret-shaped-env`/`no-workspace` render as plain catalogue codes, never "untrusted" (they are validation/environment failures, not a trust denial). ## Slice 4 — second built-in harness adapter: the pseudo-terminal fallback

This slice's Rust half (`omnifrons-domain`, `omnifrons-app`, `omnifrons-adapters`, `omnifrons-supervisor`, `src-tauri`) adds the second built-in harness adapter, `pty-cli`, described below; the renderer half is not part of this slice — a renderer implementer follows against the wire shapes stated precisely in [IPC shapes](#ipc-shapes-1), and the renderer half is recorded separately in [Renderer](#renderer-3).

### Scope

The Pre-alpha scope asks for "two structurally different built-in harness adapters". Slice 3's two adapters share one transport class, one parser, and one prompt channel; they are two descriptors over one mechanism. This slice reads "structurally different" as different on every axis that mechanism is made of — **this is the spike's reading, recorded here as such, not an owner decision** — and `pty-cli` differs on all four:

| Axis | `stream-json-cli` / `claude-code` (slice 3) | `pty-cli` (this slice) |
| --- | --- | --- |
| Transport class | `StructuredStreamingCli` | `Pty` |
| Process topology | stdio pipes, own process group | one pseudo-terminal as stdin/stdout/stderr; the child is the session leader of that controlling terminal |
| Prompt channel | `StdinThenClose` (written to stdin, then EOF) | `PtyTyped` (typed into the terminal, followed by a carriage return; nothing is closed) |
| Event production | a line parser (`LineAgent::parse_line`) | a byte normalizer in core (`omnifrons_app::TerminalNormalizer`) over an untrusted byte stream with no structured events |

Everything stays `dev-mode-only` (VP-001-R2). PTY is an explicit degraded fallback (`docs/target-architecture.md` invariant 6); a terminal is never a sandbox and never authorization ([TM-001 HAR-5, PRC-2](threat-model.md)): the only sequences that ever become a typed value are a sanitized title and a sanitized notification, emitted as data to show as text, and every other recognized family is dropped and counted. The `pty-cli` descriptor's `notes` disclose exactly that, in plain English, to every `adapters_list` caller (`crates/omnifrons-adapters/tests/pty_cli.rs`'s `pty_cli_notes_disclose_the_degraded_fallback_in_plain_english`).

The closed catalog grows from two to three: `omnifrons_adapters::catalog()` (new, crate level) is `line_agent::catalog()` (still exactly the two line agents) plus `PtyCli`; the shell's `AdapterState` now builds its `AdapterCatalog` from the crate-level list. `AdapterId` gains `pty-cli`; `HarnessKindDto::Adapter` is unchanged (`adapterId` selects it).

### Design decisions (spike defaults, each disclosed)

Every default below is the spike's; the open owner decisions they touch are named where they arise and collected under [Deviations and debt](#deviations-and-debt).

- **D1 — no new dependency.** `portable-pty` (0.9.0) was rejected: twelve transitive dependencies (`winapi` 0.3, `bitflags` 1, a second `nix` 0.28, `serial2`, …), and its unix spawn calls `close_random_fds()` in the child, which would close the sealed memfd and break the `/proc/self/fd/<n>` exec slice 2 relies on. The supervisor's existing `nix` gains the `term` feature (`nix::pty::openpty`, `nix::sys::termios::Termios`; verified against the vendored 0.31.3 source, where `pty` is gated by exactly that feature and `unistd::setsid` sits in the `process` block `signal` already enables), and its `tokio` gains `net` (`tokio::io::unix::AsyncFd`; verified against the vendored 1.53.1 source: `cfg_net_unix!` is `all(unix, feature = "net")`); the transitive `socket2`/`mio` were already in `Cargo.lock` through the shell's Tauri dependency, so no crate is new to the lockfile. `omnifrons-adapters`' dependency set is unchanged (`tests/deps.rs` as is): `PtyCli` is pure, and every piece of PTY plumbing lives in the supervisor.
- **D2 — unix only.** `openpty`, `setsid`, and `TIOCSCTTY` are the POSIX pseudo-terminal calls `nix`/`libc` expose on both Linux and macOS, and nothing else is used; a master read failing with `EIO` (Linux, once every slave descriptor is closed) is treated as end of input exactly like the zero-byte read macOS reports (`crates/omnifrons-supervisor/src/pty.rs`'s `master_read_after_the_slave_is_closed_is_eof`). On Windows `spawn_approved` refuses a `Pty` plan with a typed `SupervisorError::PtyUnsupported` (→ `ShellErrorCode::PtyUnsupported`, wire `pty-unsupported`) before touching the handle, the running cap, or any bookkeeping; the test for that is `#[cfg(windows)]` (`tests/pty_launch.rs`), and ConPTY is recorded as debt next to the Job Object debt. macOS was not executed on the contributor machine (CI's `macos-latest` leg runs these tests); one macOS-specific fact was verified from the vendored `libc` 0.2.189 source rather than assumed: there `TIOCSCTTY` is a `c_uint` while `ioctl` takes a `c_ulong` request (`src/new/apple/xnu/sys/ttycom.rs`, `src/unix/bsd/mod.rs`), so `pty.rs` widens it losslessly per target instead of casting.
- **D3 — normalization in core, plain-text rendering.** `omnifrons_app::TerminalNormalizer` (`crates/omnifrons-app/src/terminal_normalizer.rs`) is a pure, streaming state machine over bytes whose state (the sequence being collected, pending text including a held-back incomplete UTF-8 tail, the drop counts) persists across `push` calls; `finish()` flushes pending text lossily and counts a still-open sequence as `malformed`; `take_drops()` drains the counts. Its policy, mapped onto RCS-001's table, is in [Normalizer policy](#normalizer-policy) below. Every OSC/DCS/APC/PM/SOS string (and, by the same bound, a CSI parameter run) is capped at **4 KiB** — RCS-001 D11's proposed default, adopted as the spike default; **D11 is an open owner decision**, and the terminator-timeout half of it is not implemented (a bound only, no clock).
- **D4 — domain and app types.** `PromptChannel` gains `PtyTyped`; `AdapterId` gains `pty-cli`; `AdapterEvent` gains `TerminalText { text }`, `TerminalAction(TerminalAction)` with `omnifrons_domain::terminal::TerminalAction { Title(String), Notification(String) }`, and `TerminalDrops(DropCounts)` with `omnifrons_domain::terminal::DropCounts { layout, hyperlink, clipboard, file_transfer, string, unknown, malformed }` (`is_zero()`, saturating `+=`). These are **proposed AEC-001 kinds**, not adopted ones. `LaunchPlan` gains `transport: TransportClass`: `LineAgent::build_launch` sets `StructuredStreamingCli` explicitly; `PtyCli::build_launch` sets `Pty`, `stdin: StdinPlan::Null` (unused on the PTY path), `prompt: Some(..)`, `argv` empty, `EnvPlan::new(&[])` (the base allowlist only), the workspace's own path as cwd validated exactly as `LineAgent` does, and `ScopeMode::Advisory` — and refuses, with the new `LaunchPlanError::PromptNotTypeable`, a prompt carrying any C0 control other than newline and tab, or DEL: bytes the terminal's line discipline (default `termios`: canonical mode, `ISIG`, `ICRNL`) would interpret rather than type — `VINTR` 0x03, `VEOF` 0x04, `VSUSP` 0x1A, `VQUIT` 0x1C, `\r` (Enter mid-text), ESC (opens a sequence), `VERASE` DEL — decided at plan-building time, before anything is launched. The line agents' stdin path is unchanged and still accepts every one of those bytes (`crates/omnifrons-adapters/tests/pty_cli.rs`). `PtyCli::parse_line` is never called on the PTY path and is still total: every input yields exactly one byte-identical `Unknown`, so the shared `harness_adapter_contract` runs against it alongside the two line agents (`crates/omnifrons-adapters/tests/pty_cli.rs`).
- **D5 — the supervisor's PTY spawn path.** `TokioProcessSupervisor::spawn_approved` (`crates/omnifrons-supervisor/src/lib.rs`) now decides the stdio wiring from `plan.transport` first (`plan_stdio`), before the handle is touched. On unix a `Pty` plan opens a pair at a fixed **80x24** (`nix::pty::openpty`, default terminal settings; resize is a control write path, deferred), marks both ends close-on-exec (the master must never leak into the child or any other exec; the slave reaches the child only by `dup2` onto 0/1/2, which clears the flag on those copies) and the master non-blocking, hands three duplicates of the slave to the command as stdin/stdout/stderr, sets `TERM=dumb`, `COLUMNS=80`, `LINES=24` explicitly (never read from the supervisor's own environment: `TERM=dumb` asks a well-behaved program for the fewest escape sequences, which is what a plain-text rendering with layout controls dropped wants), and installs **one `pre_exec`** — the single `#[allow(unsafe_code)]` this slice adds, `pty::install_controlling_terminal`, whose `SAFETY` comment names its two async-signal-safe calls, `setsid(2)` and `ioctl(0, TIOCSCTTY, 0)`. `process_group(0)` is deliberately not called on this path: `setsid` makes the child its own session and process-group leader, so the unchanged stop path (`killpg(SIGTERM)` → grace → `killpg(SIGKILL)`) still reaches it — proven by `pty_child_is_a_session_leader_and_a_sigterm_ignoring_child_ends_killed` (`getsid(pid) == getpgid(pid) == pid`, then `Killed`, then `ESRCH`). The launch-policy choke point stays single: `finish_spawn` now takes a `StdioPlan::{Pipes(StdinPlan), Pty(pair)}` and applies the environment allowlist re-check, the running cap, `kill_on_drop`, the spawn, the bookkeeping, and the terminal `State` frame identically to both, branching only on the wiring — and `process_group(0)` moved into its `Pipes` arm from the two callers, so it too is applied in exactly one place. The running cap (`MAX_RUNNING_CHILDREN`, 16) is additionally checked by `spawn_approved` itself, through the shared `ensure_running_capacity`, before `plan_stdio` opens anything — so a caller at the cap is refused with `TooManyProcesses` before `openpty` ever runs, exactly as the pipe path (which allocates nothing before `finish_spawn`'s own check) always was; the order on `spawn_approved` is: unsupported transport, then the cap, then the wiring. Proven by `tests/pty_running_cap.rs`, its own test binary because it lowers the test process's `RLIMIT_NOFILE` soft limit to zero around the refused call (an `openpty` inside that window fails with `EMFILE` and would surface as `Spawn`; a before/after descriptor count could not tell the two orders apart, since a pair opened and then dropped on the cap error leaves the count unchanged). The check-then-insert window on the `children` lock — two concurrent launches can both pass the check and briefly exceed the cap by one — is pre-existing and shared by both paths; the bound exists to keep bookkeeping finite, not to be exact. After `spawn`, `command` is dropped explicitly (it still held this process's copies of the slave; the master only reports EOF once every slave descriptor outside the child is closed). Output is one reader on the master — `tokio::io::unix::AsyncFd<OwnedFd>`, shared through an `Arc` with the prompt-typing task since `AsyncFd` polls readiness through `&self` — wrapped in a small `AsyncRead` adapter and fed to the unchanged `output_capture::drain_stream`, so frames keep slice 1's framing (`MAX_TEXT_FRAME_BYTES`, `continued`, CRLF handling) and `dropped_before` semantics; frames are labelled `stdout` (a terminal has no stderr, so a PTY launch never produces a `stderr` frame except the supervisor's own synthetic `stdin write failed`). The `State` frame gate now counts the readers actually spawned (`output_capture::new_channel(reader_count)`: two for pipes, one for a master) rather than assuming two. The prompt, when `Some`, is typed into the master from the runtime after spawn — the bytes then `\r` — and a write failure surfaces exactly like the stdin case (`emit_stdin_write_failed`, the same text), proven deterministically against a pipe whose read end is already closed (`EPIPE`; a read-only descriptor would never report writable, which the first version of that fixture learned the hard way as a hang). Sealed-memfd exec keeps working on this path: `pre_exec` forces `std::process::Command` onto its fork-then-exec route, which never closes inherited descriptors, so `/proc/self/fd/<n>` still resolves in the child (`sealed_memfd_exec_keeps_working_on_the_pty_path`, Linux only, execs the whole `fake-agent` binary from a sealed memfd inside a terminal).
- **D6 — the shell.** `forward_adapter_output` (`src-tauri/src/ipc/commands.rs`) branches on the adapter descriptor's transport class through the pure `forwarder_for(TransportClass) -> ForwarderKind::{Line, Pty}` (tested directly, and against the managed catalog's own descriptor for each built-in id, since the live function cannot be driven without Tauri state): `StructuredStreamingCli` keeps slice 3's `LineAssembler` + `parse_line` mapping; `Pty` runs the new pure `pty_wire_frames` over a per-launch `PtyForwarder` (a `TerminalNormalizer` plus the `droppedBefore` left pending by raw frames that produced no wire frame). Per raw `stdout` frame: its text plus a trailing `\n` unless `continued` (restoring the line end the supervisor's framing consumed) is pushed through the normalizer; each `Text` chunk becomes one `terminal-text` event (adjacent text chunks coalesced), each action one `terminal-action` event, and at most one `terminal-drops` event closes the frame, only when the counts changed; the raw frame's `droppedBefore` (summed with anything pending) rides on the first wire frame it produces and `0` on the rest, and a silent raw frame carries its count forward rather than losing it. A `stderr` frame maps to `diagnostic` as on the line path. A `State` frame first calls `finish()` — a sequence still open is malformed and reported as drops — then becomes the `state` frame, always last. Everything goes through the existing `AdapterWireSequencer`, so `seq` stays contiguous per launch. `ShellErrorCode` gains `pty-unsupported` and `prompt-not-typeable` (`LaunchPlanError::PromptNotTypeable` mapped), each with a fixed, slash-free catalogue message.
- **D7 — approval and transport.** Slice 2's approval record binds path, size, and digest, not the transport: launching an approved executable under `pty-cli` is allowed in this slice with no renewed approval. The target architecture lists transport among approval identity evidence, and **whether a transport change must renew an approval is undecided** — recorded as debt, not decided here.
- **D8 — `fake-agent` and the tests.** `fake-agent` gains `--pty-report` (prints `isatty stdin=<bool> stdout=<bool> stderr=<bool>`, then `TERM=`/`COLUMNS=`/`LINES=` with their values, then one `env-keys <K1> <K2> …` line — key names only, never values), `--pty-echo` (reads one line from stdin, prints `typed: <line>`), `--pty-corpus` (writes the shared corpus bytes verbatim, then a newline and a final `corpus-done` line), and `--pty-ignore-sigterm` (unix: installs the demo harness's own SIGTERM-ignore disposition through a newly public `demo::ignore_sigterm`, so no second `unsafe` site exists, prints `ready` once it is in place, sleeps until killed). The supervisor tests (`crates/omnifrons-supervisor/tests/pty_launch.rs`, all `#[cfg(unix)]` with the reason stated in the file, generous deadlines, synchronizing only on the child's own output lines) prove: the child sees a terminal on all three descriptors with `TERM=dumb`, `COLUMNS=80`, `LINES=24`, and exits 0 through a confirmed reap; a typed prompt is read as one line; the observed environment is exactly the base allowlist plus `TERM`/`COLUMNS`/`LINES` and a planted secret-shaped key never reaches the child (the slice-3 re-exec pattern, `Command::env` on a re-exec'd copy of the test binary, never `set_var`); the corpus round-trips as raw frames that re-join to exactly the corpus bytes (the terminal's own `\n` → `\r\n` output processing undone by the supervisor's CRLF framing, nothing else altered, no frame `continued`); the session-leader and `Killed` proof above; and the sealed-memfd proof (Linux). The shell's tests drive the corpus, framed exactly as the supervisor frames it, through `pty_wire_frames` and assert the exact text, action sequence, summed drop counts, contiguous `seq`, and that the clipboard sentinel, ESC, and the hyperlink target appear nowhere in the serialized wire frames.

### Normalizer policy

The table maps `TerminalNormalizer`'s behavior onto RCS-001's policy table row by row (`docs/renderer-content-security.md` § Terminal control and OSC policy). "Dropped" always means: the sequence's bytes never reach any chunk, and the family's `DropCounts` field is incremented.

| RCS-001 row | Sequences | This slice |
| --- | --- | --- |
| Layout controls (allowed in a terminal pane) | CSI SGR `m`; cursor `A B C D E F G H f`; erase `J K`; scroll `S T`; mode set/reset `h l` including `?1049` (alternate screen); `ESC` + one character (`ESC c`, `ESC 7`, `ESC 8`, …) and charset selection (`ESC ( B`) | Dropped and counted `layout`: this slice has no terminal pane, so nothing is applied — the plain-text rendering is the whole point of the fallback |
| Title (OSC 0/2) | `ESC ] 0 ; text BEL` / `ST`, `ESC ] 2 ; …` | Typed action `Title(text)`: lossily decoded, C0/DEL/C1 and the zero-width/bidirectional format controls (U+200B–U+200F, U+202A–U+202E, U+2066–U+2069) stripped, capped at 256 characters; emitted as data, never applied to any chrome |
| Hyperlinks (OSC 8) | open and close sequences | Dropped and counted `hyperlink` (inert by default); the label text between them stays text; the target never renders |
| Clipboard (OSC 52) | write and query | Both dropped and counted `clipboard`; the payload never reaches any output (asserted on a sentinel in three test suites); no opt-in exists in this slice (RCS-001 D2 is open) |
| Notifications (OSC 9) | `ESC ] 9 ; text BEL` / `ST`, any `9;` variant's payload | Typed action `Notification(text)`, sanitized and capped exactly like a title; surfaced as data, never as a system prompt (RCS-001 D8's feed-alert routing is open — nothing here routes anywhere) |
| File transfer and image protocols | OSC 1337 family; Sixel (DCS whose final byte is `q`); Kitty graphics (APC starting `G`) | Dropped and counted `file_transfer` (RCS-001 D1's inert-bitmap option is open — no image is ever decoded here) |
| DCS/APC/PM/SOS strings | any other control string | Ignored, bounded, counted `string` |
| Unknown or malformed | unknown CSI final; an OSC number outside the rows above; an 8-bit C1 control in text, whether an encoded code point (U+0080–U+009F in valid UTF-8) or a raw byte (0x80–0x9F outside any valid UTF-8 sequence) — a raw 8-bit introducer (0x9B CSI, 0x9D OSC, 0x90 DCS, 0x9E PM, 0x9F APC, 0x9C ST) is never interpreted as a sequence start: the byte is dropped and what follows renders as text; a bare ESC at EOF or followed by an unexpected byte; a string meeting a newline before its terminator, or exceeding the 4 KiB bound | Dropped and counted `unknown` (the first three) or `malformed` (the rest). On a newline or overflow the sequence is aborted, its consumed payload dropped, and every subsequent byte renders as plain text — the aborting newline itself is kept as text so line structure survives (RCS-001's "aborted … subsequent byte renders as plain text") |

Text outside every recognized sequence is returned verbatim (RCS-001-R18): tab, BEL, a bare `\r`, and `\r\n`/`\n` all pass through (the renderer strips C0 controls, so a `\r`-updated progress bar renders concatenated — recorded as debt); invalid UTF-8 is lossily decoded, never dropped, with one exception: a raw C1 byte outside any valid UTF-8 sequence is dropped and counted `unknown` rather than replaced (a continuation byte in that range inside a valid character, `C3 85` for `Å`, is untouched); a multi-byte character split across two pushes is re-joined (an incomplete trailing sequence is held back, never emitted as U+FFFD early; a four-byte character split at each of its three interior boundaries is tested). The invariants — no chunk ever contains ESC, a C1 control code point, or the bytes of a dropped sequence; the clipboard payload never appears; sanitization never removes text outside a recognized sequence — are tested over the shared corpus (`crates/omnifrons-app/tests/terminal_normalizer.rs`), which is also what `fake-agent --pty-corpus` emits and what the shell's forwarder test drives: SGR colors, every cursor final, erase, scroll, alternate-screen enter/leave, an OSC 0 with an embedded C0, a tab, and a bidi override, an OSC 2 over 256 characters, an OSC 8 open/label/close, an OSC 52 write with a sentinel payload and an OSC 52 query, an OSC 9 with a bidi override, an OSC 1337 `File=`, a DCS Sixel, an APC Kitty, an unknown OSC number, a generic DCS, a PM, an SOS, four single-character/charset escapes, an unterminated OSC over 4 KiB, an OSC with a newline inside, invalid UTF-8 bytes, a `\r`-updated progress bar, CRLF lines, multi-byte text, and a bare ESC at the very end.

### Deviations and debt

Deviations from the brief, each with its reason:

- **`--pty-report` prints more than the brief listed.** The brief names `isatty stdin=<bool> stdout=<bool>` and `TERM=<value>`; the fixture also prints `stderr=<bool>` (the tests must prove all three descriptors are the terminal), `COLUMNS=`/`LINES=` (the two other values the supervisor sets), and an `env-keys` line (the environment test needs key names; values are never printed). A superset, chosen over a fifth mode.
- **`--pty-corpus` writes a newline between the corpus and `corpus-done`.** The corpus ends in a bare ESC; without the newline `corpus-done`'s `c` would turn it into `ESC c` (a layout escape) instead of the malformed bare ESC the fixture is meant to carry. Either way the round-trip test re-joins the raw frames to exactly the corpus bytes.
- **`process_group(0)` moved from the two callers into `finish_spawn`'s pipe arm.** The brief asked for a single launch-policy choke point; leaving process grouping in the callers would have left one launch-policy decision outside it.
- **A `Wiring` enum alongside `StdioPlan`.** `StdioPlan` is what a caller asks for; `Wiring` is what `finish_spawn` has prepared before `spawn` (the registered master, for the PTY case) — the "or equivalent" the brief allowed, kept as two types so the pair's slave is released before the child is inserted into the bookkeeping.
- **`prompt: None` is accepted on the PTY path** (nothing is typed). `PtyCli` always sets `Some`; the tests use `None` for the corpus and report fixtures so the terminal's echo of a typed prompt cannot interleave with the output under assertion.
- **The master is one `AsyncFd<OwnedFd>` shared through an `Arc`** between the reader task and the prompt-typing task, rather than a duplicate descriptor per task: one reactor registration, one close.
- **CSI parameter runs are bounded by the same 4 KiB as strings.** The brief bounds only strings; an unbounded CSI would be the one place a hostile stream could grow state without limit. Tested at exactly the bound (still recognized, dropped as layout) and one byte past it (aborted as malformed, the overflowing byte and the would-be final rendering as text), mirroring the OSC string tests.
- **8-bit C1 controls in text are stripped and counted `unknown`, in both forms.** The brief states the invariant (no chunk ever contains a C1 control) without saying where the stripping happens. An encoded code point is stripped after lossy decoding, per code point, so U+0085 in a UTF-8 stream never reaches a chunk; a raw byte 0x80–0x9F outside any valid UTF-8 sequence is detected before decoding (`<[u8]>::utf8_chunks`, whose invalid runs are exactly the ones `from_utf8_lossy` would replace) and dropped — lossy decoding alone had turned it into U+FFFD and counted nothing. A raw 8-bit introducer is deliberately not interpreted as a sequence start: `0x9B 31m` renders `31m` as text with one `unknown` counted, the conservative reading for a plain-text rendering. Only an isolated byte in 0x80–0x9F — an invalid run of exactly one byte — is counted; every other invalid run becomes exactly one U+FFFD with nothing counted, including a truncated multi-byte sequence whose continuation bytes fall in that range (`F0 9F 98` cut short by `FF` is one U+FFFD, and the lone `FF` after it, outside the range, one more — pinned by `an_invalid_multi_byte_run_containing_c1_range_bytes_is_one_replacement_and_never_counted`).
- **The running-cap-before-`openpty` proof lowers `RLIMIT_NOFILE` rather than counting descriptors.** A before/after descriptor count cannot tell the two orders apart: a pair opened and then dropped on the cap error leaves the count unchanged, so the pre-fix code would have passed such a test. `crates/omnifrons-supervisor/tests/pty_running_cap.rs` therefore lowers the test process's own soft limit to zero around the refused call — an `openpty` inside that window fails with `EMFILE` and surfaces as `SupervisorError::Spawn`, so `TooManyProcesses` proves the cap was checked first (the observed pre-fix red was exactly `Spawn("openpty: EMFILE: Too many open files")`). The limit is restored by a guard's `Drop`, so a failed assertion never leaves the process unable to open anything; the test is its own binary because the limit is process-wide; and it needs nix's `resource` feature as a `cfg(unix)` dev-dependency only, never for the library. Like the other PTY tests it has not run on macOS locally (CI's `macos-latest` leg).
- **DEL is refused in a typed prompt alongside the C0 controls.** The review brief named the C0 controls; DEL (0x7F) is `VERASE` under default `termios` on Linux and macOS and would erase the previously typed character — the same class of line-discipline interpretation, so it is refused with them.
- **A new `ShellErrorCode`, `prompt-not-typeable`, rather than `invalid-request`.** `invalid-request`'s own catalogue message names `rate_hz`/`lines`, and a typed-prompt refusal is adapter-specific and user-actionable (the same prompt launches under a line agent), so it gets its own closed code with a fixed message; the renderer's `ShellErrorCode` union must gain it.
- **The shared corpus lives in production code, ungated** (`omnifrons_app::terminal_normalizer::corpus`). The `fake-agent` binary is built without any dev feature and must emit exactly these bytes, so a `contract-tests`-gated fixture would not have reached it; the cost is one small module.
- **The Windows red was not observed before its implementation.** The `#[cfg(windows)]` typed-error test was written with the other supervisor tests, but its failure to compile against the missing `SupervisorError::PtyUnsupported` variant was not captured in a separate Windows cross-compilation pass before that variant was added; the cross-compiled clippy pass recorded under [Relationship to VP-001](#relationship-to-vp-001-3) is the only Windows evidence, and it is a type-check, never an execution.
- **The prompt-write-failure fixture's first version hung** (a pipe's read end never reports writable, so `type_prompt` waited forever inside the unit-test binary for fourteen minutes before the run was killed); the shipped fixture uses a write end whose reader is closed, which the reactor reports ready and which fails with `EPIPE`. Recorded because it is exactly the kind of platform behavior VP-S16 should probe on macOS too (kqueue reports the same condition as `EV_EOF`).

Debt and open owner decisions this slice names without deciding:

- **RCS-001 D11** — the 4 KiB string bound is the spike default; the terminator timeout is not implemented. **RCS-001 D1** (images as inert bitmaps per scope), **D2** (clipboard-write opt-in and per-write acceptance), and **D8** (notification routing to a feed alert) are all untouched: everything in those families is dropped, and a title/notification is data only.
- **Transport in approval identity** — the target architecture lists transport among approval identity evidence; whether launching an approved executable under a different transport (`pty-cli` versus a line agent) must renew the approval is undecided, and this slice allows it.
- **Resize** is a control write path (`TIOCSWINSZ` on the master) this slice does not expose; every PTY child is 80x24 for its lifetime.
- **Interactive input** — nothing after the typed prompt can be sent to the terminal; and a single-line prompt longer than the line discipline's canonical buffer (4095 bytes on Linux) is truncated by the kernel before the child reads it, silently — a real limit of typing a prompt rather than piping it.
- **A typed prompt is subject to the line discipline in general** — everything the kernel's tty layer does to typed input applies to it: the canonical buffer limit above, the control bytes now refused at plan-building time (`prompt-not-typeable`), `ICRNL`, echo, and any `termios` change the child itself makes after launch (a child that switches to raw mode before the prompt arrives reads the very same bytes differently). This slice refuses what the default discipline would interpret and records the rest, rather than changing `termios`.
- **ConPTY** on Windows, next to the Job Object debt: the typed `pty-unsupported` refusal is the whole Windows story.
- **The echo of the typed prompt** appears in the output stream (the line discipline echoes typed input by default; no `termios` change is made), rendered through the same normalizer as everything else; a consumer sees the prompt twice (once as its own transcript entry, once echoed). Disabling `ECHO` is a one-line `termios` change deliberately not made in this slice, since a real interactive CLI expects a terminal that echoes.
- **`\r`-updated progress bars concatenate** in a plain-text rendering (the renderer strips a bare `\r`), and **OSC 777** (the rxvt-style notification) is counted `unknown` rather than treated as a notification variant; **punycode disclosure** of a domain-like substring inside a title or notification (RCS-001's table) is not implemented — the text is sanitized and capped only.
- **A harness whose own stderr text is `stdin write failed`** remains indistinguishable from the supervisor's synthetic frame, as recorded for slice 3.

## Slice 5 — the outbox (HAP-001 launch side, 5a)

This slice's Rust half (`omnifrons-domain`, `omnifrons-app`, `omnifrons-adapters`, `omnifrons-supervisor`, `src-tauri`) implements the launch side of the [heavy-asset publication contract](heavy-asset-publication.md) (HAP-001, Draft): the outbox declaration and its validation, the run subdirectory created before spawn and declared to the harness, the typed publish proposal a line agent recognizes, the end-of-run and whole-outbox inventories as proposals only, candidate validation under the single-handle discipline, and the classification policy as a pure classifier. Publication itself — approval, provider adapters, the Catalog record, the journal, recovery entries, the guidance-note write (D18), the wrong-root scan (D16), and handoff preflight — is slice 5b and is not implemented here. The renderer half, built against the wire shapes in [IPC shapes](#ipc-shapes-2), is recorded in [Renderer](#renderer-4).

### Scope

In: HAP-001-R8 (a project's policy declares one project-relative outbox path, default `.omnifrons/outbox/` per D17; a declaration that is a link or resolves outside the project is `outbox-invalid`), R9 (every adapter launch plan declares the run subdirectory through exactly one non-secret environment key, `OMNIFRONS_OUTPUT_DIR`, with the working directory unchanged), R10 (the subdirectory is created before spawn with a create-exclusive operation and owner-only permissions, relative to the validated outbox handle, and verified by handle; any failure is `outbox-unavailable` and nothing is spawned, D14), R11 and the first sentence of R12 (attribution only by the run's own `artifact.publish` proposal naming a digest equal to the one computed from the entry's handle; location alone never attributes), the run-end inventory of the run subdirectory and the whole-outbox inventory as proposals (R12), R13–R16 and R20 as far as validation goes (one no-follow open per entry, every identity fact and the digest from that handle, a link never dereferenced, a non-regular file `outbox-escape`, a link count above one `outbox-linked`), R17's held handles capped at D22's 32 across every remembered run of the active workspace within a shell session, R19's Windows disclosure, and the classification defaults R1–R4 imply as a pure classifier (Markdown never `generated-heavy`; an executable always `executable`, quarantine by default; a `git-tracked` row never published through this path; no row → `unclassified`). Out, and named as debt below: everything from approval onward, and the product work area check (R7), which has no use site in 5a because nothing here writes a recovery entry or a journal.

### Design decisions (spike defaults, each disclosed)

Every default below is the spike's; the HAP-001 open decisions it assumes are named where they arise. A feature that assumes a default before the owner disposes must say so, and this section does.

- **D1 — domain types** (`crates/omnifrons-domain/src/outbox.rs`). `OutboxPath` (project-relative; refuses empty, absolute, a `C:` drive prefix on every platform since a policy roams, a `..` component, and a backslash — a roaming policy names its path with `/`), `RunId` (one path component of `[A-Za-z0-9_-]{1,64}`, so it joins onto the outbox path without a second validation; HAP-001 D20's `<outbox>/<run id>/`), `CandidateEntry { name (relative to the outbox), size, digest, detected_type, attribution, class }`, `Attribution::{Run(RunId) | Unattributed}`, `ArtifactClass::{GeneratedHeavy, GitTracked, PortableText, Executable, Unclassified}` (tokens `generated-heavy`, `git-tracked`, `portable-text`, `executable`, `unclassified`), `CandidateState::{Candidate, OutboxEscape, OutboxLinked}` and `OutboxFailure::{OutboxInvalid, OutboxUnavailable}` as the closed wire tokens, `ContentDigest` as a type alias of slice 2's `Sha256Digest` (HAP-001 D13 selects SHA-256; `Sha256Digest::from_hex` is new), `DetectedType` with magic-byte detection for PDF, Office documents (a ZIP container named `.docx`/`.xlsx`/`.pptx`/`.odt`/`.ods`/`.odp`), PNG, JPEG, GIF, WebP, MP3, WAV, Ogg, FLAC, MP4, Matroska, ZIP, gzip, 7z, tar (`ustar` at offset 257, so 512 bytes are sniffed), ELF, PE, Mach-O, and `#!` scripts, then Markdown/plain text by UTF-8 validity and extension, else `unknown` — content wins over the name (HAP-001-R1), and `PublishProposal { entries: [ProposedEntry { name, sha256 }] }` behind `AdapterEvent::ArtifactPublish`, the typed proposal a line agent recognizes for the `tool_use` named `artifact.publish` (D5).
- **D2 — application ports** (`crates/omnifrons-app/src/outbox_policy.rs`, `run_outbox.rs`). `OutboxPolicy` is a pure `ArtifactClassifier` over name, detected type, and size: two fixed rules above every row (an executable by content or by extension — the slice-2 Windows allowlist plus `sh`, `ps1`, `msi` — is `Executable`; Markdown is `PortableText`), then the project's rows, then the shipped defaults (the sixteen heavy types → `GeneratedHeavy`; plain text with a source/configuration extension at or under 1 MiB → `GitTracked`); a project row routing Markdown to `generated-heavy` or an executable type anywhere but `executable` is refused when the policy is built (HAP-001-R2, R4 — the owner-approval record R4 admits is not modeled, so every such row is refused). `OutboxPolicyStore` loads it; `validate_outbox_declaration` decides `Present(canonical)`, `Missing(joined)`, or `OutsideProject`/`IsLink` (→ `outbox-invalid`) / `NotADirectory`/`Unreadable` (→ `outbox-unavailable`); `RunOutboxPreparer::{open_outbox, prepare}`, `CandidateProber::probe`, and `OutboxInventory::{inventory, open_subdirectory}` are the ports; `assemble_run_candidates`/`assemble_unattributed_candidates`, `cap_held_handles` (the D22 cap the shell applies across the active workspace's remembered runs, D6 below), and `summarize` are the pure services; `DirectoryHandle` and `RegularCandidate::handle` keep the live `std::fs::File`s in `omnifrons-app`, as `ExecHandle` already does. `LaunchPlan` gains `output_dir: Option<PathBuf>` and `declare_output_dir`, which also records an `EnvPlan` assignment (below). Contract tests for the preparer and the prober live in `omnifrons_app::contract::run_outbox` and run against the filesystem implementations from the adapters' tests; no in-memory fake exists for these ports, because a fake filesystem would prove nothing the contract cares about.
- **D3 — environment assignments** (`crates/omnifrons-app/src/harness_adapter.rs`, `crates/omnifrons-supervisor/src/lib.rs`). `EnvPlan::Allowlist` now carries a struct payload: the allowlisted `keys` plus product-set `assignments` (`EnvPlan::assign`, which refuses a secret-shaped key exactly like a declared one). `apply_env` — still the single place that ever sets a variable on a child — sets an assigned key from the assignment and never from the parent environment, and every other allowlisted key from the parent as before (HAP-001 D4). The built-in descriptors' `declared_env` lists stay empty: an allowlisted key is *resolved from the parent*, which is exactly what D4 forbids for this key, so "both adapters declare it" is realized as the shell declaring it on every adapter plan (HAP-001-R9 binds every adapter launch plan), not per descriptor. Proven by the re-exec pattern slice 3 established: the inner run's environment carries `OMNIFRONS_OUTPUT_DIR=planted-value-not-a-directory` through `Command::env` (never `set_var`), and the child still writes into the declared directory (`crates/omnifrons-supervisor/tests/outbox_launch.rs`).
- **D4 — the filesystem adapters** (`crates/omnifrons-adapters/src/fs_run_outbox_preparer.rs`, `fs_candidate_prober.rs`, `fs_outbox_inventory.rs`, `json_outbox_policy_store.rs`; dependency tables unchanged, `tests/deps.rs` as is — `openat`, `mkdirat`, `O_NOFOLLOW`, `O_DIRECTORY` are all gated by `nix`'s `fs` feature this crate already enables, verified against the vendored 0.31.3 source). `FsRunOutboxPreparer::prepare`: validate the declaration, create the outbox when missing (`create_dir_all`, then re-validate), open it `O_RDONLY | O_DIRECTORY | O_NOFOLLOW | O_CLOEXEC`, `mkdirat(outbox_fd, run_id, S_IRWXU)` — `EEXIST` on any existing name, a dangling link included, is `AlreadyExists` — then `openat(outbox_fd, run_id, O_DIRECTORY | O_NOFOLLOW)`, `fchmod` to `0o700` through that handle so a permissive umask cannot widen what `mkdir` created, and **verify by handle**: the handle opened relative to the outbox and a handle opened `O_NOFOLLOW | O_DIRECTORY` at the exact path the harness will be given must have the same `(dev, ino)`, be a directory, and have mode `0o700`; the declared path is `<canonical outbox>/<run id>`. One POSIX residual is disclosed rather than closed: there is no atomic create-and-open for directories, so between `mkdirat` returning and the `openat` that follows a same-user process can remove the created directory and place a *different directory* at the name (`O_NOFOLLOW | O_DIRECTORY` refuses a link or a non-directory there, not another directory); what the verification proves is that the directory the harness is pointed at is the one whose identity that first `openat` captured — owner-only, a real directory, the same file the declared path names — not that no same-user swap happened before it (TM-001 A6, the residual HAP-001 § Run subdirectories and attribution already declines to pretend away and the reason attribution rests on the run's own digest-naming proposal rather than on location). `FsCandidateProber::probe`: `openat(dir_fd, name, O_RDONLY | O_NOFOLLOW | O_CLOEXEC | O_NONBLOCK)` — `ELOOP` (a link) → `outbox-escape` without dereferencing, `ENXIO` (a socket) → `outbox-escape`, `O_NONBLOCK` so a FIFO with no writer opens immediately and is then refused from `fstat` rather than blocking forever — `fstat` on that handle for regular-file, `nlink` (> 1 → `outbox-linked`), then one streaming read for the digest and the 512 sniffed bytes, and the handle rewound and returned for the approval that follows. `FsOutboxInventory` lists names with `std::fs::read_dir` (this crate enables neither `nix::dir` nor any other listing API) and opens every name relative to the held handle, so a directory swapped at the path after the handle was opened can only contribute names that then fail to open there; `open_subdirectory` is another `openat(O_DIRECTORY | O_NOFOLLOW)`. `JsonOutboxPolicyStore` reads `.omnifrons/asset-policy.json` — JSON with a `schema` integer, the approval store's own discipline (versioning-and-compatibility.md names no format for portable configuration) — through a 1 MiB bound (`POLICY_MAX_BYTES`, checked on the handle's reported size and again on the bytes actually read, so a file that grows between the two is still refused before a byte is parsed; `PolicyError::TooLarge`, reported as reason `policy-invalid`); absent is the default policy, and anything else that does not parse exactly — unknown field, unknown token, another schema, a raw path, a rule violation — fails the load (HAP-001-R40).
- **D5 — Windows** (cross-compiled, never executed here). The outbox and the run subdirectory are opened with `FILE_FLAG_BACKUP_SEMANTICS | FILE_FLAG_OPEN_REPARSE_POINT` (a reparse point opens as itself and is refused; both constants verified against the vendored `windows-sys` 0.61.2 rather than assumed, and named locally so the crate adds no dependency); creation is `CreateDirectoryW` via `DirBuilder`, `ERROR_ALREADY_EXISTS` on any existing name; a candidate is opened by its joined path with `FILE_FLAG_OPEN_REPARSE_POINT`. Three residuals are disclosed under HAP-001-R19 rather than closed: the created directory is not relative to the outbox handle (no `mkdirat`); the by-handle identity comparison and the link count are not read, because `std::os::windows::fs::MetadataExt`'s by-handle accessors are unstable (`windows_by_handle`) and no Windows API crate was added — so `outbox-linked` cannot be produced on Windows, and "verify by handle" there means only that the declared path opened as a real directory that was not a reparse point; owner-only permissions are not expressed (ACLs are outside `std`). The unix tests that need a symbolic link, a hard link, or a FIFO are gated per test with the reason stated.
- **D6 — the shell** (`src-tauri/src/outbox_state.rs`, `src-tauri/src/ipc/{commands,dto}.rs`). `harness_spawn`'s `kind: "adapter"` mints a run id (`run-<seconds>-<nanoseconds>-<sequence>`, the sequence a process-wide atomic rather than any table's counter, so two ids minted in one process differ even at identical seconds and nanoseconds — Windows's `SystemTime` has 100 ns resolution and no sub-second guarantee, which is how CI once minted two identical ids), and on the blocking thread loads the policy, prepares the run subdirectory, declares it on the plan, and only then spawns — `launch_with_run_subdirectory`, one plain function (prepare, declare, spawn) the tests drive with a fake spawn; a policy that cannot be loaded, an invalid declaration, a pre-planted path, or a failed verification refuses the launch with `outbox-unavailable` before anything is spawned (HAP-001-R10, D14), and if the declaration or the spawn fails the empty subdirectory just created is removed again — only while still empty: `remove_dir` refuses a non-empty directory, so nothing a same-user process dropped in after creation is ever deleted (both failure branches and the non-empty case are tested). The run's record — the prepared subdirectory with its held handle, the policy in force, the proposals — lives in a bounded `RunTable` (64 records, oldest evicted, its handles released; the entries stay in the outbox for the next whole-outbox inventory). The forwarder's `AdapterWireSequencer` carries a `RunEndTracker`: every `ArtifactPublish` event passing through is recorded — up to `MAX_PROPOSED_ENTRIES` (1024) proposed entries per run, a spike default HAP-001 does not name: a proposal crossing the cap keeps its first entries up to the remaining slots, and every entry beyond is counted, never silently dropped — and the raw `State` frame produces the tracker's run-end events *before* the terminal `state` frame — one `diagnostic` for the counted excess when there is one, then one `diagnostic` per recorded proposal naming a digest no entry carries (name and short digest only), then one `candidates` summary — so `state` stays the last frame and `seq` stays contiguous, with the raw frame's `droppedBefore` on the first of them. The inventory runs on a duplicate of the held handle outside the table's lock, and the candidates are stored on the record through `RunTable::store_candidates`, which is where HAP-001 D22's cap is enforced — **per active workspace within a shell session**: at most 32 handles held across every remembered run of the workspace, counted under the table's lock against every other run's held handles, the excess released in inventory order while the entries stay `candidate` (a second run ending after a first that holds 20 keeps 12); a record evicted from the bounded table (64) releases its handles with it, and `workspace_pick` of a *different* workspace clears the whole table (`OutboxState::forget_runs`, through the pure `activate_workspace`), so a previous project's runs never count against the next one's budget, while re-picking the active workspace keeps them. Nothing else holds a candidate handle, so 32 is the whole-shell bound. The inventory's two phases run under two lock scopes (`RunEndTracker::snapshot`, then the hashing outside the lock, then `RunTable::store_candidates`); if the record was evicted or forgotten in between, the table hands the candidates back, their handles are released explicitly, and one `diagnostic` names the run id and how many candidates were not retained — the loss is never silent. A PTY launch has no line parser and therefore no proposals: its inventory is entirely unattributed, as HAP-001 § Run subdirectories and attribution says. `outbox_status` and `candidates_list` are the two new commands; `ShellErrorCode` gains `outbox-invalid` and `outbox-unavailable`.
- **D7 — the fixture** (`crates/omnifrons-supervisor/src/bin/fake-agent.rs`). `--report-output-dir` (`output-dir set=<bool> writable=<bool>` then `env-keys ...`, names only), `--write-outbox <n>` (n heavy files cycling PDF, PNG, ZIP by magic, plus `notes.md` and an ELF-headed `tool.bin`, then one `artifact.publish` `tool_use` naming every even-indexed heavy file by digest), `--propose-missing` (adds `ghost.pdf`, never written), `--plant-link` (`outside.bin` at the outbox root, then `escape-link` and `linked.bin` inside the run subdirectory). The digests come from a minimal hand-rolled SHA-256 inside the fixture — pinned to FIPS 180-4's test vectors in its own unit tests and checked against the real hasher in `tests/outbox_launch.rs` — so the supervisor's normal dependency set stays unchanged, the same reasoning as slice 3's hand-built JSON; `sha2` joins the supervisor's `[dev-dependencies]` only for that check.

### Evidence procedures

#### Procedure notes for VP-S22

[HAP-001's proposed VP-S22](heavy-asset-publication.md#desktop-stack-verification-planmd) (outbox publication end to end) cannot run against this slice — nothing publishes — but its first half now has a dev-mode analogue worth carrying into the procedure once a packaged build exists: launch an adapter whose executable is `fake-agent --write-outbox 3`, confirm the `artifact-publish` event names `artifact-0.pdf` and `artifact-2.zip` by digest, and confirm the `candidates` event at run end reports two attributed and three unattributed entries (`artifact-1.png`, `notes.md`, `tool.bin`) with `candidates_list { runId }` showing `notes.md` as `portable-text` and `tool.bin` as `executable`, never `generated-heavy`. The digest in every `candidate` row must equal the digest of the file's bytes read independently; the record digest equality VP-S22 asks for is then the same fact one step later.

### Deviations and debt

Deviations from the brief, each with its reason:

- **`OMNIFRONS_OUTPUT_DIR` is not in the descriptors' `declared_env`.** The brief asked for the key "through the existing allowlist" and for both adapters to declare it. An allowlisted key is resolved from the parent environment, which HAP-001 D4 forbids for this key, so the plan gained product-set assignments instead, the key joins the allowlist through `EnvPlan::assign`, and the shell declares it on every adapter plan; a descriptor-level declaration would have let the parent's value through on any plan the shell did not assign. Every adapter kind, including `pty-cli`, gets the declaration.
- **A new wire kind, `artifact-publish`, beyond the brief's `candidates`.** D5 says the line agent recognizes the proposal; a recognized proposal is a typed domain event, and the wire must carry it somehow — as its own kind rather than folded back into `tool-call`, so the renderer can show the entries by digest and the shell never parses JSON out of `argumentsText` a second time. A malformed `artifact.publish` still surfaces as the plain `tool-call` it is.
- **`outbox_status` carries more than the brief's three fields** (`declared`, `exists`, `reason` added; `outbox` null unless valid and existing): the brief's `outbox: displayPath` cannot honestly show a device path for a declaration that failed validation, and a fresh project's default outbox does not exist until the first launch, which a renderer must be able to say.
- **A policy that cannot be loaded is `outbox-unavailable` at launch and `outbox-invalid` at `candidates_list`.** HAP-001-R10 says an `outbox-invalid` outbox renders `outbox-unavailable` at launch; R8 says a failed declaration blocks ingestion as `outbox-invalid`. Both mappings are implemented, one per surface.
- **An unreadable entry is excluded and counted, not rendered `outbox-escape`.** HAP-001's escape row names a link, a non-regular file, and an escaping path; an entry that could not be opened at all (`EACCES`, vanished between listing and open) is none of those, so it is excluded from the candidates and counted in the `candidates` summary's `unreadable`.
- **The whole-outbox inventory holds no handles.** HAP-001-R17's held handle exists for the approval that follows; the session-start inventory proposes and nothing follows in 5a, so its handles are released and 5b re-opens each entry under R15 when its turn comes. The run-end inventory does hold handles, capped at 32 (D22), with the excess kept `candidate` without one.
- **The outbox is created by the first launch, not by `outbox_status`.** A status query is read-only; `open_outbox(create_if_missing)` is the one place that creates it, and a fresh project reports `valid` with `exists: false`.
- **`sha2` joins the supervisor's dev-dependencies** so the fixture's hand-rolled SHA-256 is checked against the real hasher; the normal dependency tree (`cargo tree -p omnifrons-supervisor -e normal --depth 1`) is unchanged.
- **`--propose-missing` is a fixture flag the brief did not list**, for the unmatched-proposal diagnostic; the brief's `--write-outbox <n>` cycles three heavy kinds and always adds the note and the executable-shaped file, and its proposal names the even-indexed heavy files.
- **No end-to-end `harness_spawn` test, and what else is not exercised.** As in slices 3 and 4, a Tauri command cannot be driven from a unit test; the chain is proven in pieces — the fixture and the environment through `spawn_approved` (`tests/outbox_launch.rs`), the preparer and prober through the contracts and `tests/outbox_fs.rs`, the launch sequence through `launch_with_run_subdirectory` with a fake spawn, the tracker, status, whole-outbox inventory, and `candidates_for_run` through the shell's unit tests with a fake adapter that emits a real `ArtifactPublish`, and the error mappings directly. Stated in full, what no test exercises: `fake-agent`'s proposal line flowing through `LineAgent::parse_line` into the tracker in one test (the parse is tested on the same JSON shape the fixture emits, and the tracker on the typed event a fake adapter emits); `harness_spawn`, `outbox_status`, `candidates_list`, and `workspace_pick` as Tauri commands (only their pure bodies — `launch_with_run_subdirectory`, `outbox_status_for`, `inventory_whole_outbox` and `candidates_for_run`, `activate_workspace` — are tested); `forward_adapter_output`'s thread body wiring the `RunEndTracker` and sequencer (both are tested directly); a live shell's run-record eviction releasing handles (tested at the table level only); the growth-between-size-check-and-read half of the policy bound (the size check and the exact-cap boundary are tested, a file growing during the read is not); the `mkdirat`→`openat` window and any other real swap race (not reproducible deterministically; disclosed as residuals); every Windows code path (cross-compiled, never executed, including the reparse-point opens) and every macOS execution (CI only, including `EOPNOTSUPP` on a socket — the socket fixture binds at a short path under the temp directory and renames the entry into the run subdirectory, because the macOS temp path plus the run subdirectory exceeds `sun_path`'s 104 bytes; the assertion was shown load-bearing on Linux by removing the prober's socket arm and watching the test fail with `Unreadable`); and the `remove_dir` refusal on a subdirectory made non-empty by a *different* process (tested with a file the test itself writes into it).
- **A per-run cap of 1024 proposed entries** (`MAX_PROPOSED_ENTRIES`) and the enforcement of D22's 32 held handles across the remembered runs of the active workspace within a shell session (the table is cleared when the workspace changes) are spike defaults HAP-001 does not spell out (it names the 32 per project and says nothing about proposal volume or about what "project" means to a shell that can change workspace); both are disclosed here rather than presented as decided.
- **A `Duration` fixture instant is one second off a round hour** in `outbox_state.rs`'s test, so clippy's `duration_suboptimal_units` stays quiet without an allow.

Debt and open owner decisions this slice names without deciding:

- **The product work area (HAP-001-R7, D1)** is not implemented: nothing in 5a writes a recovery entry or a journal, so the check has no use site; 5b must add it with the canonicalize-and-re-check-at-every-use discipline, and the VP-S26 cases that exercise it.
- **Windows residuals** (D5): no by-handle identity comparison, no link count, no owner-only permissions, no `mkdirat`; `outbox-linked` cannot be produced there. Closing them means a Windows API dependency for `GetFileInformationByHandle`, which the owner has not been asked for.
- **The POSIX `mkdirat`→`openat` window** (D4): no atomic create-and-open for directories exists, so a same-user process can swap a different directory in before the first open; the verification proves that the harness is pointed at the directory whose identity that first open captured, not that no such swap happened — TM-001 A6's same-user residual, disclosed here next to the Windows ones rather than claimed closed.
- **Quarantine-flag detection** is not implemented: HAP-001-R4 identifies an executable by extension list, magic bytes, *and* the platform's quarantine flag where one exists (macOS's `com.apple.quarantine` extended attribute, Windows's `Zone.Identifier` alternate data stream); this slice reads extension and magic bytes only, so a downloaded file carrying only the flag classifies by its content and name. Debt for 5b or a later slice.
- **The listing is path-based** (`read_dir` on the directory's path) while every open is handle-relative; a handle-relative listing needs `nix`'s `dir` feature or `fdopendir` and was not added.
- **Display names are not sanitized** (HAP-001-R24 is 5b): `CandidateDto.name` is producer-supplied text and the renderer must treat it as plain text only, as it already does for every other harness-originated string.
- **The `candidates` event delays the terminal `state` frame** by the time the run subdirectory takes to hash; on a run that wrote very large files the renderer sees `state` late. A bound on inventory time, or an asynchronous inventory with `state` first, is a later decision.
- **A run record evicted from the bounded table** (64) releases its handles and forgets its proposals; its entries are then found by the next whole-outbox inventory as unattributed. HAP-001-R28's retention-by-digest of a refused entry is 5b.
- **`RunId` minting is time-plus-sequence**, unique on one device for the product's lifetime; whether the run id should be the Catalog's run identity (AEC-001's `run_id`) is AEC-001's decision.
- **HAP-001 D3, D5, D12, D16, D17, D18, D19, D20, D22** remain the owner's calls; this slice assumes D17's default path, D20's one-level layout, D22's cap of 32, and D14's block-the-launch, and says so here rather than presenting them as decided.

see the deviation below), R7 (the work area: created owner-only, canonicalized and checked at open, re-canonicalized and re-checked against the active workspace root at every use — every journal write, every recovery-entry write — and refused as `work-area-invalid` when it resolves inside or at that root), R13–R18 and R20–R21 as the transaction states them, R22 (approval by explicit user action naming the candidate by run id, name, and digest; the surface facts identity-bound; unattributed entries approved the same way; refused, unclassified, and non-heavy entries not approvable), R23 (publication identity `sha256(project identity ‖ content digest)`, a repeat → `duplicate-publication` with the existing record acknowledged and the display name added as an alias, never a second copy or record), R24 (every Catalog record field HAP-001 lists, names sanitized, the reference issued only once `registered`), R26 (the state tokens are exactly the signal mapping's), R28 (removal only after the published copy and the record are verified, and only while the path still names the handle's file; every deferral journaled), R29 (a step journaled before the next runs; a `published-local` without a registration resumed from the record the journal carries; nothing repeated; no handle survives a restart, so the entry's removal is deferred and said so), R35 (one `artifact-state` frame per transition, in order), R36 (provenance: scope, producer as the run with its adapter id and executable approval or `unattributed` with the run subdirectory as a location fact, and the UTC time of every transition), R14 for the device asset path (re-canonicalized and re-checked against the active workspace at every publication → `destination-invalid`), R17's cap re-open (a candidate remembered without a held handle is re-opened once, no-follow, relative to the outbox handle, and refused when its facts changed), and R34/R37 as "not applicable": the local-directory adapter holds no credential.

Out, named as debt below: provider upload and `provider-synced` (R25, R30), `over-limit` (R31), the secret scan (R41), per-device availability inside the portable record (R27; this device's observation is reported from its own journal instead), the whole-outbox entries' approval (only a remembered run's inventory is approvable in this slice), the re-publication of a recovery entry, the vault as a containment root (no vault exists in this repository; the checks run against the active workspace root), and a device identity.

### Design decisions (spike defaults, each disclosed)

Every default below is the spike's; a feature that assumes it before the owner disposes must say so, and this section does.

- **D1 — domain types** (`crates/omnifrons-domain/src/publication.rs`). `ProjectIdentity(Sha256Digest)` and `PublicationIdentity(Sha256Digest)`, with `publication_identity_preimage(project, digest)` the exact 64 bytes `project ‖ digest` HAP-001-R23's derivation hashes (no domain tag: the brief's formula, followed literally); `AssetRootId` (one token of `[A-Za-z0-9_-]{1,64}`, the run id's shape, so it names a device directory without a second validation); `CatalogId { asset_root_id, publication_id }` rendered `<asset root id>/<publication hex>`; `ProviderLocator` (opaque); `ProviderState::{Pending, Synced, Failed, Unavailable}`; `ArtifactState` — the ten tokens this slice can put on a surface, spelled as the signal mapping spells them (`candidate`, `published-local`, `registered`, `provider-synced`, `registration-pending`, `refused`, `integrity-mismatch`, `duplicate-publication`, `outbox-escape`, `outbox-linked`) and nothing else (HAP-001-R26); `DisplayName::sanitize` (RCS-001's file-name rule as this slice reads it: split on `/` and `\`, drop empty, `.`, and `..` components and join the rest with `_`; strip every C0/DEL control and the bidirectional override, embedding, and isolate characters U+202A–U+202E and U+2066–U+2069; cap at 255 bytes on a character boundary; trim trailing dots and spaces; prefix a Windows reserved device name — `CON`, `PRN`, `AUX`, `NUL`, `COM1`–`COM9`, `LPT1`–`LPT9`, with or without an extension, any case — with `_`; an empty result becomes `unnamed`); `CatalogRecord` with HAP-001 § Catalog record's fields (`publication_id`, `catalog_id`, `class`, `detected_type`, `size`, `digest` carried with the algorithm id `sha256` — D13 — `names`, `relationships` (empty in this slice), `provenance { scope_id, producer, transitions }`, `provider { adapter_id, locator, confirmation_kind, state, reason }`, `state`, `record_version` = 1); `Producer::{Run { run_id, adapter_id, executable_approval } | Unattributed { found_under }}`; `PortableReference` (AEC-001's `ref`: kind `artifact`, id the publication identity, locator the Catalog identity; `CatalogRecord::reference()` is `Some` only for a `registered` record, HAP-001-R24); `ArtifactApproval` (every identity-bound fact the surface shows, the destination asset root, the launch's adapter id and executable approval when the run record kept them, and `DeviceLocalUser` as the act-as identity) with `ArtifactApprovalId(u64)` derived from `sha256("omnifrons-artifact-approval-v1" ‖ publication identity ‖ nanos-since-epoch as big-endian u128)`'s first 8 bytes and carried on the wire as 16 hex characters (a `u64` does not survive a JSON number's 53-bit mantissa); and the journal's shapes `JournalEntry::{Approved(Box<ArtifactApproval>) | Step(Box<StepEntry>)}`, `StepEntry { publication_id, approval_id, step, outcome, digest, reason, at, record, recovery }`, `JournalStep` (`published-local`, `registered`, `registration-pending`, `cleanup`, `refused`, `outbox-escape`, `outbox-linked`, `integrity-mismatch`, `duplicate-publication`), `StepOutcome::{Ok, Failed, Deferred}`.
- **D2 — application ports and the transaction** (`crates/omnifrons-app/src/{content_hasher,work_area,blob_store,catalog_store,publication_journal,outbox_entry_ops,publication}.rs`). `ContentHasher { sha256, digest_reader }` exists because this crate depends on `omnifrons-domain` and `thiserror` only; the three derivations live beside it, and the **project identity is a spike default**: `sha256("omnifrons-project-v1" ‖ the workspace root's canonical path bytes)` stands in for the registered scope identity context-orb.md and RSP-001-R13 own, which this repository does not have — HAP-001's cross-project separation rests on that identity being non-forgeable, and a path digest is not that. `WorkAreaRoot::open(configured, workspaces)` refuses a configured path whose projected canonical form is or lies under a registered workspace root before creating anything, creates the area and `journal/` and `recovery/` owner-only (unix `0o700`, set explicitly after `DirBuilder::mode` so a permissive umask cannot widen it), canonicalizes, and `check(workspaces)` re-canonicalizes and re-compares at every use (a vanished area is `Unusable`, never a stale pass). `DeviceAssetPath::open` does the same for an asset root's device directory (HAP-001-R14). `BlobStorePort` is HAP-001's `BlobStorePort` reduced to this slice: `capabilities()`, `stage(identity) -> StagedObject` (a sink the transaction streams the held handle into, then `commit() -> locator` or `abort()`), `open_published(locator)` for HAP-001-R21's read-back, `discard(locator)` for the copy that fails it, and `confirm(locator)` for the observation that would yield `provider-synced`. The brief named `publish(handle, identity) -> locator`; the port hands the transaction a sink instead so the copy and its digest are **one pass in the application layer** — the bytes leave the outbox exactly once, from the held handle, through a `Tee` that hashes exactly what it writes — and the adapter never sees a path or a handle. `CatalogStore { list, find, register, add_alias }` and `PublicationJournal { append, replay }` with the pure replay queries (`find_approval`, `resume_point`, `pending_registrations`); `OutboxEntryOps { identity, unlink }` with `EntryIdentity::{SameFile, DifferentFile, Missing, Unverifiable}`. `publication::publish(ports, approval, source, on_state)` is the transaction: work-area check → journal replay → `catalog.find` (an existing record → alias when the name differs → journal `duplicate-publication` → `DuplicatePublication { existing }`) → resume point (a journaled `published-local` whose copy still verifies skips the copy; one that no longer verifies, or a `registered` step whose record is gone from the Catalog, publishes again from the held handle) → `fstat` on the held handle (not regular → `outbox-escape`; link count above one → `outbox-linked`, unix only) → `entry_ops.identity` (`DifferentFile` or `Missing` → the held bytes written to `recovery/<digest hex>` owner-only via a temporary name, journal `outbox-escape` with the recovery digest, `OutboxEscape { recovery }`; `Unverifiable` proceeds, the disclosed Windows residual) → `stage` + the tee copy (a streamed digest or size unequal to the approval's → `abort`, `integrity-mismatch` reason `source-digest-changed`) → `commit` → read-back (`open_published` hashed again; unequal → `discard`, `integrity-mismatch` reason `published-copy-digest-differs`) → the record built with `provider_state: pending` and the adapter's own reason → journal `published-local` with the record → `register` (a `Duplicate` from the store is idempotent; any other failure → journal `registration-pending`, state `registration-pending`, no reference, cleanup deferred) → journal `registered` → cleanup (`identity` again: `SameFile` → `unlink` → journal `cleanup ok`; anything else → journal `cleanup deferred` with the reason `entry-changed-after-publication`, `entry-missing`, `identity-check-unavailable`, or `unlink-failed`). Every failure journals its step and emits its state before returning; `on_state` receives `StateEvent { publication_id, state, provider_state }` per transition. `recover(ports, project, on_state)` replays the journal, and for every publication of `project` whose resume point is `published-local` re-verifies the copy and registers the journaled record (journal `registered` reason `resumed-after-restart`, cleanup `deferred` reason `no-handle-after-restart`) or, when the copy no longer verifies, journals `integrity-mismatch` reason `published-copy-unverifiable-after-restart` and leaves the retained entry for a fresh approval; a completed step is never repeated. The fakes and contracts behind `contract-tests` (`contract/publication.rs`): `FakeHasher` (deterministic, not cryptographic), `InMemoryBlobStore` with `corrupt_next_commit`, `InMemoryCatalogStore` with `fail_next_register`, `InMemoryJournal`, `ScriptedEntryOps`, and `catalog_store_contract`/`publication_journal_contract`/`blob_store_contract`.
- **D3 — the adapters** (`crates/omnifrons-adapters/src/{sha2_hasher,local_dir_blob_store,jsonl_catalog_store,jsonl_publication_journal,fs_outbox_entry_ops,catalog_record_dto}.rs`; dependency tables unchanged, `tests/deps.rs` as is — `fstat`, `fstatat`, and `unlinkat` are gated by `nix`'s `fs` feature this crate already enables, verified against the vendored 0.31.3 source: `sys::stat` is a `feature = "fs"` module, `unistd::unlinkat` sits inside the `fs` block that opens at `unistd.rs:1478`, `fcntl::AtFlags` is gated by `fs`, `process`, or `user`). `Sha2Hasher` is the real SHA-256. `LocalDirBlobStore` — **the first and only provider adapter, dev-mode only**: adapter id `local-dir`, `publish_mode: copy`, `confirmation_kind: "no remote"`, no object limit, quota unknown, no native placeholder; the copy is written to a per-call staging name `<device asset path>/.<publication hex>.<pid>-<sequence>.part` (owner-only, `create_new`, so two stages of one identity never share a file; a staging file a crash leaves between `stage` and `commit` is not removed by the adapter — disclosed, a sweep is 5c debt) and renamed to `<device asset path>/<publication hex>` on commit, a second commit of the same identity replacing the copy (what a retry after an interruption needs); the locator is `local-dir:<asset root id>/<publication hex>`; `confirm` is always `None`, so a publication through it is `registered` with `provider_state: pending` and the adapter's reason `no remote`, never `provider-synced`; a locator this adapter did not issue — another adapter's, another asset root's, anything that is not exactly 64 hex characters after the prefix — is `ForeignLocator`, never resolved to a path; credentials: none, HAP-001-R34 and R37 not applicable. `JsonlCatalogStore` — **D9's default**: `.omnifrons/catalog.jsonl` under the project (HAP-001 names no file; `catalog.jsonl` is the spike's), one line per event (`record` on registration, `alias` when a later identical publication adds a display name), each with `schema: 1`; a line that does not parse exactly, another schema, an alias naming no record, or a record whose ids disagree fails the whole read as `Corrupt`; an absent file is an empty catalog and a read creates nothing; every display name is re-sanitized on read, because a file under `.omnifrons/` is portable, synchronized, untrusted content (HAP-001-R40). `JsonlPublicationJournal` — `<work area>/journal/publications.jsonl`, created `0o600` on unix like the slice-2 store, one line per entry (`approved` or `step`, `schema: 1`), `sync_data` before `append` returns, a corrupt line or another schema fails the whole replay. `FsOutboxEntryOps` — unix: `fstat(handle)` against `fstatat(dir, name, AT_SYMLINK_NOFOLLOW)` relative to the held directory handle, the same file exactly when device and inode agree, a link at the name compared as itself and never followed, `ENOENT`/`ENOTDIR` → `Missing`, any other error → `DifferentFile` (what cannot be confirmed is not the same file); `unlinkat(dir, name)` without `AT_REMOVEDIR`. Windows: `Unverifiable` and `unlink` unsupported — the transaction publishes from the handle and defers the removal with reason `identity-check-unavailable`, disclosed under HAP-001-R19 rather than closed (`std`'s by-handle identity is unstable and no Windows API dependency was added, as 5a found). The policy store reads `assetRootId` (below).
- **D4 — the shell** (`src-tauri/src/{publication_state.rs, ipc/publication.rs, ipc/dto.rs, outbox_state.rs}`). **D1's default location**: the work area is `<app_local_data_dir>/work-area` (`journal/` and `recovery/` under it, and nothing else in this slice); the asset roots — **D8's per-OS default, derived and never written down** — are `<app_local_data_dir>/asset-roots/<asset root id>`; both sit in the same application-data directory as the slice-2 approval store and RCS-001-R10's quarantine, are re-checked against the active workspace at every use, and never cross IPC. **The asset root identity comes from the project policy**: `.omnifrons/asset-policy.json` gains an optional `assetRootId` (one token, never a path; a raw path or a traversal is `policy-corrupt` at load); a project that declares none has no destination and every approval fails `destination-invalid` — HAP-001-R6's `destination-unconfigured` folded into that code in this slice, because the asset binding the scope will carry does not exist yet. **Approval** (`approve_candidate`): the candidate is looked up in the remembered run's run-end inventory by its listed name; a state other than `candidate`, a digest that does not match the request, or a class other than `generated-heavy` is `refused`; the approval carries the run record's adapter id and executable approval when the launch kept them (`RunRecord::with_provenance`, which `harness_spawn`'s `kind: "adapter"` now uses); the derived id is checked against the journal and a collision — the same publication approved at the same nanosecond — is `invalid-request` rather than a second line (the slice-2 store's duplicate discipline); the approval line is the journal's first entry for the publication, so **the approval store is the journal**. **Publication** (`publish_approved`): the approval is found in the journal, must belong to the active project (`invalid-request` otherwise, with nothing of the other project's touched), is acknowledged as `duplicate-publication` from the Catalog alone when its identity is already registered — before any entry is touched, so a repeat of a completed publication whose entry was removed is a duplicate, never `refused` (`publication::acknowledge_registered`) — and otherwise its bytes come from the run record's held handle (`RunRecord::take_candidate_handle`, the transaction becoming the handle's owner) or, when the record holds none — the D22 cap released it, or the record was evicted — from one no-follow open relative to the outbox and run-subdirectory handles (`FsRunOutboxPreparer::open_outbox`, `FsOutboxInventory::open_subdirectory`, `FsCandidateProber::probe`) whose digest, size, and detected type must equal the approval's, else `refused` (`identity-facts-changed-at-re-open`), with `outbox-escape` and `outbox-linked` for a probe that says so, and `refused` for an entry that cannot be re-opened; then `DeviceAssetPath::open` for the approval's asset root (HAP-001-R14), the local-directory provider, the project's Catalog, and the transaction; every `StateEvent` is sent as an `artifact-state` frame over the command's `onState` channel — the `harness_spawn` pattern — and a renderer that went away is not a failure. **Restart replay**: `recover` runs at the start of `publications_list` and the pure body of `artifact_publish` consults the same resume point, so an interrupted publication resumes at the first command that touches publications after a restart rather than at process start (no workspace is active at start, and the Catalog is the project's); `publications_list` then lists the Catalog's records with this device's own availability (`local` when this device's journal shows `published-local` verified here, `unknown` otherwise — HAP-001-R27 observed, never inferred from the record) plus any `registration-pending` recovery could not complete. `ShellErrorCode` gains nine values (`run-active` arrived with the renderer risk review); `ShellErrorDetail` becomes an untagged enum so `duplicate-publication` can acknowledge the existing record's ids without changing the slice-2 detail's shape. **Concurrency** (R1-001): `PublicationState` carries the publication surface lock, held across the whole of `approve_candidate`, `publish_approved`, and `publications_for`, so the Catalog's replay-then-append is never interleaved and two publications of one identity racing each other yield exactly one `registered` and one `duplicate-publication` (proven with two threads against the real adapters; before the lock both threads registered and the Catalog read `Corrupt` afterwards); with one active workspace per shell, one lock is the per-project lock HAP-001-R23 needs, and a second shell process against the same journal is not serialized by it (no single-instance guard exists, as slice 2 records). A `Corrupt` catalog stays fail-closed (`catalog-unavailable`) and is repaired by hand for now — the offending line removed, every other kept, as `jsonl_catalog_store.rs`'s module doc spells out — with a `catalog_repair` command named as 5c debt. **Every workspace registration re-checks the work area** (R1-002, HAP-001-R7): `activate_workspace` and `workspace_current` run `WorkAreaRoot::check_configured` (a projected-canonical containment check that creates nothing) and report the outcome as `WorkspaceDto.workArea` (`valid` | `work-area-invalid`); the registration itself proceeds — the operation R7 refuses is the work area's use, which every publication command re-checks again.

### Deviations and debt

Deviations from the brief, each with its reason:

- **Eight `ShellErrorCode`s, not four.** The brief named `integrity-mismatch`, `duplicate-publication`, `work-area-invalid`, and `destination-invalid`. `outbox-escape` and `outbox-linked` are needed because a publish-time identity or link-count failure is neither of those and HAP-001-R18 and R20 forbid rendering them as `integrity-mismatch`; `refused` because an entry that cannot be approved, a mismatched digest, and a re-opened entry whose facts changed are HAP-001's `refused`, which the brief itself named as the outcome; `catalog-unavailable` because a corrupt or unwritable `.omnifrons/catalog.jsonl` is none of the others.
- **The approval store is the journal.** The brief asked for the approval "recorded (append-only JSONL under the work area, 0600)" and for the work area to hold "`journal/`, `recovery/`, and nothing else". Both hold: the approval is HAP-001's step 6 and is the publication journal's first entry for the publication. The derived id is checked against the journal before the line is appended.
- **`BlobStorePort` stages instead of copying.** The brief's `publish(handle, publication identity) -> locator` would have put the copy — and its digest — inside the adapter. The port hands the transaction a staged sink so the bytes leave the held handle exactly once, hashed as they go, in the application layer; a real provider adapter (5c) gets the verified local copy to upload from, which is what HAP-001's step 9 needs anyway.
- **`artifact.state` rides the command's channel.** The brief's "event kind on every transition" is a per-publish `Channel<ArtifactStateFrame>` argument, the `harness_spawn` pattern, rather than an application-wide event: testable without a runtime, and the transitions of a publication belong to the command that runs it. Recovery transitions at `publications_list` therefore have no channel and are journaled only.
- **The restart replay runs at the first publication command, not at process start.** No workspace is active at start and the Catalog is the project's, so `recover` runs when `publications_list` or `artifact_publish` is called for the active project — every completed step is still never repeated. Recovery cannot remove the outbox entry (no handle survives a restart) and says so in the journal; the entry is retained.
- **Only a remembered run's inventory is approvable** (`runId` is required). A whole-outbox entry (a root entry, or one under a run the table forgot) has no recorded facts to bind an approval to; approving it would mean probing at approval time and again at publish time. Debt for 5c.
- **`PublicationDto` carries `names` and `availability` beyond the brief's five fields**, and `approvalId` is a hex string rather than the slice-2 numeric shape: the names are the sanitized record names the renderer will show, availability is HAP-001-R27's per-device observation, and a derived `u64` id cannot round-trip through a JSON number.
- **`destination-unconfigured` is folded into `destination-invalid`.** The asset binding HAP-001-R6 refers to does not exist; a policy without `assetRootId` fails with a distinct fixed message under the same code.
- **The Windows residual widens.** Beyond 5a's list, the identity check before publication and before cleanup is `Unverifiable` on Windows: the copy still comes from the held handle and verifies, and the entry is retained with `cleanup deferred identity-check-unavailable`. Recorded under HAP-001-R19, not closed.
- **The duplicate's own entry is left in the outbox.** HAP-001-R23 says a repeat acknowledges the existing record; nothing in the contract removes the second entry, and this slice does not.
- **`WorkspaceDto` gains `workArea`** (R1-002), an additive field on a slice-3 shape, chosen over a diagnostic frame because `workspace_pick` has no channel and the state belongs to the workspace it was checked against.
- **A registered record's provenance is written only on success** (R3-002): the `registered` transition is pushed onto the record the Catalog writes, and a record returned `registration-pending` ends at `published-local`.
- **The publication surface is frozen while any supervised process runs** (renderer risk review R1-001, a spike default): `artifact_approve` and `artifact_publish` refuse with `run-active` while `TokioProcessSupervisor::running_ids` -- the same source `harness_stop` and `harness_observe` consult, each child refreshed through `observe`'s reap check -- is non-empty, and are open again once every run has reached its terminal state. The renderer freezes Approve and Publish while a run is active; without the backend mirror, direct IPC would bypass that guard, so one coherent frozen surface exists now. TM-001-R1's facts are re-verified by the transaction regardless of this guard, and the owner may relax it: publishing a finished run's candidates while another run streams is a legitimate future option.
