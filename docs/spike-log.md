## Slice 1 — supervisor to renderer streaming

### What it proves

That a demo child process's stdout and stderr can be captured by `omnifrons-supervisor`, framed, and streamed to a Tauri renderer over a typed `tauri::ipc::Channel`, end to end, on Linux, in a development build:

- A process spawned from a validated request (never a raw program path or argument vector) emits captured output frames in order, with a bounded delivery queue that drops under backpressure rather than blocking the producer, and reports the drop count on the next delivered frame.
- A line longer than the per-frame byte cap splits into consecutive frames with no bytes lost; invalid UTF-8 is lossily decoded rather than dropped or erroring.
- A process that ignores `SIGTERM` is still stopped, definitively, by escalating to `SIGKILL` within a bounded deadline.
- Every IPC error surfaces as a closed, typed error code with a fixed catalogue message, never the underlying OS error text (which can carry a real filesystem path).

Both `HarnessKind`s emit a leading `"ready"` stdout line before any `"line <n> out"` output, printed only once a `DemoIgnoresSigterm` process's `SIGTERM`-ignore handler is already installed (`DemoLines` prints it too, for symmetry, even though it installs no handler). A caller can subscribe to the process's output and wait for this line as a genuine synchronization point before calling `stop` against it, closing a handler-install race a fixed sleep could only ever paper over with a guess at "long enough" (`crates/omnifrons-supervisor/src/demo.rs`'s `run`; `crates/omnifrons-supervisor/tests/demo_harness.rs`).

### What it defers

- **Any acceptance claim.** This is a development-mode build on one contributor's Linux machine, not a packaged release build on a pinned baseline. See [Relationship to VP-001](#relationship-to-vp-001).
- **Windows and macOS.** The output-capture reader tasks and the demo harness are platform-generic (Tokio, `std::io`), but the final `State` frame is only ever sent once a reap is confirmed, and `omnifrons-supervisor`'s Windows stop path never confirms a reap yet (`repository-layout.md` § Crate map; pending VP-001 VP-S5, the Job Object policy). Windows output capture therefore never emits a terminal marker today — an inherited gap, not a new one.
- **Windows running-process cap is permanent, not recoverable.** Because Windows `stop` cannot confirm a reap (previous bullet), a stopped process's bookkeeping entry is never evicted from `Running` to `Terminal` there — stated plainly: on Windows, the 16-concurrently-running cap is reached for good once 16 processes have ever been spawned, and `spawn` refuses every one after that for the rest of that supervisor's lifetime, no matter how many of those 16 were actually stopped. This is a real limitation of this slice, not a test artifact — it stands until Job Object containment (VP-001 VP-S5) lands and Windows `stop` can confirm a reap like `unix::stop` does.
- **Any real harness.** `HarnessKind` names exactly two synthetic demo behaviors (`DemoLines`, `DemoIgnoresSigterm`); no user-supplied program, script, or arbitrary executable is reachable through this slice's IPC surface at all.
- **Malformed-payload fuzzing and reconnection/cancellation behavior.** This slice proves the happy path and the two edge cases above; it does not run the adversarial input corpus or renderer-restart scenarios [VP-S13](#procedure-notes-for-vp-s13) and [VP-S15](#procedure-notes-for-vp-s15) call for.
- **Drop-on-supervisor-drop.** If the supervisor itself is dropped without an explicit `stop` (a panicking caller, an early return), its existing best-effort `SIGKILL` cleanup still runs, but no final `State` frame is sent for any process still subscribed at that point — the output channel is simply abandoned. A future slice should decide whether that needs fixing or is an acceptable spike-only limitation.
- **Launcher identity re-probing.** `TokioProcessSupervisor::with_demo_launcher` resolves the launcher path once, via `tauri::process::current_binary`, and caches it for the supervisor's whole lifetime; every `spawn_harness` call execs that cached path with no re-probe of its identity (digest, signature, or modification time) immediately before each launch. [Threat model TM-001, HAR-3](threat-model.md) requires exactly that re-probe for a harness whose executable identity could go stale between launches — "re-probe immediately before launch; material change requires renewed approval and re-binds the identity evidence." This slice's cached-path shortcut is acceptable only because the "harness" it launches is this application's own binary (`--demo-harness`, gated by the non-default `demo-harness` cargo feature), re-exec'd in place — not a third-party executable a supply-chain compromise (TM-001 actor A10) could swap out between launches. A future slice adding a real, user-supplied harness must not carry this shortcut forward; it needs HAR-3's re-probe.

### The IPC contract

Three typed commands, registered next to `shell_health`:

| Command | Params | Returns |
| --- | --- | --- |
| `harness_spawn` | `kind: HarnessKindDto`, `rateHz: number`, `lines: number`, `onFrame: Channel<HarnessFrame>` | `ProcessIdDto` |
| `harness_stop` | `id: ProcessIdDto`, `deadlineMs: number` | `ProcessTerminalStateDto` |
| `harness_observe` | `id: ProcessIdDto` | `ProcessStatusDto` |

No program path or argument vector ever crosses this boundary in either direction: `kind` names one of two closed, synthetic behaviors, and `rateHz`/`lines` are small bounded numbers, validated (`1..=1000`, `1..=100_000`) into an `omnifrons_app::HarnessRequest` before the supervisor ever sees them. The supervisor turns a validated request into a real `ProcessSpec` internally, execing a launcher path fixed once at construction (`tauri::process::current_binary`) — never a path carried by any command argument.

Wire shapes (`src-tauri/src/ipc/dto.rs`, unit-tested field-for-field):

```jsonc
// HarnessKindDto (input only)
"demo-lines" | "demo-ignores-sigterm"

// ProcessIdDto
42

// ProcessTerminalStateDto — code is always present, null unless exited
{"state": "exited", "code": 0}
{"state": "killed", "code": null}
{"state": "orphan-risk/uncertain", "code": null}

// ProcessStatusDto (harness_observe's return)
{"status": "running"}
{"status": "terminal", "state": "killed", "code": null}

// HarnessFrame (harness_spawn's onFrame payload) — adjacently tagged
{"stream": "stdout", "body": {"id": 42, "seq": 3, "droppedBefore": 0, "text": "line 1 out"}}
{"stream": "stderr", "body": {"id": 42, "seq": 41, "droppedBefore": 12, "text": "line 205 err"}}
{"stream": "state",  "body": {"id": 42, "seq": 13, "droppedBefore": 0, "state": "exited", "code": 0}}

// ShellError (every command's error variant)
{"code": "spawn-failed", "message": "failed to start the requested process"}
```

`ShellErrorCode` is closed: `unknown-process`, `spawn-failed`, `already-subscribed`, `invalid-request`, `too-many-processes`. `message` is always one of a small, fixed catalogue of strings — never the underlying `SupervisorError::Spawn`'s `io::Error` text, which can carry a real path. `invalid-request` now also covers `harness_stop`'s `deadlineMs`, validated into `1..=30_000` before it ever reaches the supervisor (an unbounded caller-supplied deadline would otherwise let a single `harness_stop` call occupy its blocking-thread slot indefinitely). `too-many-processes` is returned when a supervisor already tracks its maximum number of concurrently running processes — see the capacity limits below.

Capacity and framing limits (`omnifrons-supervisor/src/output_capture.rs` and `lib.rs`): a per-process delivery channel holds at most **1024** frames (`try_send` only — full means the newest frame is dropped and counted, never that the reader blocks), **except** the final `State` frame, which is guaranteed-delivered via a dedicated blocking-send thread rather than dropped alongside text when the channel is full; a single text frame carries at most **8 KiB** of decoded text (`MAX_LINE_BYTES`), longer lines splitting into consecutive frames at a UTF-8 character boundary, never mid-character; `\r\n` is treated as a line end with the `\r` stripped, and a final line with no trailing newline is still delivered once EOF is reached. A supervisor also caps its own process bookkeeping: at most **16** concurrently running processes (`spawn`/`spawn_harness` refuse a 17th with `SupervisorError::TooManyProcesses`, mapped to `ShellErrorCode::TooManyProcesses`, without ever spawning it) and at most **256** retained terminal entries, oldest evicted first by termination order — an evicted id then reports `unknown-process`/`None` from a later `stop`/`observe`, never a re-signal of a pid the OS may have since recycled. An output-capture entry is removed once both finalized and subscribed-out (its receiver already taken via `subscribe`); an entry nobody ever subscribes to is retained indefinitely instead.

### Procedure notes for VP-S13

[VP-001 VP-S13](desktop-stack-verification-plan.md#scenario-catalog) ("IPC boundary: typed commands only; path attacks rejected") will eventually need this slice's commands exercised with a malformed-payload corpus. Candidate cases, once a packaged build exists to run them against:

- Raw filesystem paths (absolute, relative, UNC, `file://`) submitted as `kind`, where only the two closed string tokens are accepted.
- Path-traversal strings (`../../etc/passwd`, symlink targets) submitted the same way.
- Wrong JSON types for every field (`rateHz` as a string, a float, or an array; `id` as a string or negative number).
- Oversized numbers: `rateHz`/`lines` beyond `u16`/`u32` range, `id` beyond `u32` range, and boundary values just inside/outside the validated ranges (`0`, `1`, `1000`, `1001`, `100_000`, `100_001` for `rateHz`/`lines`; `0`, `1`, `30_000`, `30_001` for `harness_stop`'s `deadlineMs`).
- Extra, unexpected JSON keys alongside the accepted ones for every command (e.g. `{"kind": "demo-lines", "rateHz": 10, "lines": 10, "onFrame": ..., "path": "/etc/passwd"}`). Tauri's own per-parameter command binding (each `#[tauri::command]` argument bound by name from the invoke payload) *ignores* keys it has no matching parameter for, rather than rejecting the payload outright — confirmed against this slice's own commands, which declare no catch-all parameter. The corpus therefore cannot assert rejection for this case; it must instead assert that an extra key has *no effect whatsoever* (the command behaves identically with or without it present), since silent tolerance of an unrecognized key is not itself a path or argument reaching `omnifrons-supervisor`. Whether a future slice should close this permissiveness outright — an `AppManifest`-generated strict schema, or a wrapper request struct deriving `#[serde(deny_unknown_fields)]` for each command's arguments — is an open decision this slice does not make.

Expected outcome per [target architecture, invariant 4](target-architecture.md#proposed-invariants) and [RCS-001-R14](renderer-content-security.md): rejection with a typed `ShellError`, never a best-effort coercion, and never a path or argument reaching `omnifrons-supervisor`'s `spawn` — except the extra-JSON-keys case above, whose expected outcome is no-effect tolerance, not rejection.

### Procedure notes for VP-S15

[VP-001 VP-S15](desktop-stack-verification-plan.md#scenario-catalog) ("Structured streams, bounded backpressure, reconnection, malformed events, cancellation") is this slice's closest analogue among VP-001's scenarios. Candidate procedure, once a packaged build exists:

- Drive `harness_spawn` at the top of its accepted range (`rateHz = 1000`, `lines = 100_000`) against a renderer that does not drain `onFrame`, and confirm: `harness_spawn` and `harness_stop` still return promptly; the delivered frame count stays near the 1024-frame channel capacity, not the full line count; at least one delivered frame's `droppedBefore` is nonzero once the renderer resumes draining (`crates/omnifrons-supervisor/tests/output_backpressure.rs` is this slice's dev-mode analogue).
- Kill and restart the renderer mid-run; confirm `harness_observe` still reports the harness's true status and a fresh `harness_spawn` subscription is possible for a *new* process (this slice's `subscribe` is one-shot per process id, not reconnect-capable for an existing subscription — a gap this scenario should surface explicitly, not paper over).
- Inject malformed `HarnessFrame`-shaped events at the transport layer (not achievable through this slice's own commands, which only ever emit well-formed frames) to confirm the renderer's own parsing rejects them rather than crashing.
- Cancel mid-run via `harness_stop` with a short `deadlineMs` against a `DemoIgnoresSigterm` process, confirming escalation to `SIGKILL` and a definite terminal state within the deadline (`crates/omnifrons-supervisor/tests/demo_harness.rs` is this slice's dev-mode analogue).

### Renderer

The renderer half of this slice: a typed IPC client plus a minimal control panel driving it, all under `renderer/src/`.

- `ipc/harness.ts` — the *only* renderer module that imports `@tauri-apps/api/core`. Exports types mirroring `src-tauri/src/ipc/dto.rs` field-for-field (`HarnessKind`, `ProcessId`, `ProcessTerminalState`, `ProcessStatus`, `HarnessFrame`, `ShellError`), plus `harnessSpawn(request, onFrame)` (constructs a `Channel<HarnessFrame>`, wires its `onmessage` to `onFrame`, and invokes `harness_spawn` with exactly `{ kind, rateHz, lines, onFrame }`), `harnessStop(id, deadlineMs)`, `harnessObserve(id)`, and the `isShellError` type guard.
- `controlCharacters.ts` — `stripControlCharacters`, kept out of `PlainTextLine.tsx` so that component file only exports a component (the project's `react-refresh/only-export-components` lint rule).
- `PlainTextLine.tsx` — renders one line of untrusted text as plain text: strips C0 control characters (U+0000-U+001F except tab), DEL (U+007F), C1 control characters (U+0080-U+009F), and the bidirectional/format controls U+200B-U+200D (zero-width space/non-joiner/joiner), U+200E/U+200F (LRM/RLM), U+202A-U+202E (explicit bidi embeddings/overrides), and U+2066-U+2069 (explicit bidi isolates) — treated as format controls, not text, per RCS-001-R18, the same distinction RCS-001 already draws for OSC 0/2 titles and OSC 9 notifications ("control and bidirectional-override characters stripped"). Stripping U+200C/U+200D is a deliberate trade-off against scripts (Arabic, Indic) that rely on ZWJ/ZWNJ for correct shaping (`controlCharacters.ts`'s doc comment weighs the cost). Keeps every other character, no markup, no links, no OSC interpretation (RCS-001-R1, RCS-001-R18). `UntrustedText.tsx` is untouched.
- `HarnessPanel.tsx` — kind select (`demo-lines`/`demo-ignores-sigterm`), rate/lines number inputs validated client-side with `Number.parseInt` against the same bounds `omnifrons_app::harness_catalog` enforces (`1..=1000` Hz, `1..=100_000` lines; advisory only here, the Rust catalog is the sole authority and validates again regardless), disabling Start and showing an inline message for an empty, non-numeric, negative, or out-of-range value. Start/Stop buttons — Start additionally disabled while a spawn is pending or a harness is already active, since this slice allows only one active harness per panel; Stop disabled once no harness is active, including right after a successful stop resets it. A state badge renders the wire token verbatim (`running`, `exited (code N)` or `exited (code unreported)` when the platform reported no code, `killed`, `orphan-risk/uncertain` — never `done`, per target-architecture.md invariant 8). An output log renders every frame through `PlainTextLine` prefixed by its stream name, capped at the most recent 2000 entries with a `<mark>` marker ("showing the last 2000 lines; N earlier lines are not shown", N cumulative) once older entries are trimmed, plus a `<mark>` row ("N frames dropped before this line") whenever a frame's `droppedBefore` is nonzero. An error banner renders a `ShellError`'s `code` and `message` as plain text through `PlainTextLine` — or the fixed string "unexpected error", with no message text, for any rejection that isn't `ShellError`-shaped. A mount effect reads every process id remembered in `sessionStorage` (one key, `JSON.parse`/`JSON.stringify`, wrapped in try/catch) and calls `harnessObserve` for each: a still-`running` id shows "stream reconnected; earlier output not replayed"; a terminal status, an `unknown-process` rejection (a stale id, forgotten silently, no banner), or a completed `harness_stop` all prune the id from `sessionStorage`; any other rejected `ShellError` shows the banner once and also prunes the id, since it cannot be reconnected to either way. A `mountedRef` set false in that effect's cleanup guards both its promise handlers and the frame callback, so neither does anything once the component has unmounted. Mounted from `App.tsx` below the existing content.

Tests (Vitest + `jsdom`, `@testing-library/react`, `@tauri-apps/api/mocks`' `mockIPC`/`clearMocks`), all green:

- `ipc/harness.test.ts` (8 tests): `harness_spawn` is invoked with exactly the keys `kind`, `rateHz`, `lines`, `onFrame` and no path-shaped key; a frame sent on the live `Channel` reaches the `onFrame` callback; a rejected `harness_spawn` propagates its `ShellError` payload; `harness_stop`/`harness_observe` pass `id`/`deadlineMs` correctly and return the mocked shape verbatim (including `orphan-risk/uncertain`); `isShellError`'s positive and negative cases.
- `PlainTextLine.test.tsx` (11 tests): every C0 control character except tab is stripped, DEL is stripped, C1 control characters are stripped, the bidi marks/embeddings/isolates and the zero-width space/non-joiner/joiner are each stripped, tab is kept, non-ASCII is kept, and rendered markup stays literal (no `<b>` element, text visible).
- `HarnessPanel.test.tsx` (25 tests): initial render (kind options, input bounds, controls present); Rate/Lines validation (empty, negative, non-numeric, above-max all disable Start and show an inline message; correcting a value re-enables it); literal `<b>` frame rendering; the OSC 8 test (below, exact-equality); the dropped-frames `<mark>` text; the log-cap `<mark>` marker across 2500 pushed frames; the badge reading `killed` (with the exact `harness_stop` args asserted) and resetting `activeId`/disabling Stop once it resolves; `exited (code N)` and `exited (code unreported)`; `orphan-risk/uncertain` verbatim from a mocked `state` frame (asserting `done` never appears); the `spawn-failed` error banner with no `/` in its message, control characters stripped from a banner's code/message, and the generic "unexpected error" banner for a non-`ShellError` rejection; a second click not spawning twice while Start is disabled; a mount-time reconnection marker for a `running` remembered id, pruning on a terminal status, silent forgetting on `unknown-process`, the banner-once-and-prune path for another `ShellError`, and the mounted-guard test proving the mount effect no-ops (no `sessionStorage` write) once unmounted.

**What the OSC 8 test proves, and does not prove.** The panel is fed one `stdout` line containing a full OSC 8 hyperlink sequence — `ESC ]8;;https://example.invalid BEL label ESC ]8;; BEL` — and the test asserts the rendered output contains no `<a>` element and that the visible text is exactly the input with its ESC (`0x1B`) and BEL (`0x07`) bytes removed: `]8;;https://example.invalidlabel]8;;`. Every other byte, including the OSC marker's own punctuation (`]8;;`) and the URL text, survives literally, because `PlainTextLine` strips individual C0/DEL code points and never recognizes or interprets a sequence. This proves the stripping is per-byte and blind to OSC structure (so a malformed or partial escape sequence cannot smuggle a link past it) and that RCS-001-R18 ("sanitization must not remove textual content") holds on this path. It does **not** prove anything about a terminal content class or an OSC policy: this slice has no terminal pane, no confined terminal frame, and no OSC allowlist (renderer-content-security.md § Content classes and rendering modes defines that class; nothing here implements it). The harness output this slice renders is plain text — the default every content source with no declared class gets — never PTY output.

**Mocking `Channel` in `mockIPC`.** `@tauri-apps/api/mocks`' `mockIPC(cb)` replaces `window.__TAURI_INTERNALS__.invoke`; the real `invoke()` in `@tauri-apps/api/core` calls that function with its `args` object passed straight through, with no JSON serialization at that layer (serialization to the wire happens deeper, inside the real bridge `mockIPC` replaces). Confirmed against the installed package's own source (`@tauri-apps/api@2.11.1`'s `core.js` and `mocks.js`): the mock handler's `args.onFrame` is therefore the exact live `Channel` instance `harnessSpawn` constructed, not a serialized placeholder. Calling `args.onFrame.onmessage(frame)` from inside the mock handler is the approach that worked; no `Channel` mock or module-level hook was needed. Separately, jsdom has no WebCrypto implementation, and the mock's channel-id registry needs `window.crypto.getRandomValues` to mint callback ids for every `Channel` a test constructs; `testSupport/installJsdomCrypto.ts` installs a minimal, non-cryptographic fill for it (Tauri's own docs demonstrate this with Node's `crypto.randomFillSync`, but that does not type-check under `tsconfig.app.json`, which excludes Node's ambient types, so the fill here uses no Node built-in). Both this polyfill and React Testing Library's `cleanup()` after every test are installed once, centrally, by `testSupport/setup.ts` (`vite.config.ts`'s `test.setupFiles`), rather than each test file repeating its own `beforeAll`/manual `cleanup()` call. `vite.config.ts` also sets `test.allowOnly` explicitly to `!process.env.CI` (Vitest's own default, made explicit so a stray `.only` reads as a deliberate, reviewable choice rather than an accident that happens to also be caught in CI).

**Strict TypeScript.** `tsconfig.app.json` and `tsconfig.node.json` both set `"strict": true`; the renderer code (including every test file, since `tsconfig.app.json` includes `src`) already type-checked clean under it with no changes needed.

## Slice 2 — executable identity and approval

### What it proves

That a caller-supplied executable's identity can be probed, approved once, re-verified immediately before every later launch, and launched with no arguments — on Linux, in a development build:

- Identity is content, path, and size, never a timestamp: `ExecutableIdentity`'s equality (`crates/omnifrons-domain/src/executable.rs`) compares canonical path, size, and SHA-256 digest only, deliberately excluding `modified_at` and platform evidence — informational fields a re-probe can observe differently between two calls with no actual content change.
- `LaunchGate::decide` (`crates/omnifrons-app/src/launch_gate.rs`) never trusts a cached identity: it re-probes the recorded canonical path fresh on every call (a spy prober counts exactly one probe per `decide` call, never zero, never cached) and checks, in order, canonical path (`ShadowedPath` if the re-probe resolves elsewhere), digest/size (`ChangedSinceApproval`, carrying both digests), and status (`Revoked`) — matching [TM-001 HAR-3](threat-model.md)'s requirement to "re-probe immediately before launch". An approval store that cannot even be read denies fail-closed as `Unapproved` rather than risking a false allow.
- Revocation is honest and re-approvable: a revoked approval's id can never launch again, but the same identity can be approved again under a fresh id — `JsonlApprovalStore` (`crates/omnifrons-adapters/src/jsonl_approval_store.rs`) records this as an append-only log (mode `0o600` on unix; a revocation is a new line referencing the earlier approval id, never an edit of it), so the file's own growth is the evidence a revocation actually happened, and a truncated or malformed line fails the whole read as `Corrupt` rather than silently dropping it.
- `FsExecutableProber` (`crates/omnifrons-adapters/src/fs_prober.rs`) canonicalizes, then opens the canonical path *exactly once* (unix: `O_NOFOLLOW`, refusing a symlink placed at that exact path after canonicalization), and confirms *that one open file*'s own `fstat` is a regular, executable file within a 512 MiB cap before ever reading its content, then stream-hashes it in 64 KiB chunks from the same handle. A non-executable file is proven never hashed at all (a several-hundred-megabyte sparse fixture still probes as `NotExecutable` within a tight time budget, never actually reading that much content).
- On Linux, `FsExecutableProber` hashes *while copying* the candidate's bytes into a fresh, sealed `memfd` (`MFD_CLOEXEC | MFD_ALLOW_SEALING`, then `F_SEAL_SHRINK | F_SEAL_GROW | F_SEAL_WRITE | F_SEAL_SEAL`): the returned handle's content is provably exactly the bytes that were hashed, immutable from that point on, including against this process itself (`crates/omnifrons-adapters/tests/fs_prober.rs` proves the sealed length, digest, and a rejected write with `EPERM`). `TokioProcessSupervisor::spawn_approved` (`crates/omnifrons-supervisor/src/lib.rs`) then execs that sealed `memfd` directly via `/proc/self/fd/<n>`, with `stdin` always `/dev/null` — never the executable's own bytes — so a file replaced or overwritten at the display path after the seal was applied still executes the sealed content, proven directly (`crates/omnifrons-supervisor/tests/approved_launch.rs`) against a `#!/bin/sh` fixture whose display-path content is both replaced and overwritten in place after sealing, and against a fixture that reads its own `stdin` and observes only immediate `EOF`.
- The demo harness path is unaffected: `spawn_approved` launches with no arguments at all, never the `<kind> <rate_hz> <lines>` argv shape `spawn_harness` uses, and the shell's `harness_spawn` command dispatches to one or the other based on which tagged `kind` the caller sent. The demo launcher binary itself is explicitly exempt from the approval gate this slice: it is the app's own binary, whose identity the eventual UTA-001 platform signing will cover, not a caller-supplied executable this gate's threat model is about — a self-approval bootstrap for the app's own binary is deferred, not implemented here.

### What it defers

- **Any acceptance claim**, for the same reason as slice 1: this is a `dev-mode-only` result on one contributor's Linux machine. See [Relationship to VP-001](#relationship-to-vp-001-1) below.
- **Approval expiry.** An `ApprovalRecord` is `Active` until explicitly revoked; nothing ages it out on its own. [VP-S14](desktop-stack-verification-plan.md#scenario-catalog)'s own procedure notes below flag this as a real gap the eventual scenario should probably probe.
- **Store integrity beyond append-only structure.** `approvals.jsonl`'s `0o600` mode and JSONL-append discipline make *accidental* corruption or a naive rewrite detectable (a truncated line, or one carrying an unsupported `schema` value, fails closed as `Corrupt`), but nothing here is cryptographically signed or tamper-evident against a deliberate, well-formed edit by anyone with write access to the file (the device-local user this store's own trust model already assumes has that access, per `DeviceLocalUser`'s (`crates/omnifrons-domain/src/executable.rs`) own "opaque marker for whoever is using this device" framing — but a *different* local principal, or a later compromise of that account, could rewrite history undetected). Store signing is a real, named gap, not an oversight.
- **No single-instance guard on `JsonlApprovalStore`.** `ApprovalId` is now derived (`sha256(domain ++ canonical_path ++ sha256 digest ++ approved_at nanoseconds)`, first 8 bytes) rather than counted, and `record` rejects a derived id already on file (`ApprovalStoreError::Duplicate`) — this removes the specific "two concurrent `max() + 1` reads collide" race, but nothing here prevents two separate process instances (or two threads racing within one) from concurrently appending against the same file at all; a real single-instance guard (a lock file, an advisory `flock`) is deferred, not implemented.
- **Windows executable detection is provisional by extension allowlist alone** (`exe`/`com`/`bat`/`cmd`, `FsExecutableProber::is_windows_executable_extension`), never a real ACL or Authenticode signature check — `FsExecutableProber`'s own doc comment says so. Untested end-to-end in this spike (no Windows machine available; the extension check itself is unit-tested cross-platform, and a `#[cfg(windows)]` prober test exists but has not run on real Windows); a real Windows executability decision needs its own verification work.
- **No Windows equivalent of the Linux `O_NOFOLLOW` protection or memfd sealing.** `open_checked` (`crates/omnifrons-adapters/src/fs_prober.rs`) refuses a symlink placed at the canonical path after canonicalization on unix via `O_NOFOLLOW`; `std`'s `OpenOptionsExt` exposes no equivalent flag on Windows, so a symlink or reparse point swapped into that same narrow window would still be followed there. Windows also has no sealed-memfd equivalent, so every Windows probe returns `ExecHandle::File`, with only inode identity during hashing guaranteed and the hash-to-exec window fully open (see the TOCTOU bullet below). Both are documented, real gaps, not oversights.
- **No platform code-signing or publisher-identity verification anywhere in this slice.** "Approval" here means "a human clicked approve for this exact byte content once"; it says nothing about who published that content. This is a strictly narrower claim than a real code-signing check would make, and does not by itself close [TM-001 A10](threat-model.md) (a compromised distribution channel) beyond forcing re-approval on the next material change (HAR-3's own stated limit: "harness/adapter supply-chain integrity itself is outside TM-001's mitigation reach beyond re-approval").
- **The TOCTOU window's closure is platform-specific, stated exactly, not glossed over: Linux executes precisely the hashed bytes (sealed memfd); macOS/Windows: path spawn, in-place modification and substitution between hash and exec are not prevented.** On Linux, `FsExecutableProber` opens the canonical path exactly once (`O_NOFOLLOW`) and hashes while sealing the content into an immutable `memfd` (`ExecHandle::SealedMemory`); `spawn_approved` execs that sealed `memfd` itself via `/proc/self/fd/<n>`, so what actually runs is, by construction, exactly what was hashed — not a re-read of the display path, which may by then be replaced, overwritten, or retargeted. This still does not close every window: a symlink retargeted between `decide()`'s `canonicalize` and its one `open()` call is a race `open_checked`'s `O_NOFOLLOW` refuses only when it lands *at* the already-canonicalized path, and it proves nothing about a swap happening before that canonicalize step at all. On macOS and Windows (or a Linux probe that falls back to `ExecHandle::File`), `spawn_approved` spawns by the display path directly, with no such guarantee: only the *inode identity* observed while hashing holds, and in-place modification or a path retarget between hash and exec is not prevented there, exactly as `docs/target-architecture.md`'s honesty requirements demand recording rather than glossing over.
- **Malformed-payload fuzzing for the four new commands** (`executable_pick_and_probe`, `executable_approve`, `executable_revoke`, `approvals_list`) and the extended `harness_spawn` tagged `kind`. This slice proves the happy paths and the specific denial/TOCTOU cases above; VP-S13's adversarial corpus (slice 1's own procedure notes) has not been re-run against this larger command surface.
- **The renderer's `approved`-kind approval select does not live-refresh across components.** `HarnessPanel` and `ApprovalSurface` each hold their own independent `approvalsList()` fetch (no shared state, no context) — approving a new executable in `ApprovalSurface` does not update `HarnessPanel`'s own approval select until the `Kind` field is re-selected back to `approved` (re-triggering that panel's own fetch) or the page is remounted. A future slice should decide whether this needs a shared store or is an acceptable spike-only seam.
- **TM-001-R7's "act-as identity" clause has no distinct value to display in this narrow slice.** `ApprovalSurface` fully implements R7's identity-evidence display (canonical path, size, both digests, modification time, platform evidence), but this slice's one launch action is always "run this exact executable, with no arguments, as the current device-local user" — there is no separate actor identity a real multi-identity harness invocation would need to distinguish. Recorded here as an honest scope limit, not an omission.
- **The `changed-since-approval` handling in `ApprovalSurface` is defensive, not exercised by any wired backend path in this slice.** `executable_approve`/`executable_pick_and_probe`/`executable_revoke`/`approvals_list` never actually return this code today — only `harness_spawn`'s `LaunchGate::decide` path does, and that failure surfaces in `HarnessPanel`'s banner, not `ApprovalSurface`'s. `ApprovalSurface` still implements the required digest-comparison-plus-Renew UI generically, for whichever surface a future slice wires this code into, and its own tests exercise it via a mocked rejection rather than a real cross-component trigger.

### The IPC contract additions

Four new typed commands, registered next to `shell_health`/`harness_spawn`/`harness_stop`/`harness_observe`:

| Command | Params | Returns |
| --- | --- | --- |
| `executable_pick_and_probe` | *(none)* | `ProbeResultDto` |
| `executable_approve` | `candidateId: number` | `ApprovalDto` |
| `executable_revoke` | `approvalId: number` | `null` |
| `approvals_list` | *(none)* | `ApprovalDto[]` |

`executable_pick_and_probe` opens the native OS file picker (`tauri-plugin-dialog`'s `blocking_pick_file`, called only from a `spawn_blocking` task — calling it from the async executor's own thread would deadlock, per the plugin's own documented warning) and probes whatever the user selected. The raw path the user picked is **never** returned; `evidence.canonicalPath` — the *resolved*, symlink-followed path — is the one place a filesystem path reaches the renderer in this whole surface, deliberately, for [TM-001-R7](threat-model.md) display. A successful probe is remembered server-side under a fresh `candidateId`, in a bounded (32-entry, oldest-evicted) table scoped to this shell process's own lifetime — never persisted, never stable across a restart.

Wire shapes (`src-tauri/src/ipc/dto.rs`, unit-tested field-for-field):

```jsonc
// harness_spawn's kind parameter is now internally tagged, bundling each
// variant's own parameters, rather than a flat kind + optional
// rateHz/lines/approvalId set (deliberately: a flat shape would let a
// caller submit a meaningless combination, e.g. "approved" with a
// rateHz, that would then need extra validation to reject after the fact).
{"type": "demo-lines", "rateHz": 10, "lines": 100}
{"type": "demo-ignores-sigterm", "rateHz": 10, "lines": 100}
{"type": "approved", "approvalId": 42}

// ProbeResultDto (executable_pick_and_probe's success payload)
{
  "candidateId": 7,
  "evidence": {
    "canonicalPath": "/opt/tool/app",
    "size": 4096,
    "sha256": "<64 lowercase hex chars>",
    "sha256Short": "<first 8 of those hex chars>",
    "modifiedAt": 1732000000000,   // ms since epoch, or null
    "platform": {"os": "unix", "mode": 493}
    // or: {"os": "windows", "extension": "exe", "attributes": 32}
  }
}

// ApprovalDto (executable_approve's and approvals_list's payload)
{
  "approvalId": 42,
  "evidence": { /* same EvidenceDto shape as above */ },
  "approvedAt": 1732000000000,
  "status": "active",       // or "revoked"
  "revokedAt": null         // ms since epoch once status is "revoked"
}

// ShellError, extended with an optional structured `detail` (present only
// for changed-since-approval today; omitted entirely otherwise, never a
// literal `null`)
{
  "code": "changed-since-approval",
  "message": "the executable's content has changed since it was approved",
  "detail": {"recordedSha256Short": "aaaaaaaa", "observedSha256Short": "bbbbbbbb"}
}
```

`ShellErrorCode` gains nine variants this slice: `no-candidate` (an unknown `candidateId`/`approvalId`, or the file dialog returned nothing), `not-executable` (the re-probed target is not a regular, executable file — folding `ProbeOutcome::NotRegularFile` and `NotExecutable` together, since neither is actionable differently by a caller), `probe-failed` (the target could not be read at all), `too-large` (over the size cap), `unapproved`, `changed-since-approval`, `shadowed-path`, `revoked`, and `approval-store-unavailable` (the store itself could not be read or written — the closed `ApprovalStoreError` reasons, four as of the review-fix pass's added `Duplicate`, collapse to this one code for the same "not actionable differently" reasoning). Every message stays a fixed catalogue string with no `/`, matching slice 1's own no-path-leak discipline; only `changed-since-approval`'s `detail` ever carries digest material, and only as 8-character short-hex prefixes, never a full digest or a path.

The default capability (`src-tauri/capabilities/default.json`) stays `core:default` and nothing else — `tests/config.rs`'s `default_capability_grants_only_core_default` test is unchanged and still passes. This is not an oversight: `tauri_plugin_dialog::DialogExt::dialog()` is a direct Rust method call from inside `executable_pick_and_probe`'s own command body, never an IPC invocation of `plugin:dialog|open` from the webview — capability/ACL enforcement in Tauri 2 gates *IPC-invoked* plugin commands crossing the webview boundary, not a Rust-side call one of the shell's own commands happens to make into a plugin crate's API. Confirmed against `tauri-plugin-dialog@2.7.3`'s and Tauri's own documentation before relying on it, not assumed.

### Procedure notes for VP-S14

[VP-001 VP-S14](desktop-stack-verification-plan.md#scenario-catalog) ("Executable identity, re-probe, shadowed-path resistance") is this slice's direct analogue. Candidate procedure, once a packaged build exists:

- Approve an executable, then replace its content in place (same path, new bytes) before relaunch: expect `changed-since-approval`, with both recorded and observed short digests present and distinct (`crates/omnifrons-app/tests/launch_gate.rs`'s `rewritten_file_is_denied_with_both_digests` is this slice's dev-mode analogue).
- Approve an executable, then retarget the path to a different file (a symlink swap, or a same-named replacement one directory level up) before relaunch: expect `shadowed-path`, with both the approved and resolved canonical paths present (`shadowed_path_is_denied_with_both_paths` is the analogue).
- Revoke an approval and attempt to relaunch it: expect `revoked`; then re-approve the same executable and confirm the *new* approval id launches while the old one stays permanently denied (`revoked_approval_is_denied`, `re_approval_after_revoke_is_allowed`).
- On Linux specifically: replace the approved file's content in the narrow window between the shell's `LaunchGate::decide` call and the actual launch, and confirm the *original*, already-vetted content still executes rather than the replacement — this is a *positive* assertion (the narrowed window held), distinct from every other case above (which assert a *denial*) — `crates/omnifrons-supervisor/tests/approved_launch.rs` is the dev-mode analogue; the real scenario should also attempt to defeat this window (e.g. a tighter race, or a symlink swap instead of an unlink-and-recreate) and confirm whether it still holds under real timing pressure, not just this test's own generous ordering.
- Confirm no approval ever silently expires: leave an approval untouched for whatever the longest realistic gap between launches is, and confirm it still launches — this is the flip side of "expiry" being a deferred concern above, and the scenario should decide whether that absence is acceptable or a gap to close before VP-001 can rely on it.
- Attempt the same shadowed-path/rewritten-content attacks on macOS and Windows and confirm the *documented* outcome — a denial when the gate's own re-probe catches it (since `decide`'s comparison logic is platform-generic), but with the residual TOCTOU window from decide to launch left open there, never narrowed the way Linux's fd-exec path narrows it. The scenario's expected outcome on those two platforms is therefore "a race is theoretically possible, not eliminated" rather than the stronger claim available on Linux — recording that difference plainly, not silently normalizing it away.

Expected outcome per [TM-001 HAR-3/HAR-4](threat-model.md): "material change requires renewed approval and re-binds the identity evidence" and "canonical path resolution before authorization" — both properties this slice's `LaunchGate::decide` implements and its own tests exercise, with the platform caveats recorded above.

### Renderer

The renderer half of this slice: the tagged `HarnessKind` wire shape, a standalone executable-approval surface, and the `HarnessPanel` additions that drive a real, previously approved executable — all under `renderer/src/`.

- `ipc/harness.ts` — `HarnessKind` is now a discriminated union mirroring `HarnessKindDto` field-for-field (`{ type: 'demo-lines', rateHz, lines }`, `{ type: 'demo-ignores-sigterm', rateHz, lines }`, `{ type: 'approved', approvalId }`); `harnessSpawn(kind, onFrame)` takes the tagged `kind` object directly and invokes `harness_spawn` with exactly `{ kind, onFrame }` — no top-level `rateHz`/`lines` any more, since a demo kind now carries them nested inside `kind`, and no path-shaped key ever crosses this call regardless of which kind is requested. `ShellErrorCode` gains the nine slice-2 variants (`no-candidate`, `not-executable`, `probe-failed`, `too-large`, `unapproved`, `changed-since-approval`, `shadowed-path`, `revoked`, `approval-store-unavailable`) plus `too-many-processes` (slice 1's own code, added to the renderer's type only now since nothing exercised it before). `ShellErrorDetail` (`recordedSha256Short`/`observedSha256Short`) is optional on `ShellError`, present only for `changed-since-approval`. New types mirror the Rust DTOs verbatim: `Evidence`, `PlatformEvidence`, `ProbeResult`, `Approval`, `ApprovalStatus`, plus the opaque `CandidateId`/`ApprovalId` number aliases. Four new typed wrappers: `executablePickAndProbe()`, `executableApprove(candidateId)`, `executableRevoke(approvalId)` (discards `invoke`'s resolved value, always resolving `void`), `approvalsList()`.
- `ApprovalSurface.tsx` — a standalone region (`role="region"`, `aria-label="Executable approval"`), never mounted inside `HarnessPanel` or any output/terminal pane (RCS-001-R6; `docs/renderer-content-security.md`'s guarantee that no rendered content appears inside an approval surface). "Pick executable" calls `executablePickAndProbe()` and, on success, renders every evidence field — canonical path, size, SHA-256 (full and short), modified time, platform evidence — each through `PlainTextLine`, so a canonical path containing literal markup (e.g. `<b>x</b>`) renders as text, never an element. A `no-candidate` rejection from this specific call means the OS file dialog returned nothing — the user simply cancelled it, a normal outcome — and renders as a quiet `role="status"` line ("No file selected") rather than the error banner; every other rejection, from this call or from `executableApprove`/`executableRevoke` (e.g. a stale/unknown candidate id, which also currently reports `no-candidate`), still renders through the banner as a real error. `executable_pick_and_probe` and `executable_approve` sharing that one code for two different situations — distinguished here only by which call produced it, not by the code itself — is a known seam; a distinct `pick-cancelled` code that separates the two at the type level is a Rust-side follow-up, not yet implemented. Approval is a distinct, deliberate act, not a bare confirmation click: a text field requires the user to type the candidate's own short digest, exactly, before the Approve button is enabled at all — no fixed phrase accepted in its place, so the act cannot be completed without having read the evidence it stands in for (TM-001-R7's "a human decision grounded in what will actually run"). Immediately above that field, the surface also states plainly "Approving as: this device's local user" (TM-001-R7's act-as identity clause: the one actor this surface can ever bind an approval to, in a slice with no separate account/identity selection). Approve then calls `executableApprove(candidateId)` and merges the returned record into the approvals list directly (no refetch needed, since the command's own response already carries the full `ApprovalDto`). Each listed approval shows its canonical path and status; an active record's own "Revoke" button — disabled for that record while its own revoke is in flight, so a double-click cannot fire a second `executable_revoke` for the same id — calls `executableRevoke(approvalId)` and then refetches `approvalsList()` to pick up the store's own recorded `revokedAt`. Errors render through a sanitized `role="alert"` banner exactly like `HarnessPanel`'s own (code and message via `PlainTextLine`, the fixed "unexpected error" string for a non-`ShellError` rejection); a `changed-since-approval` error additionally shows the recorded and observed short digests side by side and a "Renew approval" button that re-runs pick-and-probe then approve — deliberately never a "proceed anyway" affordance, matching HAR-3's "material change requires renewed approval" with no bypass; a `no-candidate` rejection during that re-pick is the same quiet, non-error outcome as the initial pick's own cancellation. A mount effect calls `approvalsList()` once; a `mountedRef` guard (the same pattern `HarnessPanel` already uses) makes every async continuation in this component — pick, approve, revoke, and renew alike — a no-op once unmounted.
- `HarnessPanel.tsx` — the `Kind` select gains a third option, `approved`; selecting it hides the Rate (Hz)/Lines inputs entirely and shows an `Approval` select instead, populated from `approvalsList()` fetched lazily the first time `approved` is selected (never on mount, and never at all if `approved` is never selected) and filtered to `status === 'active'` records only, with Start staying disabled until that fetch settles and an approval is actually selected. Each fetch is sequenced against a monotonic request id, so a stale response from an earlier fetch (e.g. leaving `approved` and re-selecting it before the first one settled) is dropped rather than overwriting a newer one applied in the meantime. Leaving `approved` for another kind clears that kind's own error banner and forgets the selected approval, so returning to `approved` later always requires re-selecting one. Start, for the `approved` kind, sends `harnessSpawn({ type: 'approved', approvalId }, onFrame)` — exactly `{ kind: { type: 'approved', approvalId }, onFrame }` crosses IPC. A `LaunchGate` denial (`unapproved`, `changed-since-approval`, `shadowed-path`, `revoked`) renders in the same error banner as every other `ShellError`, prefixed with the shared public token `untrusted` — the four denial codes all mean the same thing to a caller ("this executable is not cleared to launch right now") even though their underlying cause differs — and, only for a `changed-since-approval` denial specifically, its `detail` renders both short digests inline (never for any other code, even one that happens to carry a `detail` object). The state badge's own token set is unaffected: a denial happens before any process exists, so `badge` never shows anything but its prior value.
- `App.tsx` mounts `ApprovalSurface` as a sibling of `HarnessPanel`, immediately after it, never as a child — the only place in the renderer these two components' trees meet at all is the common parent `<>...</>` fragment `App` returns.

**The RCS-001-R6 containment test.** `HarnessPanel.test.tsx` renders `<HarnessPanel /><ApprovalSurface />` together (mirroring how `App.tsx` actually mounts them) and asserts `log.contains(region)` is `false` for the `Output log` list element and the `Executable approval` region — a direct, executable check that the approval surface never ends up nested inside a terminal/output pane, rather than only an inference from `App.tsx`'s own sibling placement.

### Relationship to VP-001

Every result behind this slice — every passing test listed above, `cargo fmt`/`cargo clippy -D warnings`/`cargo test --workspace --all-targets --all-features` all green, the supervisor suite repeated three times with identical results — was produced against a `cargo test` development build, on one contributor's Linux machine, not a packaged release build on a pinned Windows/macOS/Linux baseline, and not against macOS or Windows at all. Per [VP-001-R2](desktop-stack-verification-plan.md#product-requirements), this is `dev-mode-only` and therefore **not** admissible as VP-S14 evidence; it is an input to writing that scenario's procedure well (above), and to the platform-honesty caveats VP-S14's eventual macOS/Windows rows will need to record about the TOCTOU window this slice only narrows on Linux.
